# Changelog

## 0.7.3

- **A refused proposal says which field broke.** The report helper on Linux, macOS (`mailbox_worker.sh`, jq) and Windows (`mailbox_worker.ps1`) still answers `invalid_schema` on its first line, and now adds one second line naming the field and the rule, for example `payload.checks[0].argv: must hold 1 to 16 entries, has 49`. Every coordinator proposal kind (new_work, add_source, dispatch, report, review, rollover, landing) names its field, with the field and its rule on each system (the rule's wording can differ between jq and PowerShell); any report names a missing or unknown field and the envelope's action and handover pairing; other report kinds' value rules say `payload: invalid payload for this kind` (POSIX) or keep the bare code (Windows). On Linux and macOS the same jq rules run in an explain mode only after a refusal, so the explanation cannot drift from the check; accepted and refused reports are unchanged (SKILLS-214: a coordinator spent about a minute guessing why its proposal was refused).

## 0.7.2

- **One file is one install.** On a system where `/bin` and `/usr/bin` are the same folder (Ubuntu and most current Linux), Guided setup counted `/bin/claude` and `/usr/bin/claude` as two installs, so a second Claude account could be proposed the same install, and so the same login. A program reached twice on PATH, through a linked folder or a link to the same file, is now one install (SKILLS-213, found in the live run on the VM).
- **"Not used" names you first.** The not-used line names the accounts named for the provider and your own installs, then counts the other OS accounts that can run the CLI ("43 other OS accounts can run it too (Change some to pick one)"); before, your own install could be hidden in "and 86 more". The Change some choices list installs in the same order.

## 0.7.1

- **Guided setup fits the common case: one person, one login, one folder (SKILLS-213).** The questions used to be shaped by a machine with one OS account per seat: a person alone had to tick their own login, got a "Skip Claude" filler per provider and IDs such as `claude-ann` labelled `ANN`. Now the first questions ask only about accounts: "Are there any providers for which you have more than one account?" (No is the default). On Yes: which providers, how many accounts, then their labels, numbered (Claude 1, Claude 2) or typed. SPAWN never suggests a label. One account per provider needs no label: the agent is `claude`, labelled Claude.
- **The script runs a second time with those answers** and proposes which install runs each account: every OS account that can run the CLI (reached the way SPAWN launches it) and every program of that CLI name on each account's PATH, a second install or a wrapper included. One person on one account gets one confirm: "All agents run as ann?". Several accounts get the proposed table and "Use this mapping?". An account named for the provider (`claudework` for a label Work) or a folder holding an install (`acct2` for a label acct2) is matched by name; the rest follow in order. Another person's OS account is listed as not used and is only used when chosen. "Change some" picks another install, a typed path or skip, and the script checks the choice.
- **An account with no install of its own is said plainly, never worked around:** "Claude 2: no second install or OS user found. Each Claude account needs its own install with its own login. Type its path, or skip it." Agy adds that it keeps its login per OS user. SPAWN never logs in, switches, shares or copies an account, and refuses two agents that would run the same install as the same account.
- **Permissions:** one question first, "Do you want to set special permission modes to start some of these agents with?" (No, all Default). On Yes, per agent: Default (no arguments), YOLO (that CLI's no-ask flag, offered only when its own `--help` shows it) or Custom (typed, then checked by the script as argument data). Kimi's separate "Ask when needed (`--yolo`)" choice is gone.
- **Folder:** when Glitch is found, "I detected Glitch at <path>. Would you like to start all these agents within Glitch?" All, Choose per agent, or None; every other agent starts in its own account's home folder. Without Glitch the question is not asked. OMP still gets its service question per OMP agent, with its own config's service first.
- The Windows twin asks the same questions in the same words and takes the same answer flags (`--phase`, `--accounts`, `--map`, `--skip`, `--check-args`); every Windows install is the signed-in user's own, a `.ps1` install included.
- **Model and effort follow the provider, not the program's file name.** The provider is the CLI SPAWN launches, so a second install or a wrapper can be named anything: a provider Claude agent whose program is `ClaudeSUPERAWESOMEACCOUNT` takes `--model` and `--effort`, and its List models (grok, agy, OMP) runs that agent's own program. A provider that is not one of the seven CLIs (Claude, Codex, Kimi, Grok, Agy, Muse, OMP), such as "Claude Work", refuses model and effort with a clear message instead of falling back to the program's name. This replaces 0.7.0's rule "the CLI is the program the launch actually runs". Records without model or effort are unchanged. The manual Prepare form's POSIX default agent now has provider OMP (its program is `omp`).
- The saved record keeps its shape, so saving and preparation are unchanged.

## 0.7.0

- **Choose the model and the effort per agent.** An agent's model and a new `effort` field now reach the CLI's argv, derived from one per-CLI capability table (`selectors.luau`). Set them on **Agent settings** (a Model text box, and an Effort drop-down for CLIs that have one) or on the **Setup** form. Nothing chosen adds no flag: a record without them launches byte for byte as before.
- **Model choices from the CLI's own listing, or free text with the CLI's flags (SKILLS-211).** On Agent settings, grok, agy and OMP agents get a **List models** button that runs the CLI's own read-only listing (`grok models`, `agy models`, `omp models --json --no-extensions`) as that agent's OS account (listing takes the launch's own route: the record is resolved as a launch resolves it and a literal `sudo -u` wrapper is read by the same function launch uses, so the agent's own executable runs as the account launch would use, from the record's absolute launch folder, and each account, executable and folder keeps its own catalog; a relative or empty folder, SSH, Windows and any route launch refuses are not listed); the Model field then becomes a drop-down of the listed ids with "CLI default" first. It runs only when you click, starts no agent, saves nothing, and never lists for an SSH agent. A listing that fails, needs a sign-in or prints nothing usable keeps the free-text field and shows why. Claude, Codex, Kimi and Muse have no headless model-list command, so their Model field is free text with helper text naming that CLI's model and effort flags. Empty always means the CLI's own default.
- **A model becomes a flag only when it was explicitly chosen.** Typing an id in the form or editor writes `model` and `model_selector: true`. A model saved before 0.7 is display text: it never becomes a flag, never refuses a launch whatever its length, and the editor shows it as a label with the way to turn it into a selector. `model_selector` is also what a setup result must set to ask for a flag.
- A selector id is exact, never an alias SPAWN invents: not empty, only letters, digits and `. _ - : / @ + [ ]` (so a `.cmd`, `.bat` or `.ps1` shim cannot re-read it as shell syntax), no leading `-`, at most 200 bytes. Effort is a drop-down limited to the values that CLI's own `--help` lists; a CLI with no verified effort flag shows no Effort control and refuses `effort`.
- **The CLI is the program the launch actually runs**, not the provider label: the executable of that launch (ordinary or fresh), with a literal `sudo` form unwrapped. A provider label and a program naming different known CLIs, or an ordinary and a fresh launch naming different ones, are refused. An unknown program refuses model and effort with a clear message.
- Flags added: claude `--model`, `--effort`; codex `-m`; kimi `-m`; grok `-m`; agy `--model`, `--effort`; muse `--model`, `--reasoning-effort`; OMP `--model=`, `--thinking=`. Not supported yet: codex, kimi and grok effort (values not verified from `--help`).
- A native OMP fresh default may now carry a model selector and `effort` (only those two derived flags; `profile` is still refused), so a coordinator can start on a chosen model.
- No double flags. Only the program's own option region counts, ending at its own `--` (text after it is positional). Setup, Agent settings, full-record JSON and approval refuse a record that types the same flag, except a conflict the record already held with an unchanged launch contract (selector fields and that option region). At launch a typed flag wins and none is added.
- Windows launcher shims count as their CLI: `codex.cmd`, `claude.bat`, `kimi.ps1` (any case) get model and effort flags like `codex.exe`, and only for selectors: a record without model or effort reads its command exactly as 0.6.6 did (`.exe`, `.cmd`, `.bat` only), so `codex-acp.ps1` and `sudo.ps1` are unchanged there.
- A short flag typed attached (`-mVALUE`, codex, kimi, grok) counts as a typed flag, so it is refused beside a chosen model; `-mv` is refused too (safe side).
- Derived flags never split a named task option from its value: when the task follows an option such as `--prompt` or `-p`, the flags go before that option, so `kimi -m kimi-k3 --prompt TASK`.
- A command that reads two ways under model or effort (a Windows path or POSIX shell words, for example `claude --add-dir /tmp/a\ b/claude.exe`) is refused instead of validated under one reading; with model or effort the two readings must be identical, so a Windows-style command with a backslash (even a bare `C:\Tools\claude.exe`) can no longer carry model or effort: use a launcher on PATH (for example `claude`) and put options in Arguments. This is an intended behaviour change; records without model or effort are unchanged (argv byte-identical). Launch also refuses model or effort on an unknown CLI instead of dropping them silently.
- The model and effort show where SPAWN already showed the record's model label.
- Setup JSON (manual import and a guided result) gets the same duplicate-flag refusal as the editor: a new record that types a flag its model or effort field also sets is refused before it is saved; a saved conflict stays only while its launch contract is unchanged.
- Model and effort are refused on a literal `sudo -i` or `sudo -s` launch: the target's login shell would read the value a second time (a `$` would expand). Set the OS user instead; SPAWN's own login wrapper quotes the value.

## 0.6.9

- **Guided setup asks one exact, fixed set of questions.** The helper used to improvise its questions: one list titled "Claude (anthropic)" held every provider's accounts, and "Glitch installation not detected" meant it had never looked. SPAWN now ships `structuredquestions.sh` (and `structuredquestions.ps1` for Windows) beside the setup skill. The helper runs it once. It is read-only: it finds every provider CLI as each candidate account (`sudo -n -i -u <account>`), reads each OMP account's own service from its config, checks permission flags against the installed `--help`, and prints the prompts already filled in: Accounts (one list per provider), IDs and labels, Folder, Permissions (one question per provider, Normal preselected), the OMP service per OMP account, and the final Save. The helper shows them word for word in its own question tool. It never asks for a model or a startup prompt (OMP records get the fixed default prompt).
- The script splits prompts to the stricter of Claude Code's AskUserQuestion (1-4 questions per prompt, 2-4 options per question) and OMP's ask tool, for example "Agy: which accounts should SPAWN run? (1 of 2)" when five accounts would not fit one list.
- The setup skill shrank by about 2 KB (it is stored in durable authority metadata at its byte budget), and the run context SPAWN appends now names the script's path.
- The script never puts a path inside a shell string (it crosses the `sudo -n -i` login as one encoded word, like SPAWN's own launches), encodes every field it reads so a newline or tab in a path cannot forge a row, bounds every external call itself (no GNU `timeout` needed; Windows uses `WaitForExit` + `Kill`), probes each account's own `sudo -n -i -u` route instead of root, checks permission flags against every account's own `--help` (an option names the accounts that lack it), lists at most three Glitch folders as choices, and the Windows twin reads OMP's configured service. The skill forwards every observed Glitch candidate.
- A timed-out call is killed as a whole process group (setsid, else perl's setpgrp), flags match as exact tokens and a valued flag needs its value in its own help entry, and the Windows twin starts npm `.cmd`/`.bat` shims through `cmd.exe /d /c` and skips one provider that cannot start instead of aborting.
- A help entry's continuation must be indented deeper than the flag's own line (a sibling `MODEL ... yolo` entry no longer enables YOLO). The Windows twin stops the whole process tree of a timed-out call (a `.cmd` shim's hanging child CLI included, on Windows PowerShell 5.1 and 7), reports that provider as unavailable, and writes UTF-8 to stdout. Proven on Windows PowerShell 5.1 and PowerShell 7.
- **Glitch is searched in more places.** Besides the launch folder's and the plugin's parent folders, setup now checks the Glitch root WORK saved on that host, `/opt/glitch` and `~/Glitch` (`%USERPROFILE%\Glitch` on Windows), each verified the same way (SKILLS-210).

## 0.6.8

- **Guided setup resolves each agent's CLI as the account that runs it.** On a host with several OS accounts, the setup helper looked up `grok` as the operator and wrote the operator's `/home/<operator>/.local/bin/grok` into another account's record; that account cannot run the file, and preparation stopped at that record. The setup skill now resolves every cross-account CLI through the same login route SPAWN launches with (`sudo -n -i -u <account> -- sh -c 'command -v <cli>'`), checks that the account can execute it, shows an account without the CLI as unavailable instead of borrowing another account's file, and proposes the account, provider and CLI table itself, so the operator approves it without typing paths.
- Preparation checks (account, home, executable, helper tools) now run on that same `sudo -i` login route instead of a bare `sudo -n -u … -H`, so a tool found at discovery on the account's login PATH is the one preparation finds.
- The helper writes such a record in the shape SPAWN stores after preparation: the account in `user` and that account's own executable in `command`, with no `sudo` wrapper (SKILLS-209).

## 0.6.7

- **Forget protocol `spawn-work-v1`.** SPAWN now answers the Forget exchange used by ORCH+: a capability check, a read-only preview of what would be discarded, and the discard itself. The discard is protected by a durable fence, a reservation cleanup journal, and accounting for helper child processes, so a repeated or interrupted discard is safe (SKILLS-205).
- Agents run as another OS account now start through a real `sudo -i` login, so they get that account's own PATH, including `/usr/local/bin` and `uv`. The program, its arguments and the folder cross to the other account as encoded data, so nothing in them is interpreted by a shell on the way. A launch with an empty folder is refused (SKILLS-208).

## 0.6.6

- **A helper result that SPAWN refuses is no longer silent.** Guided setup could finish with 0 agents saved and no message. Cause 1: the helper (OMP) moved itself out of its launch folder after SPAWN bound it, and SPAWN refused the result because the pane's folder no longer equalled the launch folder; the pane is now identified by its id, session, command and window incarnation only. Cause 2: the helper wrote the OMP startup prompt as `startup_prompt` instead of `prompt`; that refusal is legitimate, now names the field, and the setup skill names `prompt` exactly. Every refusal is also published to the window, so Recover setup result shows "SPAWN refused the helper's result: ..." instead of "No complete explicit submission is available".
- The OMP helper stays in the folder SPAWN started it in. OMP silently switches to a temp folder when started in a home folder; SPAWN now adds `--allow-home` for an OMP helper only when the chosen folder is a home folder.
- Agents run as another OS account now enter that account's login shell, so its `~/.profile` PATH (`~/.local/bin`) and exported login tokens apply. The shell is read from the account's passwd entry (never from the environment), the approved program and arguments travel as one fully single-quoted command run after the profile, and the launch folder is restored after it, so a profile cannot move the agent or change its argv. `-n` is kept (no password prompt). This covers literal `sudo -n -H -u <account> -- <program>` records that carry no separate user field. `sudo -i` is not used because it leaves `$` unescaped. Its lookups run with a fixed PATH, a program name starting with `-` is refused, and the account's profile still builds the real PATH. An explicit `sudo -i`/`-s`, a shell target, an unknown shell or a missing passwd tool is run through plain `/bin/sh` or as before. If your sudoers rules allow only specific programs, they must also allow `/bin/sh`.
- A refusal shown on Setup is bound to its own authority, setup run and submission binding; another run never displays it.

## 0.5.0

Requires Tern 0.9.10 (now declared in `requires.json`).

### Added

- Self-updater: **SPAWN: Check for updates** reports whether a newer SPAWN is on GitHub (a background check runs at most every 6 hours), and **SPAWN: Update** checks the release's `requires.json`, asks first, optionally updates connected remote hosts, then reinstalls with `tern plugin install --force`. Linked development checkouts are never updated. Copies installed before 0.5.0 need one manual `tern plugin install --force github.com/blastworksai/tools/plugins/tern/SPAWN`.
- Config has a **Spawn agents** page: one **Spawn all** button and one button per saved record with its provider logo, `Provider — Suffix` and its command, arguments and working directory. Disabled records and records needing review are greyed with the reason.
- Automatic settlement: the host checks its panes on load, every 15 seconds and after each observation, and moves ordinary launches to history by itself: `Exited` "Pane closed", `Failed` "Never started (ticket not claimed)" after 30 seconds, `Exited` "Host restarted" 20 seconds after a host restart. Agents Tern reruns in their pane within those 20 seconds are re-adopted as `Running`. On non-Linux hosts the restart epoch is unverifiable, so only the pane rule applies. Managed (ORCH+) launches are unchanged.

### Changed

- One record can run any number of copies: every Spawn starts a new launch. Only disabled records are skipped.
- The SPAWN menu is **Guided setup** (only until the first record is saved), **Config**, **Spawn all** and **Spawn specific**. **Running agents** and **Review setup result** left the menu; the `SPAWN: Running agents` and `SPAWN: Guided setup` palette commands stay, and **Review setup result** moved to Config › Setup while a setup run is active.
- The host-restart notice is one informational line, "Host restarted: N SPAWN agents ended (cleared automatically)", with no action.
- When a batch finishes, SPAWN closes the Config view it opened for that batch instead of hiding it, so no idle SPAWN block is left behind. A Config you opened, or are looking at, stays.
- Reset transport now waits only for live or managed attempts.

### Removed

- The `duplicate_policy` record field and the `skip`/`allow` duplicate choice.
- **Mark no longer running** and **Mark all N lost agents no longer running**, with the `resolve_attempt` and `resolve_lost_attempts` operations and the `Unknown` blocking state for ordinary launches.

### Fixed

- The Config › Setup **Guided setup** row raised an error; it now starts Guided setup.

### Upgrade notes

- Saved records, Paste JSON imports, setup results and managed imports that still carry `duplicate_policy` have it stripped on restore or import, never rejected.
- A retained or journalled old Mark request is cleared automatically ("An old Mark-no-longer-running request was cleared; SPAWN now does this automatically") and never replayed.
- Leftover parked SPAWN Config blocks from older versions are closed when the window loads, unless one still has a pending request.
- Launches left `Unknown` by an older version settle on the host's first check.

## 0.4.0

For ORCH+ 0.4.0. The mailbox helpers changed: reinstall `mailbox_target.*`, `mailbox_worker.*`, `mailbox_json.awk` and `mailbox_reply.jq` on each execution target. Ordinary SPAWN launches are unchanged.

Includes all 0.3.1 fixes (SPAWN 0.3.1 had no changelog of its own; its entries are the `SPAWN:` items under ORCH+ 0.3.1): a short focus guard keeps managed launches from taking focus; a pending request the host already refused is acknowledged automatically; attempts lost to a daemon restart are recognised and can be released together with **Mark all N lost agents no longer running** (`resolve_lost_attempts`); **Spawn all** waits 5 seconds between launches; unused-mailbox retirement accepts a launch whose window challenge expired unconsumed.

### Changed (breaking)

- Managed records may declare up to seven mailbox capabilities (was five): `check-runner-v1` and `release-manager-v1` are new. Config, the codec and both helpers accept the same set.
- REVIEW_RESULT is now `{review_id, round, artifact_revision, outcome, findings, summary?}`, with findings tied to file and line, instead of `evidence`. Coordinators no longer send it; ORCH+ reviewer workers do.
- `landing_grant` and `deploy_grant` replies need `release-manager-v1` in the provisioned capability set; the helpers refuse them otherwise (`capability_missing`).

### Added

- Assignment manifest: `mailbox_provision` accepts optional `manifest` bytes (declared checks, files, scope and base ref; at most 4,096 bytes). Its digest joins the provision binding digest and `provision.json`, and the target helper writes the bytes as `manifest.json`. Provisions without a manifest keep their 0.3.0 digest and descriptor.
- Helper mode `checkout` (POSIX and Windows) publishes CHECKOUT from git: worktree, common dir, branch, head, merge base, changed files (committed, staged, unstaged and untracked; at most 512) and a dirty flag. Without a manifest `base_ref`, the first `checkout` pins the launch HEAD in `<mailbox>/checkout-base`, so later checkouts report committed (including out-of-scope) files instead of only uncommitted ones; a tampered pin is refused `storage_error`.
- Helper mode `run-checks <check_id>` (Windows: `-Mode: run-checks -CheckId: <check_id>`) runs one declared check's exact argv from the authenticated manifest without a shell and publishes CHECK_RESULT with its argv digest, exit code, output digest and head.
- CHECK_RESULT and CHECKOUT are helper-only: publishing them through `report` is refused `helper_only_kind`. Refusals `capability_missing`, `manifest_missing`, `manifest_mismatch`, `check_undeclared` and `git_unavailable` are definite and publish nothing.
- New report kinds LABEL and DEPLOY_RESULT (the latter needs `release-manager-v1`); new reply kinds `review_request`, `rework`, `deploy_grant` and `label_request`; DONE may carry `output_ref`.
- The helper JSON validator accepts arrays of up to 512 entries (was 256), for CHECKOUT's changed-file list.

### Fixed

- POSIX `wait` no longer leaves `producer/lock` behind with no running helper, which refused every later call `producer_locked`. A later poll or an interrupted wait now waits up to 10 seconds for a capacity gate held by a target commit; if the gate stays busy, the helper leaves it untouched and still removes its own empty workspace and producer lock. A helper killed without cleanup still needs explicit stopped-producer recovery (see BRIDGE.md). The PowerShell helper's lock already ended with its process; its `wait` polls and post-retirement lock-file removal now wait out a busy gate the same way instead of failing `capacity_locked`.
