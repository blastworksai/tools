# SPAWN managed dispatch bridge reference

Full specification of SPAWN's host-local dispatch receiver that [ORCH+](../ORCH+/README.md) uses: managed launch, authority compatibility and retention, managed configuration, mailbox producer prerequisites, the public dispatch protocol, owner-gated import and recovery, bounds and durability, and verification entrypoints. For ordinary SPAWN use see [README.md](README.md).

## Scope

SPAWN keeps one canonical host-owned configuration and ordinary launch ledger. The window resolves that host roster rather than choosing a client-local copy. The main palette opens a real right-hand pane: Setup with Guided setup first until a reviewed configured agent exists, otherwise Start an agent. Each explicit launch selects one saved agent; ORCH+ owns multi-agent orchestration. Retired bulk-launch settings are stripped during a backed-up, idempotent roster normalization without changing execution identities, account selectors, history or grants.

Managed dispatch uses the existing ORCH+ host panel as an explicitly trusted same-user relay into an immutable host-local file carrier. It creates no SPAWN transport pane, tab, parked card, daemon, SSH connection or network service. `spawn.dispatch` remains registered only so retained panes can display an inert recovery notice and preserve their original saved state; they accept no execution events and are never rebound to a new relay. Source and fixtures are not runtime certification: each configured host/OS/account/CLI still needs the checks below before its managed capability is enabled. USAGE owns evidence collection and ORCH+ owns policy.

`dispatch_relay.luau` installs once at host load. It observes the actual ORCH+ source pane/program on the execution host, binds an immutable source/endpoint/lane/producer-incarnation descriptor, and explicitly delegates desktop session/window proof to the trusted ORCH+ relay. An attached remote desktop does not require a local SPAWN desktop CLI or an invented SPAWN surface. SPAWN's window still observes exact native origin, grants and claims before effects. The numeric internal correlation names the actual ORCH host pane; retained old correlations are never reassigned.

Carrier files preserve exact request and callback bytes; durability alone grants no freshness. The current SPAWN carrier boot, exact relay digest, current private engine nonce/boot/deadline, admission, both claims and WindowJournal remain independent fences. Expired or previous-incarnation effects are held for reconciliation, never restarted by delivery retries. Setup catalog observation is read-only and cannot initialize an authority scope.

Polling and settlement are bounded, projections are sent only when bytes change, and storage/backpressure failures retain obligations. An incoming delivery is acknowledged only after reducer handling and its immutable response/rejection are durable. Native-effect frames require a SPAWN-issued `consumed_execution` receipt after authoritative callback handling; a window echo alone is not settlement. Reserved carrier settlement slots let this proof drain an otherwise full execution outbox. Transport acknowledgement is not managed ACCEPTED or completed native execution.

A schema-2 `control_authorize` challenge can instead receive an exact `revoked_execution` receipt when SPAWN positively establishes expiration or supersession and removes its matching private challenge. Source disappearance alone is not revocation. The proof binds the carrier ID/incarnation, current source, relay and lane; it cannot retire a native effect, report success, replay the old control or grant replacement authority. The producer retains it through write failure/backpressure, and ORCH+ retains retirement through acknowledgement failure. A proof arriving before its matching frame stays pending. Ordinary consumption emits no duplicate revocation.

## Ordinary launch and managed execution

Use the SPAWN status-bar entry (its menu) or the command palette. Current agents, Start an agent, Agent settings and required resources/capabilities share the canonical host roster. Linking/reloading launches nothing. Ordinary JSON and transport details remain Advanced.

Guided setup uses Tern's actual configured default agent; OMP in ACP mode is recommended before the click, but other defaults remain supported. A bounded read-only Glitch-installation detector runs before structured questions and distinguishes incomplete/ambiguous discovery from an accessible bounded miss; it never enables integration. The helper discovers available providers and installed help before proposing permissions, with Normal default and explicit provider-specific unrestricted/all/subset overrides. It submits one run-bound immutable result for native review, not arbitrary unreviewed edits. Only Import reviewed records changes the roster; commit includes exact storage readback. The original helper then receives the run-bound save receipt and may report **SPAWN SETUP SUCCESSFUL**. Delivery alone gives the concrete Review setup result → Import reviewed records action, never a success claim. Required managed observations and optional paid readiness are separate.

Cancelling a review preserves its pending result. **Discard this setup result** is a separate explicit floating decision, available in the ordinary Setup pane and result review even when the original helper has closed. Its admitted `discard_setup_result` request binds current authority/config revision, `attempt_id`, `setup_run_id`, `pending_digest` and `confirmed=true`; current native Config membership must still be proven. Only that exact unconsumed pending submission becomes `{consumed=true, discarded=true}` with its original digest/length retained and pending bytes released. The reply is `{discarded=true}`. No roster import, helper stop, unrelated result/history deletion or fake readiness occurs; a fresh Guided setup run may then be approved. Old imported results remain distinct from discarded results.

Untrusted Guided/manual proposals cannot assert new managed verification or evidence; unchanged previously saved verified records retain their real prior setup. Owner-validated paired migration is a separate exact-gate path and preserves its existing verified identities rather than resetting them or requiring a new attestation.

Ordinary saved-agent launches use host-executor tickets. The window allocates only `exit 125 # SPAWN:<token>`; the host consumes that ticket once, verifies native membership and the approved revision, persists submission intent, then writes the approved invocation once. Unknown effects never retry. Guided setup uses a separately journalled native default-agent start and moves that helper left of the original SPAWN pane without replaying start if arrangement fails.

`provider_family` is optional normalized lowercase bounded text (96 bytes, nonblank and no controls), owned by SPAWN configuration/catalog. Only explicit declarations are saved; known direct-service defaults are derived when projecting the catalog, not invented as saved choices. Wrappers—including configured Claude/Codex alternative-provider routes—declare their actual underlying provider explicitly. Metadata is not runtime identity. The admitted `declare_provider_families` action accepts current `record_revision` and 1–32 unique `{record_id, provider_family}` declarations. It atomically fills absent declarations or accepts identical canonical values, refuses real explicit conflicts/missing records, and returns `{config_revision, applied, families}`. `families` includes every requested record exactly once with its actual canonical saved family, even idempotent requests. ORCH+ uses that exact bound response to normalize legacy targets, then confirms the fresh catalog; it owns no alias map and never writes SPAWN stores. USAGE excludes this metadata from account fingerprints.

Routine controller reconciliation may refresh only epoch/alias for the same owner, generation, native host/window/session and controller pane after every issued effect journal is quiescent. `attach_worker` accepts `same_native_conversation_no_pending_effects` for an actual recognized native agent, or `same_terminal_process_no_pending_effects` for a qualified retained terminal. Both require the exact accepted worker and same pane/host/session/window, with no outstanding effect/publication, including retired uncertain effects. Reconnect changes routes only: no launch, prompt replay or mailbox reprovision.

Tern may present a terminal-based agent as pane kind `agent`; that label is not native-agent identity. The accepted terminal backend and retained process proof remain required for automatic continuation. Its asynchronous proof must finish on the original request lane before status observation can replace that request. An admitted current controller binding atomically revokes an older binding's never-consumed authorization, retaining its fence and earlier outcome; consumed permits and uncertain effects are not converted into no-effect results.

For new managed terminal launches, SPAWN observes the one exact issued command in the existing native spawn hook without altering it. After bound ACCEPTED, it records the actual host-native pane/daemon route and the exact configured executable/task argv in foreground process ancestry, not a transient report helper. Linux retains boot/PID/start ticks, root/provider argv digests and tty/session/foreground-group association. Windows observes exact configured direct-child executable/CRT command line, root/provider StartTime ticks and native foreground ancestry through read-only native process/CIM observations. macOS uses the optional capability below. Reconnect re-observes the original native pane root, both process identities and current foreground/parent association. The read-only observation stays pending before ordinary native authorization; stale/changed proof never becomes permission.

macOS terminal continuation has a named optional **Python 3 + standard-library ctypes + native libproc** capability on the execution host. SPAWN discovers it by running its packaged read-only `macos_process.py capability` check; **Required resources and capabilities → Check terminal continuation capability** shows the actual outcome and safe setup action when absent. Use an approved macOS Python 3 installer, then check again; SPAWN never installs an interpreter, changes permissions or makes Python a global launch/native-OMP dependency. The helper uses Apple's [`proc_bsdinfo` / `PROC_PIDTBSDINFO`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h), [`MAXCOMLEN=16`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/param.h) and bounded [`KERN_PROCARGS2`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/sysctl.h). It checks the 136-byte ABI and offsets, complete kernel return size and requested PID, same user, exact microsecond creation timeval, argv digests, tty/process session/group and native foreground ancestry. Environment bytes are neither parsed, emitted nor hashed.

Legacy terminals without launch-time proof, ambiguous/custom process arrangements, missing/reused PID/start identity, changed native pane/tty/foreground or unavailable capability remain held with an actionable explanation, never a normal attest checkbox. Installing a missing capability does not retroactively certify an old process. Linux, Windows and macOS source support is not runtime platform qualification: the owning verification stage must exercise each actual OS later. Existing explicit retired-executor recovery remains for genuinely unresolved cases.

The read-only admitted observation `mailbox_inventory` accepts `stale_ms` (1–315360000000). SPAWN—not ORCH+—resolves the current logical session's retained nonretired mailbox targets, invokes packaged helpers asynchronously as the same execution user, and returns `pending` followed by `inventory` with `{observed_at_ms, open_files, stale_files, mailboxes}`. The complete supported 32-worker target set is counted without truncation. Reads share the existing four executor slots, wait for busy slots and retain the existing 30-second overall budget, with each child bounded by its remaining budget and at most 15 seconds. Counts describe bounded regular files and actual mtimes; stale is age, not permission to delete. Empty retained scope is a genuine zero; an inaccessible, cross-user, SSH, linked/reparse, malformed or deadline-exceeding target is unavailable, never a fabricated zero or partial successful total. One request polls to settlement; a new request obtains a new observation. No cleanup, lock, launch, credential operation, account inference or journal mutation occurs, and no root/helper paths are exported.

The inventory's 32-record protocol bound is not an allocation promise. Managed mailbox allocation retains the existing **16 live generations / 64 MiB / 16,384 files** host budget and default logical concurrency four. Intent, prepared and uncertain generations occupy allocation until positive retirement; an owner sees real capacity exhaustion rather than fabricated availability. A rejection after persisted preparation does not itself prove its allocation disappeared.

`mailbox_allocation` is the one read-only admitted allocation observer for both current and consumed provisioning actions. It uses the ordinary OBSERVE envelope without a serial/consumed cursor and adds `target={logical_session_id,worker_id,worker_generation,launch_request_id,work_id,enrolment_sha256}`; the target session must match the outer session. Only a unique full generation/nonce-hash match with a settled original provision journal and retained authority/admission/native-owner facts returns `status="allocation"` with `{target=<exact echo>,allocation={state="retained",provision=<existing full provisioned-payload shape>}}`. That metadata proves an allocation, not provision success, agent launch or readiness, and exports no token/root/helper path. Existing guarded retirement remains a separate owner action.

`allocation={state="none"}` requires exact retained positive preallocation rejection/no-issued-operation proof, or exact completed retirement proof. Missing records, consumed-away proof, duplicates, foreign scope, missing binding and uncertain effects stay `unknown_effect/uncertain`; none is never inferred from absence. Actual active helpers use structured `allocation_pending` and receive read-only relay refresh within existing observer timing; static unavailable proof does not spin forever. The durable provision write retains its own original request identifiers after the old action is consumed, so this target lookup never guesses old status IDs, recreates the old framed outcome, calls prepare or reissues a helper. Legacy evidence lacking current authority/admission/native scope remains held. Ordinary `status` remains unchanged with only its original immutable `outcome`.

Managed launch through the host-local receiver is the deliberate exception: the host constructs an immutable **fresh** command projection, and the exact granted window invokes native `agents:start` or terminal layout APIs. Native wake separately claims `agents:ask`; native stop/terminal close require their own exact grants and observations. The ordinary spawn hook does not intercept ticketless managed panes. Native agent recognition, idle checks and window alias fences remain prerequisites; a terminal wrapper is not a substitute for native OMP.

`launch_resolution.luau` shares canonical record validation, ordinary/fresh argv selection, configured OS-user checking and SSH identity resolution. Rendering is executor-specific: ordinary rendering uses the captured host pane program and retained-shell semantics; managed rendering uses the host authority's `SHELL`/`ComSpec` observation and explicit target declarations. Managed shell evidence is not proof of an actual pane shell. Ordinary OMP startup prompts and managed terminal task-argument insertion intentionally differ. Existing `sudo` must select exactly the configured user; missing, conflicting or ambiguous selectors and malformed/conflicting SSH destinations are rejected for review, never silently rerouted.

## Authority compatibility and retention

Durable authority is **version 4**, with `namespace`, `host_key`, `config_revision`, `config.hosts[host_key].agents` and the setup lifecycle. Ordinary request/snapshot envelopes remain version 2 (`SPAWN_STATE_V2`). Every ordinary attempt has exactly one ticketed job; every managed attempt has `purpose:"managed"` and **no** ordinary execution job. Managed observer, attempt, original launch and mailbox identities remain immutable.

Reply capacity still rotates `authority_id` and rejects old ordinary requests. A separately retained `managed_authority_id` is the initial scope identity; native effect callbacks bind the exact namespace/session, host and native session, not a reply-transport epoch. Rotation neither replays effects nor adopts a new controller/window. Explicit reset retains both guards: resolve active/unresolved attempts and reconcile managed owners, consumed authorizations, live mailbox generations and unresolved import gates.

An old detached version-1 authority migrates only when every attempt has exactly one immutable `dispatch-v1` launch reference matching scope, authority, native session, host, record, exact request-derived observer and attempt (or the exact interrupted reservation intent), with matching recorded pane evidence. The original is preserved as `managed-v1-original` before conversion. No record name or observer prefix is enough to classify an old ordinary attempt as managed. A never-created bridge registry is valid for an empty clean authority, but never evidence for a saved attempt; unreadable/corrupt storage and a missing previously initialized registry still refuse unchanged. Nonempty old request/reply transport and unmatched attempts require original-version review.

Old ordinary setup import receipts are shape-validated and preserved in the original backup, then discarded from the live ledger without replaying their settings. Managed `bridge-` receipts instead require an exact consumed gate, matching canonically normalized records and the stable session-key/host-key/native-session tuple; an intervening reply-transport rotation does not invalidate that receipt. Detached v1 receipt normalization strips retired fields consistently with gate normalization but never changes the gate's immutable source bytes/hash, invents a family declaration or resets verified managed identity. Unmatched managed receipts refuse unchanged.

**Rollback is a state restore, not a package downgrade.** Older writers cannot read the current version-4 authority and managed state. Before upgrading, preserve the matching package version and a consistent copy of all SPAWN plugin state (including `authority`, `dispatch-v1`, its initialization marker, gates/fences and mailbox journals). `managed-v1-original` preserves only the pre-conversion authority, not a complete rollback snapshot. Stop/quiesce all affected executors and reconcile every post-backup effect before restoring the matching complete state and old package; restoring an old ledger while newer effects remain can replay work. Never delete managed fields or reset a registry to make an older package load.

ORCH+ request ids and logical session ids are per-store counters, while SPAWN keeps request fences keyed on `logical_session_id`/`request_id` in `dispatch-v1`. If ORCH+ is re-initialized as a first-use store while SPAWN keeps that state, new requests reuse fenced ids and SPAWN refuses them with `content_conflict` ("Compacted request ID reused"). Restore ORCH+ from its backup, or reset SPAWN plugin state together with ORCH+'s; never re-initialize ORCH+ alone over retained SPAWN state.

**Before downgrading SPAWN below 0.3.1,** settle every pending window request and acknowledge (or **Mark result reviewed**) every retained reply. An older host validates every retained request against its own closed operation list, so a retained request with an operation it doesn't know makes the whole authority unreadable to it. **Downgrading SPAWN below 0.5.0 is not supported.** Once 0.5.0 has settled an attempt automatically or started a restart grace, its authority carries job fields and settled phases an older host does not know, and the older host cannot read it.

The `resolve_attempt` and `resolve_lost_attempts` operations were removed in 0.5.0, because ordinary attempts now settle automatically (pane closed, ticket not claimed, host restarted). A retained host request or journalled window request with either operation is acknowledged with an `ok` reply `{obsolete: true, notice}` and never replayed; the authority stays readable. Managed attempts keep their existing release rules.

Managed imports atomically retain bounded exact request/payload receipts with configuration. Replaying a committed import returns its receipt before revision checks and never overwrites subsequent owner edits; changed payload reuse conflicts. Ordinary imports retain released identical-record idempotence.

Automatic trimming keeps the newest 26 reclaimable finished attempts across ordinary and settled managed work. A managed attempt is reclaimable only when it is `Exited`, not unresolved, and no interrupted `retirement_result`, unsettled linked request/wake or unretired mailbox generation still needs its ledger. Unknown, failed or active managed evidence remains protected; operator resolution alone is not successful retirement. Explicit history clearing uses the same eligibility. Unreadable bridge evidence prevents managed reclamation, and missing/corrupt storage blocks explicit history clearing and session forgetting.

Wholly settled absent session scopes may be forgotten once active owners and unsettled references are gone. Retained successful receipts or tombstones alone do not pin the scope; bridge request/identity fences are never erased by authority cleanup. Exact interrupted retirement reconciliation remains available while its pending settlement evidence exists. After successful settlement and eventual reclamation, callers read the retained bridge result rather than re-settling a removed authority attempt. History cleanup never removes native sessions or panes.

Catalog payloads add `namespace`, `host_key` and `config_revision` while retaining `revision == config_revision` and each record's `id`/`revision`. The exact USAGE join is `(namespace, host_key, config_revision, record.id)` from one complete catalog revision. USAGE's definition SHA256 is independent definition evidence, not the numeric configuration revision. Configured model/profile/capacity labels do not establish a verified account or model binding.


## Managed configuration

### Native setup ownership and evidence

**SPAWN → Setup → Prepare agents for ORCH+** opens SPAWN's preparation owner page, available without a pre-existing OMP record. ORCH+ links into that page using native pane launch/focus/events; the optional readiness return uses the same native navigation boundary, not installed-plugin action dispatch inside callbacks. Reuse requires the live matching source/session/host; missing or closed sources refuse. Navigation is not roster import or controller authority.

New-record creation and existing-record adoption are distinct explicit operations. Adoption retains the stable record ID, ordinary command/resume arguments, disabled/review state, unrelated records and old resources. One approved **Prepare and save** workflow binds reviewed inputs, configuration revisions, per-record nonces and the clicking native recipient through preparation, diagnostic, positive cleanup and normal durable save/readback. A standalone Advanced resource probe grants no save authority.

The owner page publishes reviewed helper bytes into stable `helper-bundles/<digest>` directories outside the installed package. Same-user setup uses plugin data; an implicit cross-user root uses `.local/share/tern-spawn/managed` under the actual verified selected home, while an explicit root is preserved. Existing files are read back and compared, never replaced on mismatch; linked package paths and old helper bundles are not overwritten. This supports stable saved helper references, not a promise of future managed-history retention or updater migration semantics.

Prerequisites resolve the actual selected identity/home and executable before checking its accessible working folder, root, helper tools and durable read/write/hash/journal/wake access. Same-user is not a sandbox. POSIX cross-user setup uses existing noninteractive `sudo -n -u <user> -H --` access; no permission, account, credential, authentication or policy changes are performed. Current native routes are discovered from Tern's configured command and observed native agent commands, not a provider-label allowlist. Explicit restore/resume/continue/session-reuse selectors cannot qualify a fresh route. This does not certify arbitrary ACP/CLI compatibility or provider readiness. This local wizard does not provision managed SSH. Native OMP requires POSIX; Windows local terminals require an explicit native `.exe` and `windows-crt`, and do not support native OMP or cross-user setup. PowerShell policy must already permit the helper: refusal is reported honestly, with no shipped `RemoteSigned` override or default-policy support claim.

Resource probes, native route proof and configured-CLI semantics remain distinct evidence, even when one user action runs the required workflow. Before any diagnostic cost, host-wide checks reject disabled/review-gated records and records retained by ordinary, managed, uncertain or unretired work. Reciprocal launch/save guards prevent a new launch from racing preparation. Legacy obligations without a provable record ID remain cleanup-only and conservatively block new effects; they are not discarded to free capacity.

- **Native OMP route:** explicit consent discloses a small real model turn. The selected model/profile/auth flags remain intact; only owned diagnostic session storage changes. Proof requires the exact startup user body, actual native child argv/cwd and exact owned pane identity, followed by owned cleanup. A `READY` response alone is not proof.
- **Local-terminal route:** the owned offline helper exercises native pane creation and exact literal argv/account readback. Its approved observation lifetime is at most 45 seconds, normally ending early after positive native identity. This does not execute or certify the configured provider CLI. Incomplete observations can continue only within that bound; missing/ambiguous identity remains unresolved. Output alone never authorizes retry, clearing ownership or closing an unrelated pane.
- **Configured CLI semantics:** the offline terminal diagnostic cannot certify fresh-task flags, authentication or provider behavior. Preparation reads the actual selected executable's `--help`; a declared `--prompt-interactive` may supply an otherwise inferred final task slot. Existing explicit input modes, `--` separators and custom positions remain unchanged. The approved workflow saves only after successful route observations and owned cleanup. No resource probe alone fabricates `mailbox.verified`.

After the Guided setup helper's single approval, SPAWN automatically commits and reads back the immutable submitted import, then prepares only its exact enabled roster under the captured run/digest/configuration/consent binding; no review popup or second click intervenes. A roster with nothing enabled, an SSH route or a review-required record is saved without preparation. Saved agents installed after ORCH+ are prepared by one **Prepare agents for ORCH+** action covering only the agents lacking verified preparation. Native checks disclose real model costs; terminal checks are offline. Required setup and optional provider readiness remain independent. Neither delivery nor roster saving proves full setup, login, real-task success or platform qualification.

The offered manifest is published before its native approval link opens. The consumer captures the original clicked scope synchronously and may wait for that exact offer only within the original **30-second approval deadline**. Source, recipient, configuration revision and nonce changes refuse the handoff; duplicate or expired links do not renew or replay it. Resource preparation has its separate **180-second bound**. Before each serial entry, native identity is refreshed against the same captured recipient; each actual diagnostic retains its independent **45-second lifetime**, starting when that diagnostic begins rather than consuming the earlier preparation time.


To update an existing record, open **Config → Configured agents → Full record JSON** on that record. Activation loads only the focused record's current JSON; paste/edit one complete record object, not the schema/agents import wrapper, and keep its stable `id`. Saving changed JSON validates the normal schema, replaces only that record through the existing revision-fenced authority, and sets **Needs settings review**. Inspect the complete settings, then use **Approve reviewed command and settings** before launching. This is the operator route for mailbox verification/evidence, fresh argv and model/profile metadata; setting `review_required:false` in JSON cannot bypass approval. Stale edits refuse rather than overwrite another record's changes. Ordinary Paste JSON import remains add-only and still refuses a conflicting existing ID.

Existing records retain their normal `command`, `arguments`, `cwd`, `prompt`, backend, placement, enabled state and settings-review requirement. Managed launch additionally requires one of:

- Native OMP: `fresh_native_default: true`, explicitly selecting a new default OMP context without inheriting resume arguments. Model/profile metadata cannot silently override this default.
- Structured CLI: `fresh_executable` and `fresh_arguments`, plus `task_argument_index` for terminal backends. This is the one-based insertion slot for **one literal task argument**, including any quotes/newlines/Unicode. The configured CLI must document this as fresh input. No command stripping, predecessor command reuse or task text appended as shell code occurs.

Managed Windows targets additionally require `argv_contract: "windows-crt"` and an explicit native `.exe`. Batch/script targets, extensionless PATHEXT resolution, and direct `cmd.exe`/PowerShell command-code input are not managed argv-v1 routes. Ordinary existing Windows batch/script behavior remains separate.

`cwd` and `placement` are explicit managed allowances: requests must match the selected record. Native placements are `tab`, `split`, `replace_if_alone`; managed terminals support `tab` and `split`, not a silently substituted replacement. `target_os` and `target_shell` are mandatory for managed SSH. `host_shell`, when configured, must agree with the host authority's shell observation; this is distinct from the actual pane-program observation used for ordinary tickets. The client machine's OS never chooses the target serializer.

Optional `model`, `profile`, `variant_id`, `selector_evidence`, `capacity_binding`, and positive `capacity_limit` remain configured metadata for subsequent policy work. They are not verified effective identity or available quota.

A mailbox record contains:

```json
{
  "permitted_root": "/absolute/reviewed/mailbox-root",
  "helper_path": "/absolute/reviewed/mailbox_target.sh",
  "producer_helper_path": "/absolute/reviewed/mailbox_worker.sh",

  "producer": {"read": true, "write": true, "hash": true, "journal": true, "poll": true},
```

This illustrates the **mailbox object**, not a ready-to-use account. `verified` is an explicit operator-attestation gate, never a probe result fabricated by the normalizer. Only set it after establishing the configured producer/target/CLI evidence. Native-recognized OMP may instead use `native-ask-v1`; it must really be recognized by the attached window's native agent API. A terminal with argv input alone is not eligible for managed duplex work.

The complete capability set is validated once by the shared backend/mailbox contract, persisted and digest-bound at provisioning, and returned unchanged. Terminals require `report-files-v1`, `worker-poll-v1`, and `argv-v1`; native agents omit `argv-v1` and declare exactly their configured wake route. Missing producer/capability metadata or mismatched backend/wake declarations make the catalog row ineligible rather than throwing.

Existing host Config imports accept the extended record schema. Private wrappers, credentials and rosters are deliberately not part of this package. Unix user routing is explicit; unsupported Windows user selection rejects rather than emitting `sudo` or using the current user. Ordinary matching prewrapped sudo selectors are checked, not doubled. SSH retains normal host-key verification and configured user/key references; no automatic trust or authentication changes occur.

## Existing-tool target and producer prerequisites

No daemon, new language runtime, or automatic installation is provided. Review and deliberately place the applicable short-lived helper assets on the **execution target**, with owner-controlled regular files and non-symlink/non-reparse ancestors. Config points to their exact absolute paths:

| Target | Host transport helper | Producer/consumer helper | Existing tools required |
| --- | --- | --- | --- |
| POSIX local or SSH | `mailbox_target.sh` | `mailbox_worker.sh`, with sibling `mailbox_json.awk` and `mailbox_reply.jq` | POSIX shell/core tools; `base64`; `sha256sum` or `shasum`; producer additionally `jq`, `awk`, `iconv` |
| Windows local or SSH | `mailbox_target.ps1` | `mailbox_worker.ps1` | Existing Windows PowerShell/.NET |

Both the actual transport identity and worker identity must have the required access. Provisioning probes the resolved target, validates the expected worker account, creates a unique handle directory and proves immutable write/readback before returning a provisioned handle. A helper missing on the target is a prerequisite failure, not permission to install a runtime or run a client-side substitute.

SPAWN's private adapter passes nine literal data arguments to the target helper: `root, handle, mode, selector-or-"-", operation_id, worker_identity, report_floor, reply_floor, producer_helper`. Writes additionally send one Base64 object line on stdin. The adapter supplies these values; ORCH+ never resolves paths or builds this command. POSIX producer validator assets must remain adjacent to its helper.

Private selectors map the `report` stream to `reports/` and `reply` to `replies/`. Slot and watermark sequence filenames use exact decimal integers through 9,007,199,254,740,991; exponent notation or rounded counters are not valid selectors.

The producer owns a cooperative single-writer journal. It atomically saves the entire logical report and next sequence together before publication, writes chunks before the manifest, and retains exact bytes until the exact ACK and cumulative receipt chain are durably consumed. Locks left by an interrupted producer require operator recovery after establishing that the prior producer is stopped; no PID inspection or timeout stealing is used.

The private launch preface contains the target root, handle, producer helper and enrolment binding. The exact original ORCH+ assignment follows it unchanged; `assignment_sha256` hashes only that assignment's bytes, not the transport preface. Producer `report` input is a closed JSON object `{kind,payload,action_id?,action_revision?,handover_id?,handover_token?}` on stdin. The helper supplies immutable BE, sequence and deterministic event ID itself. Initial ACCEPTED has no handover pair; rollover supplies both, and the preface tells the successor to copy them verbatim from its JSON.

With `native-ask-v1`, the worker returns idle immediately after publishing ACCEPTED so the native notification can arrive. It then drains the durable receipt and resumes its original assignment without waiting for another assignment reply. The preface explicitly identifies ordinary-worker versus coordinator transport role: a capability alone does not make an ordinary worker wait for coordinator activation. Review requests and exact landing/deployment grants remain mandatory for those operations; an ACK-only wake never authorizes unrelated work.

A rollover successor's `mailbox_provision` carries the issued `handover_id` and `handover_sha256` = SHA-256 of the UTF-8 bytes `handover_id:handover_token`. The raw token is never provisioned. Both fields are required together. They are part of the binding digest and are written to `provision.json` as `handover:{handover_id,handover_sha256}`. Ordinary generations carry neither, so their `provision.json` and digest are unchanged. SPAWN refuses a launch whose enrolment pair does not hash to the provisioned digest. Before allocating a sequence, both producer helpers check every ACCEPTED against `provision.json`. A missing pair, a pair on an ordinary generation, a different `handover_id` or a token whose pair digest differs is refused with exit 1 and a stderr line that names the field and never echoes either value, for example `binding_mismatch: handover_token differs from the provisioned handover digest; copy it verbatim from the launch preface and report ACCEPTED again`. Nothing is published or journaled, so the worker retries with the exact values at the same sequence. Only ACCEPTED reads the provisioned handover. A malformed one refuses ACCEPTED with a plain `binding_mismatch`, while every other report and mode, including `retire-authorized`, behaves identically in both helpers.

Each `mailbox_read` returns only its requested, validated object. ORCH+ owns incremental report assembly: it validates each arriving chunk once, stores JSON-safe Base64 slices across reload, then validates the complete digest, schema and issued-launch binding (assignment digest, handover pair and capabilities) before intake. The durable receipt cursor precedes ACK publication. Rejected complete bytes remain available for rejection handling; an already published report keeps its sequence and is never replaced. SPAWN still validates the full assembled reply before publishing its manifest.

Coordinator use additionally requires explicitly reviewed/configured `coordinator-control-v1` in the provisioned capability set. It is not implied by `report-files-v1`, and existing ordinary records remain usable without it. The eight recognized capability names are `report-files-v1`, `native-ask-v1`, `worker-poll-v1`, `argv-v1`, `coordinator-control-v1`, `check-runner-v1`, `release-manager-v1` and `project-start-v1` (at most eight per record, each once); backend/wake-route compatibility still applies. An actual coordinator launch carries paired enrolment `coordinator_owner_id`/`coordinator_generation`. Only that explicit role adds the transport instruction to emit ACCEPTED, then wait for and claim typed activation before coordinator work. A capable record used for ordinary work does not wait. Original assignment bytes and digest remain unchanged; no activation token is sent through the preface.

The closed version-1 replies add `coordinator_activation` payload `{owner_id,owner_generation,activation_token,instructions}` and `coordinator_retirement` payload `{owner_id,owner_generation,activation_token,reason}`. The closed version-3 report adds `COORDINATOR_RELEASE` payload `{owner_id,owner_generation,activation_token,quiescent:true}` and requires `action_id`/`action_revision` referencing the issued activation or retirement. Tokens are exactly 64 lowercase hexadecimal bytes, instructions at most 32,768 UTF-8 bytes, reasons at most 1,024. Helper schema support is not authorization: configured/provisioned launch capabilities and ORCH+'s exact issued grant/receipt govern intake. A release report means cooperative quiescence, never native closure.

Managed project START additionally requires **both** `project-start-v1` and `coordinator-control-v1`. The `project_start` reply and action-correlated `PROJECT_START_CLAIM` report contain the same closed payload `{owner_id,owner_generation,activation_token,orch_project_id,project_revision,decision_context}`. The project revision is positive; activation and decision-context values are exact 64-character lowercase hexadecimal values. The report's `action_id`/`action_revision` must name that issued reply. Consume, locally claim, publish the claim once, wait for its actual accepted receipt, then resolve; the coordinator does not launch project workers itself. Updated managed setup advertises this support only after the new content-addressed helpers are installed and read back. Previously saved helper descriptors are not upgraded merely by changing the recognized capability list.

A receipt accepts a consumed report fact, not independent project execution authority. Exact authenticated START claims that are definitively revoked may settle as refused facts so the producer can resolve its local claim; no work is released. Malformed/foreign claims and a claim whose original publication is not yet proven remain held. The host's current validated claim transition remains the execution gate.

**Assignment manifest.** `mailbox_provision` may carry `manifest`: the exact canonical bytes of a closed JSON object `{checks[≤16 {check_id, argv[1..16 strings ≤512 bytes]}] (unique ids), files[≤64], scope{paths[≤64], systems[≤16]}, base_ref?}`, at most 4,096 bytes (`manifest_too_large`, `invalid_schema` otherwise). SPAWN hashes the bytes, appends `manifest` and that digest to the binding digest after any handover pair, records `manifest_sha256` in `provision.json`, and the target helper writes the bytes verbatim as the mailbox's `manifest.json` (a second Base64 stdin line after `provision.json`). Without a manifest the digest and `provision.json` keep their 0.3.0 form. Current provisioning persists the complete negotiated capability set. Legacy descriptors retain their older representation only where supported; missing capability metadata never implies support for project START or another new control.

**Helper-only modes** (need `check-runner-v1` in the provisioned set). Both verify `manifest.json` against the provisioned `manifest_sha256` first and publish their report through the normal journal, sequence and manifest-last path:

- `run-checks <check_id>` runs that declared check's argv from the manifest, never argv from the worker, executed directly without a shell, stdin empty, in the worker's current directory. It publishes CHECK_RESULT `{check_id, argv_sha256 (SHA-256 of the argv JSON), exit_code, output_sha256 (first 65,536 bytes of combined output; the rest is drained), head (git HEAD after the run), ran_at_ms}`.
- `checkout` publishes CHECKOUT `{worktree_path, common_dir, branch, head, base?, changed_files, changed_overflow, changed_total, dirty}` from git: committed paths since the merge base with the manifest's `base_ref` (when it resolves), plus `git status` paths including untracked files and both sides of renames; at most 512 sorted paths, trimmed until the report fits 64,000 bytes, with `changed_overflow` when any were dropped. When the manifest has no `base_ref` (absent or empty), the first `checkout` pins the current HEAD in `<mailbox>/checkout-base` (beside `provision.json`, written atomically, first writer wins). Every later checkout reports `base` = merge-base(checkout-base, HEAD) and includes committed changes from `base...HEAD` in `changed_files`. A `checkout-base` that is not a regular file holding one 40- or 64-hex revision is refused with `storage_error`. A hyphen-led `base_ref` is still treated as unusable and never pins.

Refusals, in order: `capability_missing`, `manifest_missing`, `manifest_mismatch`, `check_undeclared` (unknown or malformed ID), `git_unavailable` (no git, not a worktree or no HEAD; a suffix names the cause); `checkout` additionally refuses a tampered `checkout-base` with `storage_error`. Publishing CHECK_RESULT or CHECKOUT through `report` is refused `helper_only_kind`. `release-manager-v1` gates `landing_grant` and `deploy_grant` on `consume` and DEPLOY_RESULT on `report` (`capability_missing` otherwise).

**Report and reply kinds.** Version-3 reports add `CHECK_RESULT`, `CHECKOUT` (both helper-only, `check-runner-v1`), `LABEL` `{work_ref, class, reason?}` and `DEPLOY_RESULT` `{deploy_id, attempt_id, landing_id, outcome: deployed|held|not_applicable|failed, revision, evidence[≤16], reason?}` (`release-manager-v1`). REVIEW_RESULT is `{review_id, round, artifact_revision, outcome: approved|changes_required, findings[≤32 {finding_id, path, line?, summary ≤400}], summary?}` and DONE may carry a relative `output_ref` (≤256). Version-1 replies add `review_request`, `rework`, `deploy_grant` and `label_request`; `landing_grant` (now addressed to the release manager) and `deploy_grant` need `release-manager-v1`. The codec and both helpers validate the same closed shapes.

**Landing proof and review modes.** The shared [report-files-v1 codec](../../../shared/report-files-v1/codec.luau) and both mailbox helpers accept a `landing_grant.proof` containing `mode`, `artifact_revision` and mandatory `check_refs` (up to 16). ORCH+ requires every declared check to have passing helper evidence at the submitted artifact revision in **all** modes; an empty list is valid only when no checks are declared, not as a bypass for missing, failed or stale checks.

| Policy (`require_code_review` / `require_other_family`) | Proof mode | Review fields |
| --- | --- | --- |
| `true` / `true` | `cross_family_review` | Mandatory review, different provider family |
| `true` / `false` | `helper_checks` | Mandatory review; same family allowed |
| `false` / `false` | `review_disabled` | No reviewer or review result |

In `review_disabled`, the grant omits `review_id`, `reviewer_family` and `proof.review_id` entirely: no fabricated review IDs or synthetic approvals. In either review-enabled mode, the grant requires `review_id` and `reviewer_family`, and `proof.review_id` must equal the grant's review ID. `artifact_revision` and check references remain mandatory in every mode. ORCH+'s default actor is the exact existing accepted builder with actual `release-manager-v1` capability; selected-record mode uses a separate release worker. The reviewer cannot be the merge/deploy actor in either mode. ORCH+ owns policy selection and admission, while SPAWN enforces the closed wire shape and provisioned capability boundary.


Concrete POSIX work-tool invocation, using the private values from the launched assignment:

```sh
sh "$producer_helper" "$root" "$handle" "$enrolment_token" init
printf '%s' "$report_json" | sh "$producer_helper" "$root" "$handle" "$enrolment_token" report
sh "$producer_helper" "$root" "$handle" "$enrolment_token" receipts
sh "$producer_helper" "$root" "$handle" "$enrolment_token" consume
sh "$producer_helper" "$root" "$handle" "$enrolment_token" wait '' 5 30
sh "$producer_helper" "$root" "$handle" "$enrolment_token" checkout
sh "$producer_helper" "$root" "$handle" "$enrolment_token" run-checks "$check_id"
```

Windows uses `powershell.exe -NoLogo -NoProfile -File <producer_helper> -Root: <root> -Handle: <handle> -Owner: <enrolment_token> -Mode: init|report|replay|receipts|consume|wait|claim|resolve|retire-local|run-checks|checkout`; `report` takes the same JSON on stdin, `-PollMs: 5000 -WaitSeconds: 30` bounds wait, `-MessageId:` addresses claim/resolve, and `-Mode: run-checks -CheckId: <check_id>` names the declared check. Each colon-ended parameter name and its literal value are separate argv elements: this prevents `-File` from interpreting the `-` selector or a hyphen-prefixed identifier as a parameter name, without coercing boolean-looking strings. The target adapter uses the same explicit binding for all nine helper fields; POSIX keeps its positional protocol. Use structured work-tool argv/target quoting, not interpolation of untrusted report text as code.

Windows report stdin is UTF-8 bytes, read directly from the standard-input stream with a 65,536-byte ceiling and one overflow-detection byte. It does not use PowerShell's automatic input enumerator or locale-dependent console text reader. Send UTF-8 explicitly; an OEM-code-page process writer is not a valid substitute. Empty, malformed UTF-8 and oversized input are rejected before journal mutation. The Windows regressions exercise the documented `-File` entrypoint, including all seven capability names, multibyte text boundaries and unchanged journals on rejection. The helper suites also exercise `run-checks` and `checkout` on disposable git repositories and their refusals.

`init` takes no input: non-empty stdin is refused with a nonzero exit before any journal is created, and success prints `journal initialized; next: publish ACCEPTED with mode report` on stderr (stdout stays empty). Publish every report, including ACCEPTED, with `report`.

`init` is only for a genuinely new journal. Restoration uses `replay`, never a reset of sequence. `consume` durably records a validated reply and emits its correlated `reply_ack` before returning the reply. `claim`/`resolve` record the recipient's execution uncertainty separately from receipt. At work checkpoints call `receipts` and `consume`; while awaiting a reply use bounded `wait` calls through the actual configured CLI's existing execution loop. A shell helper existing on disk does **not** prove a CLI polls it during work or while waiting. Demonstrate that route before marking a terminal record eligible.

Receipt and application delivery are separate. `consume`/`wait` re-deliver retained **unclaimed** exact reply bytes after a crash between durable receipt and stdout, even if the receipt cursor advanced or transport files were compacted. Claimed/uncertain effects are never presented as new execution permission. At most eight consumed facts and 524,288 raw reply bytes are retained; unresolved facts count toward this limit and cause visible backpressure.

For eligible recognized native agents, durable ACK/reply publication records a bounded notification obligation, not a native execution claim. ACK wake requires the exact launched `awaiting_acceptance` or `accepted` worker; reply-manifest wake requires `accepted`. A separate ORCH+-granted `native_wake` references that exact publication. Its fresh window checks the current execution origin/controller alias, exact grant, pane association and safe idle state before `cx.agents:ask` with the bound numeric pane ID. The ask drains receipts first, then consumes a complete reply if present; ACK-only notifications require no synthetic report. Working, waiting-input, exited, unknown and permission-held agents are not interrupted. Queued input is not receipt or execution success.

Publication exposes canonical `wake_target_request_id` / `wake_target_action_id`, `wake_status` and `wake_effect_started`. Only `awaiting_window` with `wake_effect_started=false` proves an unstarted obligation: ORCH+ can settle publication without occupying an execution slot. Separate wake reservations/claims share the normal four-host/one-generation limits with transport. A proven pre-effect idle race defers under a fresh exact grant; possible asks stay uncertain and never repeat. Polling routes need no native wake. Duplicate publication and compaction preserve the canonical notification and cannot reset a submitted/uncertain wake.

Open the native block and read its current response node before sending an action:

The prefix is `SPAWN_DISPATCH v1 ` and the closed outer frame is:

```text
{schema:1,op,request_id,complete:true,body_bytes,body_sha256,body_json}
```

`body_json` is the exact UTF-8 JSON string hashed and counted, not parsed/re-encoded data or another Base64 layer. The entire prefix plus escaped outer JSON must fit 8,192 bytes. The body is `{schema,op,request_id,action_id,origin_binding,controller_generation,status,payload?,error?}`. Reject clipped, oversized, mismatched or partial surfaces; never mine generic pane text for results. Only SPAWN consumes its separate private execution projection.

Runtime common fields: `schema:1`, `origin:"orchplus"`, `op`, host-issued `request_id`/`action_id`, decimal-string window-local `controller_pane`, positive `controller_generation`, and exact `origin_binding`:

```text
{logical_session_id,owner_id,owner_generation,host_pane_id,alias_nonce,
 window_key,window_epoch,native_session_id,window_host_id}
```

These correlate/fence the admitted controller; they do not authenticate OS principals or establish canonical cross-window identity. After asynchronous membership verification, public mutations persist `pending` with `authorization_required:true`. SPAWN privately issues a boot-, bridge-, request- and time-bound nonce. Its window checks the exact live ORCH+ owner, immutable request and `{executor,epoch,grant_id}`, plus the projected current execution origin/controller alias and durable control cursor. Read-only reconciliation projections cannot authorize execution. The host rechecks its independent owner fence and consumes the nonce before intent/effect; a public request alone never authorizes mutation. No suitable window leaves authorization pending. A newer same-origin intent sequence does not invalidate a retained effect claim, but continuation fences old-window callbacks. No `WindowCx` is retained.

Bridge membership scans the host daemon's `window` clients and `remote` clients (window halves attached through `tern remote serve`), at most 16, and requires exactly one session across them to hold the bridge pane, re-inspected once before use; CLI/script clients are ignored. Regression: `dispatch/remote_membership`.

Authorization deadlines preserve the native clock's fractional monotonic milliseconds; integer-only validation applies to revisions, generations and sequence counters, not clock values.

A requested nonce is projected only on its originating host bridge while still live. Other request/status panels may inspect public outcomes but cannot solicit that nonce's one-shot window response, and duplicate submissions cannot rotate an unexpired challenge onto another bridge. Authorization refusals distinguish request, nonce, VM, bridge, phase and deadline mismatches without exposing nonce or filesystem material publicly; none grants retry permission.

A `status` read of a staged request whose challenge is still `requested` but expired or issued by an earlier host VM reports definitive pre-effect evidence instead of `pending`: the retained pre-challenge outcome when one exists, otherwise `full` with `{resource="window_authorization",current=1,limit=1,retryable=true,effect_started=false}`. Such a challenge can never be consumed, so nothing started. The projection is read-only; re-staging the identical request still issues a fresh nonce. The window executor rearms its 250 ms observation timer before each tick, so a tick that trips the window budget cannot end later authorization observations.

The bridge view shows one compact human line (`SPAWN bridge - <op> <status> - <note>`). Its machine nodes stay in the native surface, keyed and bounded as before, and `dispatch.css` (manifest `styles`) only stops drawing them. A third keyed node, `main.spawn-dispatch-lease` (role `spawn.dispatch.lease`), carries `SPAWN_BRIDGE v1 {schema:1,held,live,busy,owner?}` (at most 2,048 bytes) for the ORCH+ window's bridge lifecycle; it is never authority. `held` means the registry still names this pane as the bridge of a `requested` window authorization that can still be consumed (issued by this host VM and not past its deadline), or the registry is unreadable. An expired or earlier-VM challenge can never be consumed, so it stops holding its bridge once the deadline passes, whether or not the window that requested it still exists; a granted launch, adoption, stop or wake keeps the bridge `live` through its execution projection until its native outcome is recorded. `live` means an execution projection is current, and `busy` means a membership verification is in flight. `owner` is `{controller_pane,alias_nonce,window_key,window_epoch}` of the current request. A request-less bridge reports instead the creator JSON `{schema:1,...same fields}` that ORCH+ passes as `new_block` argument 1, kept in saved state. ORCH+ reuses a bridge only when its lease is idle and its owner is the same controller and window, and it closes only an idle bridge of an earlier incarnation of its own window. Regression: `dispatch/bridge_view`.

Never move a bridge pane between tabs after it opens. In the live window a pane moved with `move_to_tab`/`move_to_new_tab` answers `cx.session:surface` with nil, so neither ORCH+ nor this package's window executor can read its response, lease or execution nodes any more. Open it where it stays: a `"tab"` placement, or `"beside"` with `target` set to a pane in the destination tab. Never park it either, since a parked pane has no tab and fails the session-membership check.

The window marks a nonce sent only after both exact-origin observations and final payload checks succeed, immediately before enqueueing the private authorization event. A rejected pre-send observation leaves the unsent challenge available for a later valid observation. Once enqueueing begins, exceptions or missing acknowledgements do not permit another send; the host still enforces nonce freshness and one-shot consumption.

The window VM's sent/effect markers and stop observations are grouped per ORCH+ request. A group is dropped only once that ORCH+ action reads back `complete` or `resolved` from its own controller pane (same alias nonce and session), when no marker can authorize anything; a claimed, uncertain, missing or unreadable action keeps every marker. One group is checked per tick, so the tables stay bounded by unsettled work instead of growing for the VM's lifetime.

Withdrawal admission can drain already-written valid receipts through the ordinary authenticated receipt path before checking the real final floors. Unrelated unsettled data still refuses retirement.

A journal that is not settled at the authorized floors (pending reports, a cursor or receipt chain off the floors, or a consumed message not acknowledged and `resolved`) is refused before anything is removed: the helper releases its gates and exits 0 with exactly `producer_unsettled\n`. As the first child it proves no effect, so the adapter returns a definite `rejected` (`producer_unsettled`), never uncertainty, and the target is not invoked; the mailbox stays provisioned and a later retirement needs a fresh grant. Any other output, a non-zero exit, a timeout or that line from the target child remains uncertain. Older installed helpers report the same refusal as uncertain; reinstall the reviewed helpers to get the definite outcome.

The narrowly guarded failed-startup exception uses that same retirement and reservation settlement, not a synthetic stop. ORCH+ permits only a cleanup request after fenced coordinator-owner recovery, with no accepted event/report/reply/activation, unresolved action or restoration. Unknown core lifecycle evidence is never converted into exit or removal. SPAWN requires the retained fresh native/local-terminal coordinator launch still `awaiting_acceptance`, no acceptance, attachment or stop intent, zero report/reply floors and the initial receipt chain. Its existing private authorization projects the original pane/backend; the genuine `WindowCx` reuses the native stop adapter's exit/absence observer without invoking stop or close. The nonce/claim/execution-receipt-bound callback must prove the exact pane exited or is absent before any helper effect. Across a continued controller epoch, only genuine absence is accepted; any existing old-epoch target is refused as potentially restored, even if it currently says exited. Current admitted owner routing and the original native host/session/window must still match; CLI inventory IDs and process callbacks are not native-window proof. The existing producer helper then proves the journal and mailbox really unused under their locks; nonempty/claimed journals stay provisioned. Successful retirement settles only the original attempt/observer/record/pane and marks its mailbox nonlive, making the original record re-preparable. Original launch/pane/target identity is never rewritten, and no acceptance, activation, release or native stop is fabricated.

Focused regressions: `run.luau(root, "dispatch", "failed_startup")` covers both launch backends, exact private witness consumption, acceptance/floor/chain fences, continued epochs versus restored targets, expired/recovered/reloaded authorization, original-attempt settlement and real mailbox-adapter producer refusal. `run.luau(root, "window_dispatch", "failed_startup")` exercises the actual native window observer and private authorization emission against exited/absent, live, partial/parked/foreign, stale-epoch/restored and drifting native fixtures.


A launch or adoption SPAWN rejected never reached native execution: every stored launch-family rejection precedes the native call, and an adoption `refused` result precedes its ask. When that entry is `rejected` with no pane, attachment, acceptance or stop intent, `mailbox_retire` (`mode=retire`) of its never-used mailbox is accepted without native stop evidence or explicit attachment, as if no launch had been issued. The same holds for a launch that was only staged: no execution or ORCH+ claim was ever recorded, it has no pane, attachment, acceptance or stop intent, and its requested window challenge expired or was issued before a host restart, so it can never be consumed. A live challenge (current host VM, before its deadline), including an expired one re-staged with a fresh nonce, is still refused. Accepting that retirement fences the unconsumed challenge in the same save: the challenge moves to `authorization_fence` and the launch becomes terminal `rejected` (`authorization_revoked`), so staging can never re-nonce and authorize it while its mailbox retires. An entry that was already rejected keeps its own rejection. Either way the retirement runs the ordinary empty-producer retirement, never the private producer cleanup, and settles no launch reservation. ORCH+ uses this when the owner cancels such never-launched work. Except for the narrowly guarded failed-startup path above, an executed launch still requires its exact stop. Regression: `dispatch/unused_retirement`.

A proven pre-effect capacity refusal includes `payload.retryable:true,effect_started:false`. Only this result authorizes rechecking the same exact request after pressure clears; its identity and immutable contents must not change. An ordinary `full` after a possible effect, a pending child/claim, or prior uncertainty carries no such permission. Capacity handling must retain the preceding worker state rather than inventing failed launch or acceptance.

Every `full` includes truthful `resource,current,limit`: resource is a nonempty ID of at most 96 characters, current is a nonnegative safe integer, and limit is a positive safe integer. Admission may report a projected count below a ceiling; this is not itself retry permission. Helper stdout for `full` is exactly four newline-terminated lines: status, resource, current, limit. Missing/malformed accounting remains uncertain.

The explicitly amended retry-proof contract has only two cases: host admission refused before launching a child; or a fresh, non-reconciliation operation on an existing mailbox whose reviewed target helper terminates successfully with exactly `admission_full\ncapacity_admission\n1\n1\n`, before acquiring the shared commit lock or beginning any effect. The adapter validates complete output and exit status, settlement releases the child/generation claim, and exact replay requires a new live ORCH+ authorization. Provisioning is excluded because it may already have created directories. Timeout, cancellation, failure, a matching prefix, other `full` results, or earlier uncertainty never grant this proof.

## Owner-gated import and recovery

Migration is a separate schema, not an ORCH+ runtime exception:

```text
{schema:1,origin:"spawn-migration",op:"import_config",request_id,
 migration_gate_id,source_client,target_host,source_revision,source_sha256,records_json}
```

`records_json` is the exact bounded record-array JSON string; its original bytes determine `source_sha256`. Paste the same preview **without migration_gate_id** into Config → Setup, inspect the source/target/revision/hash and records, then click **Allow roster import**. That owner action returns a one-use gate; it imports and launches nothing. Cancel explicitly or let a host runtime restart invalidate an unused gate. Consumed gates retain their result, and divergent existing record IDs are never silently overwritten. Keep source snapshots until canonical readback and a configured launch succeed. Never place literal credentials in a migration snapshot.

A consumed gate with an uncertain cross-store result is reconciled on exact replay through the retained authority binding and immutable snapshot. The authority checks its existing import receipt before revision checks; an already committed import is recovered without importing twice, and an unattempted idempotent import can complete. Changed tuple bytes cannot use that gate.

An occupied controller binding refuses ordinary mutations from another origin. A replacement window of the same stable owner/generation/controller host pane may inspect retained outcomes read-only after matching SPAWN authority and host-session checks; inspection changes no owner and exposes no effect grant. Routine `attach_worker` uses the exact retained native conversation or qualified terminal process proof described above, together with settled effect journals and a fenced previous controller generation; no human attest checkbox is substituted for those observations. It stores a separate control route and fences earlier authorization callbacks. A staged request whose authorization challenge was never consumed when owner recovery or attachment fences its old controller becomes `rejected` with pre-effect code `authorization_revoked`: nothing executed. An `accept` revoked this way may be re-sent as a new request on the attached route, and `accept` validates that route against the attachment record and original immutable launch, enrolment and acceptance event.

Config → Running agents shows retained bindings, pane aliases, claims and outcomes. When real active/uncertain effects or missing exact conversation/process observations prevent automatic continuation, the affected worker remains held with the specific missing evidence/action. Explicit **Fence managed controller for recovery** and exact-revision stopped/retired-executor confirmation remain separate exceptional recovery decisions, not routine reload requirements. Such confirmation preserves unknown outcomes and worker reservations and starts no replacement. Retired executor occupancy cannot block unrelated safe workers forever, but the affected generation remains held if an ask/publication outcome is still unknown. Config read failures/corruption are recovery errors, not empty state.

Tombstone checks also apply when no current owner slot exists: a retired binding cannot request a new catalog or stage an authorization. Read-only status may inspect that binding's retained outcome without allocating or recreating ownership.

Recovery includes native wake and authorization records. A resolved wake without an execution claim can be conclusively fenced as pre-effect while retaining its notification. Possible effects remain uncertain; unused nonces are revoked. Stopped-executor attestation never claims those unknown effects succeeded or permits retry. Normal transport identity reset refuses while that authority owns managed controllers, consumed authorizations or unresolved import gates. Authorization preflights canonical configuration; only retained proven pre-effect prerequisite failures can obtain a fresh challenge after repair.

## Bounds and durability

Logical reports/replies: 65,536 UTF-8 bytes; 1–32 chunks of at most 2,048 raw bytes; chunk wire JSON <=4,096; control/manifest <=2,048; bridge <=8,192. Outstanding data reports and replies each have eight slots; reply ACK reports have eight reserved control slots. Each generation is limited to 4 MiB/1,024 files. Host allocation is 64 MiB/16,384 files; every unretired generation reserves its full 4 MiB/1,024-file allowance, so at most 16 unretired generations exist (`LIMITS.generations`, also reported in the provisioned `limits`). The 17th provision is refused `full` (`resource=mailbox_allocation`), and a stored registry with more live generations fails validation. One operation/generation, four/host, 30-second process deadline measured in awake time. Transport registry <=4 MiB with 256 KiB reserved for settlement/control.

For managed protocol 2, only the read-only `status` response has a separate 16,384-byte inspection-envelope limit. Its retained original must still fit its own ordinary 8,192-byte frame; nested-status or oversized originals are refused. Requests, launches, other responses and mailbox/report bounds above are unchanged. Readers validate the complete wider status frame before applying its exact original outcome through the normal commit and acknowledgment path; inspection never authorizes another launch or original-request resubmission.

The mailbox adapter's whole-operation deadline counts awake progress. A 1 s watchdog adds the elapsed time between observations, but a gap of more than 5 s (host sleep, App Nap throttling or a paused hook) counts as one nominal second. Each helper child receives the remaining awake budget as its `process.run` timeout, so a child spanning a suspension is not declared uncertain because wall time passed, and a later child keeps its unspent budget. Awake waiting still ends as `uncertain`; a child that `process.run` itself timed out (for example, if the runtime counts the suspension) stays `uncertain` and needs the existing readback reconciliation. The deadline is never shortened. The bridge's authorization-challenge freshness window (30 s, host clock) is a separate security fence and is unchanged.

Within each physical mailbox, ordinary durable allocation is capped at 2,097,152 bytes/896 files and settlement allocation at 2,359,296 bytes/1,008 files, leaving room for a 1,572,864-byte journal replacement and 262,144 bytes/16 files of workspace. Target and worker use a separate short-lived shared capacity admission/commit lock; the producer's invocation lock is not reused. The capacity lock is released before stdin/stdout or polling sleep, so an awaiting worker cannot block incoming replies. Abandoned locks require explicit operator recovery, never PID/time-based stealing. Failed reconciliation (`full`, incomplete or missing) cannot clear an earlier uncertain-child fence.

The POSIX producer also creates and removes its invocation lock and workspace under shared capacity admission. Releasing admission before deleting those directories let a concurrent target scan enumerate disappearing entries and incorrectly reject valid reads as `binding_mismatch`. Normal cleanup now finishes before releasing the gate. Inside one invocation, re-admission (a later `wait` poll, or exit cleanup after an interrupted wait) waits out a busy gate for up to 10 seconds, because every holder releases it before sleep or stdin/stdout; a poll no longer fails `producer_locked` because a target commit briefly held the gate. If the gate is still busy after that bound, the exiting helper leaves the gate untouched and removes its own empty workspace and then its producer lock without it. Every commit had already finished under the gate and the workspace was emptied before the gate was released, so that lock holds no recovery state; keeping it refused every later call `producer_locked` with no live producer. A scan still running after the bound may see those two empty directories disappear and refuse at that scan, before the write it was admitting. Elapsed time only ends this helper's own wait; no PID or time test removes another invocation's lock or gate. A helper killed without cleanup still leaves its lock as a recovery gate: after establishing that no helper for that mailbox is running, explicit stopped-producer recovery removes `staging/worker-<owner>/`, `producer/lock` and any abandoned `capacity.lock`. The PowerShell producer lock is an exclusive handle on the retained `producer/lock` file that the OS releases when the helper exits, so it cannot outlive its process; its `wait` polls and its post-retirement removal of that file wait out a busy gate the same way, and an abandoned gate there needs only its own explicit recovery.

Publication uses exclusive same-filesystem staging and atomic no-replace final names. Existing identical bytes are success; different bytes conflict. Regular-file and ancestor checks reject symlink/reparse redirection; this is not a malicious-same-user sandbox. Host KV commit, OS files and native panes are separate stores: intent/claim, effect, readback and retained uncertainty replace any claim of a cross-store transaction. Reload/process-failure recovery is covered by the design; no power-loss/fsync guarantee is asserted.

Windows uses a fixed UTF16LE-encoded PowerShell wrapper with a separate UTF8 JSON payload and Windows CRT argv escaping; SSH nests the remote serializer inside the pane-host serializer. Commands are bounded before pane creation (Windows 7,000 encoded characters; POSIX 32 KiB). Native OMP on an unverified Windows launch shell remains explicitly unavailable rather than falling back to another identity.
