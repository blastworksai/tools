# ORCH+ protocol reference

This is the detailed contract behind [ORCH+](README.md) 0.6.2: conversation/project association, storage, dispatch, mailbox, roles, proof, landing, rollover and recovery. [plugin.toml](plugin.toml) declares the package version; [requires.json](requires.json) declares Tern 0.9.10 and SPAWN 0.4.0 requirements. Those requirements are not qualification results. The README covers everyday use. The agent-facing contracts are [worker-brief.md](worker-brief.md) and [coordinator-brief.md](coordinator-brief.md).

Normal use is **New orchestration…**, the compact agent picker, an orchestrator pane and **ORCHESTRATED WORK**. Settings and project START decisions are normal controls; compatible reconnection is automatic. Internal owner cards, raw commands and manual settlement/recovery belong under **Advanced**. There are no `orchplus://` links. Dispatch and assistance publish bounded one-shot operator intents (`main.operator-intent`, role `orchplus.intent`). Only the controller-origin window runs a dispatch intent after rechecking the pane, logical session, host and window incarnation; the host independently validates it. Expiration does not prove nonexecution, and a stale rendered action never authorizes replay. Host-block clicks do not authenticate a human.

Assistance buttons (**Inspect**, **Recheck**, **Reveal owner**, **Stop assistance…**) follow the same rule while a live continued origin exists: when the session's command cursor belongs to the active controller owner and generation, the host stamps that origin's window (key, incarnation, native session, host) into the intent and only that window runs it. Before the controller's first command there is no cursor, so intents are not fenced to one window and any ORCH+ window showing the controller in its admitted session may take them. While the controller is restored uncertain (no live origin), assistance stays open to any window showing it, so a recorded owner can still be inspected, rechecked or stopped. Both cases keep their pickers and host re-validation.

Background receipt, reply, claim, notification and exit settlement uses the captured controller's numeric session/pane and rechecks its exact host, window incarnation, owner and grant. Selecting another session does not transfer that authority. Human actions still require their foreground context; displaced actions are refused, not saved to run when the user returns. Background settlement must not reveal panes, switch sessions or open another window.

The current Tern SDK cannot target a native-agent start or a new-tab launch into a specified inactive session. Such creation remains unissued and visibly waiting; it is not an uncertain launch and cannot expire into a claim that might have executed. Existing-agent settlement continues. No terminal substitution, temporary window or session-switch workaround is used.

## Settings and saved defaults

Settings use the native `orchplus.form` pane; scheduling and settlement continue. **SAVE AS DEFAULT ORCHESTRATION SETTINGS** seeds future orchestrations, while existing policies remain in `dispatch.policies`. Installation saves use `expected_revision`; a first explicit save sets the server-owned `defined` marker even when policy values are unchanged. Later unchanged saves do not advance revision. Clients cannot set that marker. Required SPAWN setup, saved defaults and separately consented provider readiness are independent. Agent commands, authentication, model/profile selection and declared provider families stay in SPAWN; repository/target choices belong to projects.

The following editing controls apply to **session overrides**, not precontroller Installation defaults.

Only the session's admitted active controller may save instance settings. Native fields keep a complete unsaved draft; **SAVE FOR THIS ORCHESTRATION INSTANCE ONLY** commits changed fields through `policy`, fenced by the saved `expected_policy_sha256`. A stale save refuses with `policy_conflict` without overwriting newer state; the pane retains entered values for review. Policy saves exclude operational pause/exclusion state. Templates use the same fenced policy contract, with bounded `{id,title,prompt,output,next,class?,custom_fields?}` entries. A canonical policy over 48 KiB is refused as `policy_too_large`. Native form receipts bind nonce, request, source window, host and native session; hiding the source tab is not loss of its native identity. A refused source-bound operation acknowledges only the local draft, not a write. Close cancels its exact nonce-bound draft even when an ACK was lost or its source is unavailable; it never saves.

**Agent selectors.** Preferred worker/orchestrator, reviewer and alternative-agent preferences list saved SPAWN configurations independently of launch readiness. Actual starts still require the current record's capabilities and eligibility. Merge/deploy defaults to the exact accepted worker with actual `release-manager-v1` capability; selected-record mode uses a separate release agent and excludes reviewers. There is no task-type routing table or model-substitution permission. Commands and model flags are never constructed by ORCH+.

All values are exposed on the machine-readable `workflow-index` node's `policy`. Restore accepts the supported legacy 5-, 10-, 16-, 18- and 27-key policy shapes and legacy review policy through explicit migration; arbitrary shapes remain rejected. Legacy `auto_launch_intake` becomes `auto_start_projects=false`, not permission to launch imported work. Policy drafts exclude operational `paused`: saving preferences never resumes a paused orchestration. Routing-policy digests cover routing fields, so pre-upgrade decisions are re-evaluated on capacity refresh before claiming.

**Advanced pane orchestration list.** The diagnostic Config view lists agent panes in the current native session on this host, from `cx.agents` (at most 64 rows, with an "N more" note; titles are UTF-8-safely truncated and never identity). Rows are ticked by default:

- Managed workers are listed by durable `worker_id`. Unticking adds the worker to `excluded_workers`; automatic progress-report requests and automatic rollover skip it. Observation, mailbox reads, receipts and owner actions continue; a tick never stops or retires anything.
- Hand-opened agent panes are window-scoped (pane id, window incarnation, native session, host). Their marks are eligibility only and not durable. Ticking never adopts a pane; the exceptional assignment-injecting path is [Advanced explicit verified attach](#advanced-explicit-verified-attach). Normal **Attach…** uses passive association and separately consented enrollment instead.

Pause holds new work, not committed receipts, replies, decisions or already-issued effect settlement. START while paused records only the selected project's permission and waits for resume; resume does not START other projects. Launch records, accounts, models and host configuration stay in SPAWN; ORCH+ settings cannot submit commands or credentials.

**Context measurements.** READY, HEARTBEAT and CHECKPOINT may carry either `context_used_pct` (integer 0–100) or `context_snapshot={current_tokens,window_tokens,observed_at_ms,first_turn_tokens?}`, never both. Snapshot counts are safe integers, `window_tokens > 0`, and counts cannot exceed the window. Measurements bind to the reporting worker generation and report sequence; calculated mode also requires its stable first-turn baseline. Billing/output totals are not context occupancy. Missing clock provenance, stale observations or inconsistent baselines/windows cannot trigger rollover. Restore retains evidence but requires continuation and fresh measurement/observation before eligibility returns. The workflow projection exposes `context_rollover={mode,status,threshold_pct?}`; `unknown` is not estimated.

## Projects and conversation association

`dispatch.projects` binds each project to one logical session by `orch_project_id`, with a revision, name, `started`, sources, passive associations and optional verified repository. Workers, plans, intakes and template chains retain that association. **ACTIVE** describes live associated work/conversations, including idle live conversations; it is not the same as `started` or execution permission. Pane names, provider/account labels and displayed usage are presentation, never identity.

`new_project` creates unstarted work. `project_start` checks the exact project revision and, when `checks_pending`, explicit review of proposed check argv. With a managed coordinator, it records one immutable `project_start` control for that exact activated owner/generation and approved source snapshot; publication alone does not release work. The coordinator consumes and locally claims the control, publishes the action-correlated `PROJECT_START_CLAIM`, and waits for its accepted receipt. ORCH+ accepts that claim and releases only the captured held sources and eligible unissued work once. Both `coordinator-control-v1` and `project-start-v1` are required; a reserved, uncertain, retiring or old-capability coordinator never falls back to direct execution. The established standalone mode with no coordinator retains host-owned explicit START. Admission, pause, quota, checkout and proof gates still apply in either mode. Newly added sources stay held by default (`auto_start_projects=false`); explicit automatic-start policy remains separate authority and `force_held` coordinator additions stay held until their own approval. Later additions cannot inherit an earlier START.

`project_start_retry` names the existing project, START/action identity, captured revision and decision context. It inspects uncertain publication or retries only a demonstrably unissued original delivery; it never allocates another START grant. Normal UI shows pending publication or waiting for the coordinator instead of claiming the project is running. Failure remains visibly held with an actionable explanation; exact owner/project/action/revision and delivery evidence belong in Advanced.

A START for newly held additions never revokes an already-started project's earlier permission or pauses its approved work. Definitively changed ownership or source closes the old grant without releasing anything; authenticated exact old claims can settle as refused report facts so the producer is not permanently blocked. The host retains private original correlation and exposes only safe status. Once closure is proven, a fresh explicit START approves the current subject and current orchestrator; Retry still cannot replace the old grant.

If the old orchestrator died before consuming its START, explicit retirement can withdraw only its exact closed unread START tail. It requires positive exact native stopped evidence, owner-generation fencing, complete original publication/wake settlement, and every unrelated delivery, report, gate and local claim settled. The physical helper verifies the actual journal and unread bytes before removal. No consumer ACK, cursor, self-release or stopped/retired evidence is invented. Uncertainty or another unresolved control remains held.

**New Agent Session** deliberately launches a saved configuration with `open_conversation=true`; the orchestrator uses `presentation="coordinator_adjacent"`, ordinary conversations `user_new_tab`, managed background tasks `background`. Conversation/coordinator starts and explicit enrollment do not need project task START, but still require an unpaused session and their own admission/capability checks. Discussion is not approval to execute held project tasks.

**Attach Existing Agent Session** first records `associate_conversation` against an exact scoped pane binding, without injecting an assignment or changing permissions/context. Busy native conversations stay passively attached. Optional managed enrollment uses `enrol`: Native OMP sends once to the exact idle conversation; terminal enrollment copies instructions once for the owner to paste. Copying is not acceptance; the real matching ACCEPTED and SPAWN acceptance remain required. This normal flow is distinct from Advanced legacy `adopt`.

`detach_conversation` removes only passive membership, never stops the conversation. `project_associate` moves managed membership without changing the existing task; outstanding effects/decisions, active plan members and unfinished intakes/chains refuse movement as `association_busy`. Project repository changes require canonical host-verified `{cwd, repo_root, common_dir, target_ref, head_revision, queue_route}`; conflicting shared routes or live repository obligations refuse the change. Text/research projects need no repository.

Normal conversation workflows consume the hidden `conversation-result` node (`orchplus.conversation.result`), not the generic last command message. Its single per-view payload is `{source_nonce,orch_session_id,result}`; `result` is the actual host response with `request_id`, `command`, `ok` and returned fields. A `new_project` result may additionally carry `creation_request_id`, bound by the host to this pane's actual current orchestration-creation response. Housekeeping cannot overwrite it. The consumer matches source nonce, logical session, exact request and command, then requires the corresponding live projection before completing its local job. A missing/mismatched result stays pending; it never authorizes repeating the command.

Initial startup controls wait for that creation-bound completion, not admission or project presence alone. A premature, already-clicked Start may retain only one unissued project-choice continuation on the exact default-creation job. Matching successful completion with unchanged scope opens that choice once; unknown, mismatched, failed or changed-scope results never release or replay a native effect. The existing idle-wake helper advances pending creation/settings continuations even with zero workers. Waiting for human input alone does not keep that helper running.

Finishing requires settled work and sources; unresolved enrollment, effects, deliveries and decisions remain blockers. Finished summaries do not erase live authority. `project_reopen` creates a new unstarted project from the retained source reference, never replays tasks/approvals. Restore migration associates retained work with projects, holds unstarted sources and disables legacy automatic intake start; it preserves existing effects and owner fences.

## Roles and provider families

Current roles are `builder`, `reviewer`, `release_manager` and `coordinator`; historical `labeller` work remains settleable but no new classifier sessions are launched. Reviewers and optionally selected release agents use the normal managed provision/launch path and are not quota-routed. Worker-mode merging reuses the exact accepted builder, not another session on the same account. The physical allocation domain remains sixteen live generations, 64 MiB and 16,384 files; queued or uncertain allocations count conservatively, with headroom reserved for review, rollover and selected release actors.

Assignments retain their actual task instructions and built-in role/review guidance. Optional global role-instruction overrides are retired: legacy policy maps are validated and discarded during migration, not injected into new assignments. Historical immutable assignment evidence is preserved. Actual permissions remain in SPAWN's saved CLI configuration. Task classes are optional metadata, not static agent routes.

**Families are declared, not verified.** SPAWN owns canonical `provider_family`. Direct-service defaults are Claude→anthropic, Codex→openai, Kimi→moonshot, Agy/Antigravity→google, Grok→xai and Muse→meta. OMP, custom commands and alternate-provider wrappers need an explicit underlying provider declaration. ORCH+ consumes that catalog value and migrates legacy declarations through SPAWN's admitted writer; it does not keep a second editable `family_map`. Configuration is not proof of the model actually running.

## Scope, checks and checkout facts

Queued work may declare `files`, `scope = {paths, systems}` (default: `paths` = `files`), `checks = [{check_id, argv}]` and `base_ref`. For work that declares any of them, ORCH+ builds a canonical **assignment manifest** `{checks, files, scope, base_ref?}` (≤ 4096 bytes), sends its exact bytes in `mailbox_provision.manifest` and stores its digest on the worker; the helper modes below need a record with `check-runner-v1`. SPAWN binds the digest into the provision digest and writes the bytes as the mailbox's `manifest.json`; ORCH+ re-derives the manifest before provisioning (`manifest_mismatch` otherwise). `scope.systems` is brief text only: ORCH+ cannot see outside systems, and workers must ASK before touching an unlisted one.

The SPAWN producer helper publishes two **helper-only** reports, which workers cannot send with `report`:

- `checkout` → CHECKOUT `{worktree_path, common_dir, branch, head, base?, changed_files (≤512), changed_overflow, changed_total, dirty}` computed by git (committed changes since the merge base with `base_ref`, plus uncommitted and untracked paths). When the manifest has no `base_ref` (absent or empty), the first `checkout` pins the current HEAD in `<mailbox>/checkout-base` (beside `provision.json`, written atomically, first writer wins). Every later checkout reports `base` = merge-base(checkout-base, HEAD) and includes committed changes from `base...HEAD` in `changed_files`. A `checkout-base` that is not a regular file holding one 40- or 64-hex revision is refused with `storage_error`. A hyphen-led `base_ref` is still treated as unusable and never pins.
- `run-checks <check_id>` → CHECK_RESULT `{check_id, argv_sha256, exit_code, output_sha256, head, ran_at_ms}`. The argv comes only from the authenticated manifest and runs without a shell; a result counts only for the `head` it ran on.

Gates from these facts (all host-consumed owner gates; see [Owner gates](#owner-gates-loop-caps-and-stale-claims)):

- **`shared_checkout`** at queue time, before provisioning: work whose cwd is the same as, contains, or is nested within another visible live worker's cwd or reported worktree waits for **Launch anyway** or cancel. Peer detection spans logical sessions in the same authority/data directory; positively distinct execution hosts are separate. `checkout_roots` annotate the finding, not whether protection applies. A later CHECKOUT reporting the same shared worktree raises an acknowledgement gate once per path. Unrelated processes and separate Tern data directories are outside this authority's visibility.
- **`file_overlap`** at queue time: declared files intersecting files declared or changed by another live worker.
- **`scope`** on CHECKOUT: changed paths outside `scope.paths` (or an overflowed list). Accepting it is durable on the worker (`scope_accepted`); shared-checkout acknowledgements likewise (`shared_acked`).

A CHECKPOINT whose `worktree_ref` differs from the latest CHECKOUT holds landing as `checkout_mismatch`; an unaccepted out-of-scope checkout holds it as `scope_open`.

## Review (cross-family judge and rework)

While `require_code_review` is true, REVIEW_READY or an approved coordinator `review` proposal opens one durable review per work in `dispatch.reviews` (≤64): `queued → requested → approved | changes_required → … | capped | cancelled`. Each round launches a fresh reviewer on the first current, eligible `reviewer_records` entry in owner order, distinct from builder and release manager; `require_other_family` additionally requires a different declared family. Missing reviewers hold as `reviewer_unavailable`; missing required families hold as `family_unknown`. After ACCEPTED the reviewer receives `review_request {review_id, round, question_id="implements_task_v1", builder_work_id, task_ref, plan_ref?, plan_revision?, source_ref, artifact_revision, scope_paths, findings_prev}` and answers whether that exact change implements the task without out-of-scope changes, with REVIEW_RESULT `{review_id, round, artifact_revision, outcome: approved|changes_required, findings[≤32 {finding_id, path, line?, summary}], summary?}`. No score or confidence. The reviewer finishes when its result settles; a lost reviewer holds as `reviewer_lost`, never an automatic relaunch. With review disabled, no new reviewer or `review_request` is created, no reviewer-availability gate is needed, and explicit review proposals do not execute.

Typed `rework {review_id?,round,artifact_revision,failed_checks[{check_id,exit_code}],findings}` carries failed checks and review findings. Check repair is independent of reviewer availability; without review, `review_id` is absent. With review enabled, REVIEW_READY on a new revision opens the next round with previous findings. `review_rounds` defaults to five; check repair has its own loop cap. A new revision invalidates older review/check proof. Only the assigned reviewer reports REVIEW_RESULT; the builder cannot review itself.

A review's `void` is `{artifact_revision, at_ms}` when a newer checkpoint voided the approval, or `{target_revision, at_ms}` when a landing refresh (target moved / `stale_target`) voided it; earlier records keep `artifact_revision`.

## Proof rule

`workflow_rules.verify_landing_proof` decides every ungranted landing from durable facts. Every declared check requires a helper CHECK_RESULT with exit 0 on the exact source revision, in all modes; worker-attested checks do not replace helper proof. Wire validation remains in shared `wire/codec.luau`.

| `require_code_review` | `require_other_family` | Proof mode | Additional review proof |
| --- | --- | --- | --- |
| true | true | `cross_family_review` | Approved exact-revision review by a separate worker on a different record and declared family |
| true | false | `helper_checks` | Approved exact-revision review by a separate worker on a different record; same family allowed |
| false | false | `review_disabled` | None: no reviewer/review request; proof and grant review IDs remain absent/nil |

Fresh defaults are true/true. Legacy `enforce_cross_family=true` migrates to true/true; false migrates to true/false. Turning review off normalizes the family flag to false; re-enabling review does not resurrect its old value. False/true is invalid.

Current policy is checked before new grants. Issued live grants and proof remain immutable across policy edits: drain committed replies/results, or block for explicit recovery when uncertain. Never rewrite delivered proof, invent review IDs or discard live reviewer settlement obligations.

Failure codes include `review_required`, `reviewer_is_builder`, `reviewer_record_is_builder`, `review_stale`, `review_not_approved`, `family_unknown`, `family_same`, `checks_undeclared`, `check_missing`, `check_stale` and `check_failed`. The merge/deploy actor must have actual `release-manager-v1` capability and a current eligible binding. Worker mode requires the exact accepted builder; selected-record mode additionally separates that actor from the builder. Both separate it from the approving reviewer. The checkpoint and passing checks must match the requested revision with no unresolved holds.

## Owner gates, loop caps and stale claims

Gate kinds: `owner_question`, `coordinator_proposal`, `native_input`, `landing_approval`, `quota_fallback`, `loop_cap`, `stale_claim`, `legacy_grant_outstanding`, `shared_checkout`, `file_overlap`, `scope`, `reviewer_unavailable`, `family_unknown`, `deploy_hold`, `intake`, `label_unknown`. The host-consumed kinds (`quota_fallback`, `loop_cap`, `stale_claim`, `shared_checkout`, `file_overlap`, `scope`, `legacy_grant_outstanding`, `reviewer_unavailable`, `family_unknown`, `intake`, `label_unknown`) are answered from fixed options, never free text, and send the worker nothing; the others (including `deploy_hold`) deliver an immutable `owner_decision` reply. Answers carry a tagged source: `{kind="owner", …origin}` or `{kind="policy", policy_revision, rule="auto_approve:<kind>"}`; untagged answers from earlier builds are read as owner answers only at restore.

A coordinator proposal that ORCH+ refused itself (`source.kind = refusal`) reads "Refused by ORCH+ (<code>), not an owner answer: <reason>".

**Loop caps.** Model/worker loops stop at the configured `loop_cap` (default five) and publish a scoped decision. These include rollover checkpoints, report requests, owner retries, check repair, landing refresh/grants, review and deploy attempts, and template chains. **Allow more** resets only the named loop; structural bounds and final stop decisions are not bypassed. Code-only readback/backoff waits remain bounded.

**Stale claims.** A claimed or uncertain action older than `stale_claim_min` (default 120 minutes, zero disables) opens one `stale_claim` decision: keep waiting or inspect recovery. The native editor uses `hh:mm:ss`. Age alone never takes ownership, resends or settles an action; the decision is superseded when the claim settles.

## Autonomy inside plan scope

In-scope automation applies only to imported plan/board work with declared paths and no unresolved scope, file-overlap or shared-checkout gate; dispatch must name a current eligible record. Fresh defaults allow `dispatch`, `report`, `review` and `landing` policy approvals. The durable answer records the exact policy revision and rule. Manual/out-of-scope work still asks. Proof, pause, capacity, loop limits and repository protections remain mandatory. A paused execution proposal is refused without wedging its report lane; resume reevaluates only still-pending eligible decisions, not rejected effects.

Approved proposals execute exactly once through a durable execution record: `dispatch` queues the proposed record and prompt inheriting the parent's source and scope; `report` sends `report_request`; `review` opens a reviewer-worker review only while code review is required; `landing` approves the matching item. Review-disabled policy refuses review execution. `rollover` is recorded only. Policy never bypasses loop caps, proof, capacity or pause. Decisions answered before 0.4.0 are never executed.

Conversation-first coordinator proposals `new_work` and `add_source` are different: they name exactly one existing `orch_project_id` or `new_project_name`, and approval adds **held** work only, including while paused. They do not require an existing work checkpoint and never START the project or resume other work. `new_work` carries its proposed record/revision, prompt, scope and declared checks for review; `add_source` preserves source identity and desktop-board observation requirements. The pause/refusal and in-scope automation rules above concern execution proposals, not these passive additions.

## Mailbox lifecycle and nightly sweep

Each managed worker generation has one private report mailbox on its execution host, provisioned by SPAWN (`mailbox_provision`) under the configured permitted root before launch. ORCH+ reads reports through SPAWN, publishes exact ACKs and replies, and the producer confirms ACKs with a cumulative receipt watermark. A confirmed watermark sets `compaction_pending`; the next poll issues `mailbox_retire mode=compact`, deleting only the confirmed prefix. `mode=retire` happens only after an explicit finish or coordinator release, a settled generation (receipts, replies, notifications drained) and an exact native stop observed `exited` or `absent`. Once the exact retirement result is consumed through the authenticated request floor/page, SPAWN reclaims its retired mailbox and worker metadata rather than retaining a lifetime tombstone. ORCH+ keeps any worker still pinned by live obligations. Uncertain retirement is never repeated.

The nightly sweep retires orphaned mailboxes without an OS timer. On normal window ticks the due slot is today's `sweep_time` once passed, else yesterday's. When it is newer than the session's durable last run, the window sends one `sweep` with the slot's local date (`catch_up` when more than 15 minutes late), so a missed time runs exactly one catch-up for the latest slot. The host refuses any date at or before its last run (`sweep_already_ran`); a refused request is retried by the same window only after 10 minutes. Decisions, checked in order per worker with a mailbox:

| State | Decision | Reason code |
| --- | --- | --- |
| Mailbox already retired | nothing | `retired` |
| Control route needs continuation, or another controller incarnation | keep | `continuation_required` |
| Any uncertain effect | keep | `uncertain` |
| Retirement issued and unsettled | keep | `retirement_pending` |
| Other queued, claimed or backpressured effect | keep | `effect_pending` |
| Coordinator with unresolved owner generation or executors | keep | `owner_unresolved` |
| Rejected report held | keep | `report_held` |
| Worker held | keep | `held` |
| Never bound to a launched pane | keep | `unlaunched` |
| Not stopped, `compaction_pending` | compaction queued | `compaction_pending` |
| Not stopped | keep (the sweep never stops) | `live`, or `finishing` |
| Stopped, not settled | keep | `unsettled` |
| Referenced by active rollover, landing or review work | keep | `referenced` |
| Exact stop observed, settled, unreferenced | `mailbox_retire mode=retire` queued | `stopped_settled` |

Queued effects follow the normal claim, grant, deadline and uncertainty rules. The sweep never stops a worker, infers a stop or touches another session. Runs are logged in `dispatch.sweeps[session]`: `last_date` plus a ring of 14 runs (date, registry revision, time, catch-up flag, counts, up to 64 per-worker decisions). Config (**Mailbox sweep**) and the workflow card show the last run. Turning the sweep off stops new runs and keeps the log.

## Quota routing (USAGE capacity)

With `quota_routing` on, ORCH+ consumes USAGE's read-only **capacity v1** export (owner-enabled and revocable in USAGE Setup) through the controller's pane-free host relay. The window requests bounded `snapshot`/`page`/`validate` operations; keyed relay responses retain request ID, peer incarnation and binding proof. No `usage.capacity` pane or background transport tab is opened. Pages of one immutable revision are assembled in index order; byte length and SHA-256 must equal declared `size` and `revision` before parsing (≤2 MiB). Hashing is incremental, at most 16 KiB per window tick (`quota.HASH_BLOCKS_PER_STEP`); interruption fails closed as `hash_interrupted`. Validation follows complete hashing/parsing and precedes host admission of evidence. Failures retry on automatic refresh (30 s) or an explicit refresh. No private USAGE state, provider call or credential is touched, and no account is guessed. Optional display usage is separate from capacity authorization: unavailable display does not disable manual selection, while unavailable required capacity holds routed work.

**Normalization** (`quota.luau`, at most 24 records per evidence set: pending routed records first, then the allowlist, then other eligible records):

- **Binding:** only USAGE's exact join `(scope.spawn_join.namespace, host_key, config_revision, account.id)` = SPAWN catalog `(namespace, host_key, config_revision, record id)` with a `profile_binding`. Labels, `capacity_binding`, equal percentages and titles are never identity. A local publication must agree with USAGE's `current_roster`.
- **OMP consumers:** a record matching a scope `consumers[].id` with `account_ids = ["<account id>"]` is evaluated against that account under the same rules; locally the same consumer must appear in `current_roster` with the same `definition_revision` and `account_ids` (else `local_roster_changed`). Unassociated: `consumer_unassociated`.
- **Source:** `current`, unchanged generation/profile generation, no clock skew.
- **Readings:** every bound reading exists, has a canonical ID inside the binding and numeric remaining percentages; unavailable or last-known windows carry no proof. Duplicates use the newest observation per window/pool; equal-time disagreement is a conflict.
- **Result:** `known` with the lowest remaining % across bound windows, oldest observation, earliest reset, earliest weekly (`seven_day`) reset, binding and principal digests, and a `usage` reading (below); otherwise `unknown` with a reason (`unbound`, `consumer_unassociated`, `ambiguous`, `binding_unverified`, `source_*`, `local_roster_changed`, `reading_missing`, `identity_mismatch`, `unavailable`, `conflict`, `future_timestamp`, `stale`, `reset_passed`, `unit_unknown`, …). The host re-checks freshness with its own clock: past USAGE's lease, older than `quota_max_age_ms` or past a reset is unknown, never a refill.

**Rule.** For new work and orchestrator starts, eligibility and the explicit alternative allowlist precede quota and preference. Fresh, bound capacity must be strictly above the reserve in every window. Keep the requested record when sufficient; otherwise order permitted alternatives by weekly reset, then record ID. A provider or account/principal change requires its matching `initial_dispatch_*` permission. Model flags are not compared or changed by ORCH+. A disallowed qualifying alternative opens a revision-bound `quota_fallback` decision; approval applies only to that work and is refused after the relevant catalog, policy or evidence changes. No qualifying evidence holds work before provisioning. With routing disabled, dispatch uses the selected record exactly.

**Launch-time check.** The decision binds the USAGE and authorization revisions. Immediately before claiming the launch the window asks USAGE to `validate` that revision; the claim must carry a `current` result validated within 30 s, and the granted host claim stores it (`claim.capacity`). A changed, expired, revoked or incomplete revision means refresh: the provisioned record can only stay or be held. Routing-policy edits re-evaluate unlaunched routed work and void stale fallback gates. This is not a provider-side reservation.

**Rollover routing.** A successor prefers its predecessor's saved record and uses only that rollover kind's enabled alternative allowlist and provider/account permissions. A disallowed sufficient alternative opens a decision on the predecessor. Rejection or missing evidence holds the rollover; it does not change the running predecessor or silently select another model.

**Concurrency ledger.** Each routed worker's `routing.reservation` moves `reserved → claimed → launching → active → released` (`uncertain` keeps occupancy), bound to the decision digest and evidence revision. Released on verified stop or retirement, a definitive pre-pane failure, or a hold before launch. With `concurrency_limit` > 0, exceeding it holds with `concurrency_limit`; a rollover successor may overlap only its predecessor. Restore validates phases, history (≤8 edges) and that only provisioned routed work holds a reservation.

**Selector evidence.** Model/profile settings remain SPAWN configuration, not verified runtime identity. ORCH+ has no model-substitution toggle. Reviewers and separately selected release actors retain their records and are not quota-routed. Unlaunched work on a continued route is reevaluated against current evidence.

## Per-worker USAGE deltas

`quota.normalize` attaches to each known record a reading `usage = {account = {canonical_ids (SHA-256 of each USAGE canonical id, sorted), generation}, windows[≤16 {key, pool, remaining, resets_at_ms, observed_at_ms}], observed_at_ms}`. From current, unexpired evidence ORCH+ stores `usage_before` when the launch/adopt outcome binds the pane and `usage_after` at DONE, refreshed at finish when newer — never from `claim.capacity`, never copied to a rollover successor. Projected workers carry `usage_before`, `usage_after` (nil while running) and `usage_shared_with` (other workers with readings on the same account whose observation spans overlap); the health card computes `quota.usage_delta` per window, or says why it is not comparable (unbound, different account, reset crossed). USAGE is percent-only and account-wide: a delta is never one worker's exact use.

## Reconnect and Advanced recovery

Compatible paired reconnection is automatic for the same verifiable controller and retained worker identities. It reads existing outcomes without replaying uncertain effects, attesting termination, erasing ownership or resuming paused work. The lower-level controls below are exceptional **Advanced** recovery, not a required reload checklist. Local/current-account execution is the default; remote work uses the existing Tern connection to one execution host, with no parked pane or product daemon.

**Inspect**, **Recheck**, **Reveal owner** and **Stop assistance…** are window-handled requests returning bounded events. Observations are limited to the source pane's host. Controller aliases are associated by the host-issued nonce on the exact native surface, never by ID equality. Stop assistance closes only the uniquely nonce-associated controller block; it never guesses a target. If an alias cannot be proved, inspect or stop the recorded owner manually. Native snapshots are not claimed to enumerate all ownership.

Closing a controller **does not clear ownership**. Reopen ORCH+, choose the registration and **Recheck**. An observed-unavailable result makes current activity unknown, not stopped, and retains pending executors; an observed positive executor count cannot be overridden by attestation. After restore, a retained positive executor count is **unconfirmed**. Only with an observed-unavailable owner, unknown activity and unconfirmed executors does **Verify retained executors and unavailable owner…** appear; it records `executors_verified=true` as operator-attested evidence. Then **Begin fenced recovery** and confirm the displayed owner/generation/revision (intervening registry changes invalidate it). Recovery retires that owner and advances the generation floor without retaining a completed-owner history; it never launches a replacement.

If the entire continued controller window ended, active-owner assistance remains addressed to that exact window; a different window cannot turn its local absence into stop evidence. A normal ORCH+ host reload/restore makes occupied owners uncertain while preserving pending work and document intents. This fences all occupied owners, not just the closed window's owner. After independently verifying the original native incarnation ended, use the surviving view's fresh **Recheck**, explicit owner verification and guarded recovery, then separately **Claim controller in this pane**. Reload or timeout alone never proves termination or clears ownership.

For an already stopped worker with its mailbox retired, local ended-writer ruling recovery needs the bound active ORCH+ owner, not SPAWN execution admission. The new owner proves the original writer ended and independently reads the live buffer and disk before settling an existing ruling or clearing an absent intent for a separate new write. Native execution remains unadmitted; future work or live-worker reattachment still needs the independent SPAWN recovery and retained-admission steps below.

ORCH+ retains the **dispatch action/request/executor ledger**; a zero inspection count does not clear it. A restored uncertain claim is reconciled only through the displayed exact action/executor/revision confirmation after unavailable-owner evidence and operator verification; this records the attestation and holds the work, never repeating an effect. Resolve retained actions before ordinary owner recovery.

**Continuation.** **ORCH+ Continue controller in this window** (palette, in the window that should become the origin) confirms the displayed owner/generation/revision after you verify old executors stopped. It records a new control origin while keeping claims, counters, pending decisions and coordinator uncertainty. Inspect original SPAWN outcomes read-only before attaching workers; a missing or oversized outcome is not permission to resubmit.

Never-launched work follows the continued controller: a queued or provisioned ordinary worker of the same owner, generation and alias whose launch is absent or never-claimed `ready` has its route and never-claimed `mailbox_provision`/`launch` requests moved to the continued window with the same request and action IDs. A provision claimed in the old window settles through the continued route, and its launch is built there (**Run queued launch**; quota routing re-evaluates). Claimed, backpressured, uncertain or settled launches, adoptions and rollover successors (`successor_launch_fenced`) keep their route.

**Cancel never-launched work…** (`cancel_work`) accepts an unissued intent or definitive current pre-effect refusal; continuation and missing peer history are not proof of nonexecution. An uncertain request needs its exact retained SPAWN status and positive pre-effect evidence. A live challenge, missing/consumed history, open outcome or another request's response cannot authorize cancellation. Without a provisioned mailbox, a definitive provisioning rejection permits removing the worker and its reservations without a status read, native stop or mailbox retirement. The controller identifies the operation as `mailbox_provision`, not the reserved launch.

With a provisioned, never-used mailbox, cancellation records the live `withdrawn` obligation, consumes the proven-unexecuted action and queues one exact `mailbox_retire` (`mode="retire"`). The routed worker releases concurrency and is excluded from further routing, on both the original and explicitly continued controller route. Nothing native is stopped, launched or re-sent. The worker remains until SPAWN confirms retirement; a coordinator's unresolved owner/executor obligations still prevent release. A definite retirement refusal consumes that completed action but keeps the mailbox and refusal visible: cancel again to issue one fresh retirement. A pending or uncertain retirement never issues twice (`retirement_unresolved`). Reload preserves the withdrawal and retirement obligation. Regression: `dispatch/withdraw_fenced`, `health/withdraw_fenced`.

**Worker reattachment.** **Continue after reload / reattach explicitly…** selects the exact worker and attests its identity. Its scoped proof names the target/owner evidence; the native input also keeps its captured authority namespace/revision, so a real intervening commit still refuses that input without refreshing the attestation. SPAWN checks attachment independently. Launch, mailbox and enrolment identities never change; only the control route does, and old callbacks stay fenced. The control also appears for any launched generation awaiting acceptance (including a rollover successor). A generation reloaded between its ACCEPTED and SPAWN `accept` may meet `authorization_revoked`; ORCH+ keeps `accept_pending` and re-issues the same acceptance on the attached route. Revocation is pre-effect for every operation: a revoked `native_wake`, publication, read, compaction/retirement or stop completes as `authorization_reissue` and its lane re-issues it on the continued route; a revoked `attach_worker` completes as `reattach_required`; launch, adoption and provisioning keep an explicit hold. Non-holding diagnostics never overwrite a held worker's recorded cause.

**Unknown outcomes stay held.** Continuation cannot satisfy unavailable-owner recovery or reactivate an uncertain coordinator. A coordinator restored `uncertain` resumes (`running`, or `retiring`) only when its exact attested attachment commits and none of its executors remains claimed, uncertain or counted; a recovery intent, retired-generation fence or restored-pane hold prevents reactivation.

**Advanced reload recovery.** The retained recovery guide reads SPAWN's exact `owner_status` and exposes only unresolved steps. Automatic continuation handles the same verified native controller and quiescent worker bindings; absent identity or issued uncertainty remains a scoped decision. Operator recovery may require independently verifying old executors, fencing a previous owner, reconciling admission and reattaching the exact worker. Later steps remain unavailable until earlier prerequisites settle. No guide opening is an attestation or permission to replay.

Controller retirement uses the captured authority namespace/revision and exact current owner/generation; pending executors and unresolved dispatch still prevent it. The explicit native operator route permits only controller retirement; the background authority route remains closure-only. Retirement clears executable admission permission but preserves the admission sequence, workers and pending evidence. Use **Open ORCH+ controller** to reach the separate normal claim, then reopen the guide and reconcile the retained admission. Reattachment refuses `admission_required` before queuing an action until current admission is restored. ORCH+ never attests SPAWN recovery, replaces ownership, repeats an approval or relaunches a worker automatically.

Operator attestation is labelled as such. Tern's `UiEvent` and button APIs do not authenticate a human or isolate a same-user caller; nonces correlate aliases and are not credentials.

## Authority and persistence

- One host-module registry owns the `authority_state` KV value; windows never write authority. Saved block data holds only view/registration/alias binding and prior-initialization evidence.
- A reducer builds a candidate; only a successful `tern.kv.set` publishes it. Failed admission, release or recovery leaves ownership intact with an error. Repeated input can report only still-current matching state or live evidence, not reconstruct a completed request's original result. Captured authority and immutable effect content remain fenced; a refused request is never silently retried.
- Native admission/reconciliation keeps its exact captured revision while SPAWN authorizes it. A pending control takes priority over new automatic mutations and unissued claims; already-issued effects and all original timers continue. Automatic reconciliation waits for a readable native receiver before occupying the control lane. An intervening commit still invalidates the captured proof; read-only recovery never refreshes or replays that control.
- An already captured ruling write preparation also takes priority over new automatic reconciliation and unissued work until it starts its one-shot edit or is refused. Existing controls, issued effects and timers still advance; any intervening real authority change still refuses the captured preparation. Neither the operator attestation nor the write is automatically repeated.
- The original local writer keeps its five-second read-only observation cadence after an exactly correlated `stale_revision` refusal of a post-write read. Each observation is a new read intent, not a refreshed or resubmitted envelope. Preparation/edit is never repeated; remote or ended-writer attestations are not reused. Silence does not trigger this recovery. Concurrent document edits remain `needs_review` without automatic repair.
- Authority-bearing native owner pickers and prompts retain priority over new background mutations only while their captured authority remains current: work sources, configuration, worker confirmations, document association and explicit recovery choices use the same lifecycle. Completion/cancellation releases that priority. A real intervening commit or lost origin releases obsolete priority without refreshing the input or dropping its callback: the existing stale/origin refusal still runs. Existing effects and host timers continue throughout.
- Plan import excludes only the well-formed canonical ruling block and its own leading separator from `plan_revision`. Earlier routine Progress edits are accepted by fresh B0/B1 ruling verification, not by comparing with the older imported hash. Ordinary Progress or executable-content edits still follow existing re-import/invalidation semantics; recording a ruling does not replace those rules.
- Every write first checks that persisted authority still equals the committed value (exact saved JSON text first, deep compare only on difference). Removed, unreadable or changed storage freezes changes. Refusals, exact replays and no-ops never write. The 1 s workflow tick clones the registry only when derived health or due flags changed. Host events render controller blocks only when committed authority or store status changed; otherwise only the originating block, and only on a visible change.
- Sequenced observations (`observation_seq`) and polls retain no completed-command history: the `command_seq` barrier and per-worker observation cursor fence older input. An observation repeating persisted native state commits nothing until `stale_ms/4` old, except on a state or delivery-error change, busy/erroring evidence with a pending wake, a recheckable native-input gate, exit or restored-coordinator evidence. Current effect/grant and native-result delivery evidence remain while unsettled or unacknowledged. Proven request floors, consumer retirement and confirmed scoped closure reclaim settled markers; old requests remain non-executable without a completed-result or retired-owner history. Missing historical output never proves that an effect did not run.
- A native-only idle poll commits nothing (`mailbox_idle`) when nothing is due (publication, acceptance, compaction, decision, wake, stop/retirement, requested report, rollover, assembly, held report), the last read of the next slot was empty, the poll follows persisted idle evidence under `stale_ms/4` old and, for a watermark poll, every receipt is compacted. An unobserved working blip therefore delays a report by at most about `stale_ms/4 + poll_ms`. Workers with `worker-poll-v1` never use this suppression: their helper can publish a report while the terminal still looks idle, so their configured discovery cadence remains active.
- Automatic discovery alternates cumulative-watermark and report reads while committed receipts remain unconfirmed; fully confirmed prefixes use report discovery only. Known publication/acceptance/compaction continuation keeps priority, held reports still block automatic reads, and `poll_ms` is unchanged. Watermark evidence must still match the retained receipt chain before any prefix is reclaimed.
- The window re-sends a claim for a still-`ready` action after 1/2/4/8 s of awake backoff and replays a captured SPAWN outcome awaiting receipt after 1/2/4/8/15 s. A delivered outcome is marked `lost` after 5 min of awake time with no host progress, or 15 min total. A duplicate claim refused because this window's own claim won does not hold the action.
- Encoded authority is capped at 8 MiB; the last 512 KiB is reserved for completing coordinator bindings, retirement/recovery and genuine safety facts. Registration, admission and generic uncertainty stop at 7.5 MiB. The live dispatch-action ledger is capped at 4,096, with ordinary queue/catalog work held at 3,072 to preserve settlement room. These are current-state bounds, not lifetime completed-outcome counters. At most 64 logical sessions are retained concurrently; confirmed closure removes a session and its settled scoped state so later registrations can use that capacity. Completed owners are represented by generation floors, not history rows.
- Inside the authority-byte reserve, settlements run one at a time across sessions: while any recovery intent is current, other retirement, release and recovery requests are refused `settlement_pending` naming the holder. Confirm the intent in the view that began it, or reload the host (restore withdraws pending intents). A genuinely new safety observation supersedes it.
- If a fresh observation or uncertainty fact cannot persist, later release/recovery is blocked behind a visible safety fence until storage is repaired and the host restarted; a failed observation is never evidence of quiescence.
- Restore validates the complete schema, keeps occupied owners uncertain, fences old recovery intents and persists the new execution epoch before exposing authority. Missing established storage, malformed JSON or invalid state require backup restoration and **Recheck restored store**. Schema-1 state is quarantined unchanged; there is no automatic reset.
- First-use initialization (**Initialize first-use authority…**) assumes a fresh ORCH+ and SPAWN pair. Existing stores require matching authority namespaces, paired compatibility and monotonic admission/request floors. Store loss is not evidence that an old effect stopped or never ran. Preserve both sides and restore the appropriate backups or use the explicit paired migration path; never re-initialize one side alone or manufacture replacement counters to bypass the peer's fences.
- **Forget this orchestration…** (Orchestration menu, and at the top of the panel when blocked or pending) is the one explicit owner action that discards a saved orchestration, including its unfinished logical obligations, instead of restoring it. It never closes a pane, stops an agent or revokes an approval, and it never observes panes or processes. Opening it asks SPAWN, over the dedicated opt-in `discard_capability`, `discard_preview` and `discard_session` operations (their own `SPAWN_FORGET v1` protocol in the shared codec, whose requests, responses and capability all carry the required `spawn-work-v1` discriminator; a peer without it is refused before any intent persists, and legacy operations are unchanged), for a read-only preview: no fence, no revoked permit, no acknowledged request, and none of the reload recovery writes. SPAWN inventories only its own execution obligations for that session (requests, workers, wakes, mailbox generations, linked Authority reservations, outstanding helper invocations). Claimed or launching operations, consumed authorizations without a settled result, pending reservation, mailbox or publication effects, uncertain outcomes and unmatched reservations are blockers; settled launches, acknowledged publications and retained agent bindings are not. Agents that may still be running appear as informational participants (deduplicated, at most eight rows plus an exact count of the rest) and never block; the residual notice that Forget neither stops them nor revokes their authority is shown after them and is part of the confirmation. The host forwards a discard only when its bytes equal the request the authority persisted, and stamps the relay with their sha256 for SPAWN to check. Blocked previews show an exact count of omitted blockers (`{count} additional blockers.`) and are never ready. Only a ready preview enables the confirmation, bound to the session/admission, owner, SPAWN boot and observed dispatch revision. Confirming atomically persists the intent (discard flag, retained origin, attempt id, exact request bytes) and fences the session; there is no cancel. A challenge is bound to both namespaces, session/admission, retained owner identity (without its window epoch), SPAWN boot and attempt id; only the latest per identity counts and a SPAWN reload invalidates it. SPAWN then persists a durable fence and a reservation cleanup journal under the session (no new admission, native begin or delayed continuation starts; settlement recording continues), removes exactly the journaled managed Authority reservations, and only then deletes that session's graph and journal together; roster, other sessions, watermarks and physical mailbox files stay. A crash or reload leaves the session selectable and fenced: **Continue forgetting** obtains a fresh challenge and atomically replaces the pending request bytes from the re-verified current controller. Completion is one ORCH+ commit that reclaims the graph, removes the session, advances `next_admission_seq` above SPAWN's returned cursor and stores a bounded installation-level notice; views are then normalized against the loaded authority.
- **Manual reset** is the last resort. Resetting ORCH+ removes all its saved orchestrations. Resetting SPAWN also removes its saved agent roster and dispatch state. Resetting either plugin does not prove that existing agents have stopped, and uninstalling alone never stops existing execution.
- KV durability is the native store's guarantee, not fsync/power-loss. One active native host worker per plugin data directory is assumed.

Coordinator reservation, its immutable task/work/enrolment and the first provisioning intent commit together. Provisioning must return a complete mailbox contract before the launch intent exists. Worker pane aliases bind only through the correlated SPAWN outcome.

## Dispatch and mailbox contract

`dispatch.luau` is a pure extension of `state.luau`. Host events use `kind="dispatch"` for catalog/queue, USAGE `capacity` evidence, `cancel_work`, effect claims/results (a routed launch `claim` carries `capacity_validation`), polling, report requests, observation, policy/pause/resume, owner decisions, `finish`, coordinator `retire`, continuation, work sources (`plan_import`, `board_intake`, `inbox_intake`, `template_start`) and owner landing/deploy controls. Every intent needs an origin-scoped monotonic `command_seq`; `claim`, `result` and `lost` forbid it and are bound to exact grants. A durable highwater rejects old intents after settled-command history is reclaimed. External direct `intake` is rejected; reports arrive only as correlated SPAWN mailbox pages.

Before an effect the host commits the exact request and an exclusive executor claim. The window checks the controller alias, registration, native session, host and window incarnation before and after async boundaries; callbacks receive fresh contexts. Grants use native nodes `main.dispatch-state` (`orchplus.dispatch`) and `main.dispatch-request` (`orchplus.request`, exact bounded request JSON). Every projected claim, including per-action `main.dispatch-action-<id>` nodes, is exactly `{executor,epoch,grant_id}`; `claim.capacity` stays on the durable host claim. Newly queued work never replaces an outstanding claimed action in the machine nodes.

Each attempt has a persisted `claim.grant_id`. Result callbacks use `act="dispatch-result/<grant_id>/<execution_window_epoch>"` with the raw frame as `value`. Delayed callbacks cannot settle a successor attempt. Only a SPAWN `full` carrying `retryable=true, effect_started=false` authorizes an exact-request retry under a fresh grant; other ambiguous writes stay occupied. Such backpressure is rechecked after 5 s of awake time through the **Recheck unexecuted capacity refusal** path, one per lane, at most 120 times. A claim refused `full` before any grant stays `ready` and is retried every 5 s of awake time, at most 120 times, then held for **Run queued … in its original window**. Every `full` must carry `resource` (≤96 bytes), `current` (≥0) and `limit` (>0); `retryable`/`effect_started` occur together.

The window retains an observed SPAWN outcome until `main.dispatch-state.receipt` names the committed `action_id`, `grant_id` and `response_sha256`; until then it may replay only that observation. Observation IDs are deterministic. This UI receipt is separate from worker ACKs.

**Host sleep.** The 30 s effect deadline and receipt-replay deadline count awake time: the 500 ms observation timer counts a gap over 5 s as one tick, so suspension extends deadlines and never shortens them or retries an effect. SPAWN's adapter applies the same rule to helper `process.run` timeouts; a child killed by the runtime across a suspension still settles uncertain. SPAWN's authorization challenge keeps its 30 s host-clock window; one that expires during sleep is refused definitively; queue the work again.

**Idle-wake helper.** Tern 0.9.12 does not wake an untouched window when a window `tern.timer` comes due. The window runs plugin timers only after something else wakes it: input, a control request, a rendered block frame or a finished child process. Without help, an untouched controller window therefore stops observing and dispatching. Under Xvfb this stall lasted minutes; host timers are unaffected. This is a Tern bug, and the helper is a workaround for it.

While the window drives an *active* controller that has timed work, it keeps exactly one short wait child in flight. Timed work means any of:

- a registered worker, whose observation and poll run every `poll_ms`;
- an effect driver;
- a capacity or backpressure backoff;
- a USAGE read;
- an owner-started recovery or withdrawal read.

Inbox or board polling this window performs counts as timed work, so a controller with only an intake inbox or board configured keeps the helper running (Health: **Idle-wake helper active: polling the intake inbox** / **the board** / **the intake inbox and board**). A remote host's inbox, or an unconfirmed remote board, does not.

The child is `sleep 2`, or `ping -n 3 127.0.0.1` on Windows; both are argv-only with no shell. It does nothing: its exit wakes the window, every due timer runs, and its callback starts the next child. The 2 s interval stays under the 5 s suspension gap, so an untouched window is not counted as suspended.

The helper does not run in these cases:

- the controller has no such work;
- the controller is awaiting continuation;
- the window drives no controller;
- the VM is a host VM (native tests).

A child that fails or exits early stops the helper for that window VM. Where `tern.process` is unavailable (iOS), the helper does not run at all.

The controller's Health card shows **Idle-wake helper active: …** with its reason, or **Idle-wake helper unavailable: …**. Covered by `health/idle_wake`.

**Automatic read-only reconciliation.** An uncertain action with its exact claim receives at most four `status` reads, after 2, 10, 30 and 60 seconds of awake time. Definitive outcomes settle; pending, missing or uncertain mutating outcomes stay held. Reads never claim, resubmit or relaunch. The ordinary UI explains the unresolved start and offers a safe status check; exceptional reconciliation remains under Advanced. Renewed observation preserves the same original claim, origin and used readback allowance. It cannot resume paused work or create another startup. Up to sixteen uncertain actions are tracked, one read per lane.

**Retained uncertain reads.** A read-only operation (`mailbox_read`, `catalog`) changes nothing until its outcome commits, so an uncertain read is evidence, not a pending effect. SPAWN `missing` for it lets the window send `read_missing` with the exact status bytes (`resolution.evidence="read_lost_no_effect"`, with `status_sha256`); an explicit attested reattachment supersedes it otherwise (`read_superseded`). Either way the read releases its executor counts and the lane re-reads from the durable cursor; a late outcome is stale. Mutating effects (publications, retirement, provisioning, launch, adopt, stop, `native_wake`, `attach_worker`, `accept`) keep strict holds and block reattachment until reconciled.

**Publication readback.** ACK and reply objects are immutable bytes. After one non-definitive automatic read the window sends `readback_publication` (≤3 per publication; owner control **Read back and re-publish the exact same bytes**). On the worker's continued route, while the receipt or reply part is outstanding and unconfirmed, the host resolves the attempt (`publication_readback`) and re-issues the same bytes; SPAWN reads back first and republishes only if absent (`already_published` otherwise).

**Effect slots.** At most four host actions may be claimed or uncertain at once; uncertain read-only operations do not count (they have no effect a new one could conflict with), claimed reads do, and an uncertain read still holds its worker generation. SPAWN's own limits (four per host, one per mailbox generation) apply independently.

**Window bookkeeping.** Per-action markers (set-before-send grants, reconciliation attempts, holds) are pruned only on positive evidence from the action's own surface (`complete`/`resolved`, or a different current claim), one action per tick. Readback counts and issued request IDs age out after 512. State for vanished workers is dropped.

Explicit operator commands use the `dispatch-operator-command` UI action; drivers use `dispatch-command`. The `command_result` projection keeps a failed operator command, bound to its `request_id`, until acknowledged or superseded.

**Pane-free transport.** Logical SPAWN lanes are bound through the ORCH+ host relay, not native `spawn.dispatch` panes. The window sends `spawn_relay` actions containing exact request bytes plus `source_nonce`, `relay_endpoint`, `relay_boot`, `lane_id` and `peer_boot`; host-projected `spawn-relay-<lane>-<kind>` nodes provide bounded response/current/catalog bytes and message proof. Endpoint, controller nonce, host pane, lane binding and peer incarnation are checked across reads. Payload `SPAWN_DISPATCH v1` length/digest and dispatch authorization remain independent checks. Status addresses retained request IDs; only the original execution context may replay the immutable request for an oversized retained outcome.

Carrier ACKs name `{route,id,incarnation}` and are not dispatch-result receipts, worker ACKs or proof of execution. Idle lane release requires the exact positive peer release receipt before cached endpoints are dropped; uncertain release never means managed work stopped. Reconnect preserves outstanding routes/evidence and holds unissued mutating actions rather than replaying them. Legacy carrier panes are considered only for positively proved inert closure, never reused as transport. Local and remote use this same pane-free mechanism through Tern; there is no parked transport tab, split or deck chip.

A successful durable `control_observed` may retire an older connection-control response using one bounded proof record on its live lane. The response must decode against the exact control captured before settlement, come from the same SPAWN incarnation, and have a strictly earlier producer sequence than the committed settling response. Failed saves, unreadable or diverged authority, unrelated requests and later responses remain held. This proof expires with lane release or host reload; revision/serial high-water marks do not reconstruct it. It acknowledges obsolete transport evidence, not a worker outcome or permission to repeat a launch.

**Report intake.** The host accepts complete `report-files-v1` pages and validates ACCEPTED, REGISTER, `reply_ack`, READY/HEARTBEAT/WAITING/BLOCKED, ASK, CHECKPOINT, CHECKOUT, CHECK_RESULT, REVIEW_READY, REVIEW_RESULT, LABEL, DONE (`output_ref?`), ROLLOVER_REQUEST, LANDING_REQUEST, LANDING_RESULT, DEPLOY_RESULT, COORDINATOR_PROPOSAL and negotiated COORDINATOR_RELEASE. Reports are data, not lifecycle grants. Cursor, ACK bytes/receipt chain, semantic state and the SPAWN accept outbox commit atomically before publication. Only a cumulative watermark permits compaction; only the matching `reply_ack` settles a reply. Transport `full`/`incomplete` never demotes a worker: an unadmittable read records backpressure without receipt, cursor or ACK. A semantically rejected report settles the read grant and is **held** with its exact bytes and diagnostic; that generation's report lane stops automatic reads and requests (outbound settlement still polls). **Re-check held report…** re-decodes the same retained bytes with current validation; valid bytes enter normal intake, nothing is skipped or substituted.

**Wakes.** ACK/reply publication is separate from native wake. Only `wake_status="awaiting_window"` with `wake_effect_started=false` and canonical `wake_target_request_id`/`wake_target_action_id` establishes an unstarted notification; ORCH+ settles publication and later grants a separate `native_wake` when the worker is safely idle. Busy and waiting-input workers are not interrupted; started/uncertain wakes occupy execution limits and never repeat.

Threads retain assignments, reports, questions, answers and delivery states. Health keeps native state, reported state, progress, freshness and gates separate; READY cannot override a native prompt or exit. Clock epochs stop restored timestamps counting as fresh. There is no screen parsing, transcript reading or raw terminal typing.

## Work sources (plans, board, inbox, templates)

The orchestration/project menus offer native plan-file, board and template entry. WORK ON is shown only with Glitch integration and its own switch enabled, and opens WORK's selection pane. Sources belong to a project and are held for START by default. Plan-board synchronization is presentation, not execution approval. Plan/inbox bytes are read on the execution host; the desktop window reads and writes its board.

- **`plan_import {path}`** reads at most 1 MiB and normalizes Checkpoint/CP/C headings, named tasks and supported file-action tasks with child steps/checks. Parser errors remain explicit. Imports preserve semantic task identity across unchanged content and checkpoint renumbering; old immutable reports/work links are never rebound to a different task. A same-path/revision import is unchanged. Ambiguous or changed managed tasks remain held. Checkpoint joins and independent/sequential dependencies still govern scheduling through the preferred worker or explicit allowed agent, not a mandatory build/class route.
- **`board_intake {board_path,card_id,text,tags,text_sha256}`** and **`inbox_intake {name,content_sha256}`** retain their exact digest-based deduplication and project association. Generated plan cards are mirrors, not another executable intake. Class tags/metadata do not require a classifier or select an agent. Inbox files are archived only after acceptance; unsupported remote polling is not silently redirected to the desktop.
- **`template_start {template_id,source_revision,input,custom_fields?,orch_project_id}`** validates the displayed template revision and shared 2048-byte input limit. Each template uses its own defaults; only explicit custom-field overrides carry through a chain. DONE with the required output advances to the next template, subject to the existing eight-step bound, START/pause and loop controls.

The window reads `workflow-intake`: `workflow.intakes` (newest 64, including `orch_project_id`, `held`, identity, state, worker/work links, refusal, hold, lane and label), `workflow.board = {path, cards[{card_id, intake_id, lane}]}`, `workflow.plans` and `workflow.chains`. Desired board lanes `queued|running|review|done` map to `board_lanes` titles and are applied by `cx.board:move`; the window is the only board writer. Desktop `cx.board` has no change events, so board and inbox are polled. On a remote host connection the board path is the desktop's and requires explicit confirmation; inbox polling runs only when the observing window is on the execution host.

Normal plan presentation groups work by project and logical checkpoints/features in ORCHESTRATED WORK, with child conversations; it is not an eight-row diagnostic card pager. Durable plan IDs, revisions, checkpoint/task states, flags, worker links and holds remain available to protocol projections and Advanced inspection.

## Source identity and live native boards

On first use the native ORCH+ Board uses fixed Plans/Todo/Doing/Review/Done lanes without setup mappings. Projection includes checkpoints, tasks, file actions, steps and explicit validation/checklist completion; it never mines Progress prose for invented completion. Stable source/card identities preserve managed work and human edits. A progress-only source revision does not force card edits or create duplicate intake.

Native card text is a single line: a short human title, meaningful parent/description and a **Source plan** reference. Current Tern card clicks select the card rather than activating its Markdown reference; use the real **Open plan** button beside the plan title in ORCH+. That button resolves the current plan under its controller/project scope and opens the execution-host file, never a desktop-path fallback. The canonical `tern://orchplus-plan` URL carries `scope`, execution-host `path`, hashed desktop `board`, `projection=2`, stable `node`, `kind`, description `base`, source `rev`, explicit `done` and `retired`; these machine fields are not visible hash tags or diagnostic body text. Supported URL routing validates its retained source capability, current origin, owning scope and the actual native board. Native text-only writes preserve inline source hashtags and human suffix tags; the separate `tags` setter would remove and relocate body hashtags. Readback verifies the exact human prefix against the URL's baseline before replacement. Legacy hash-footer cards and the previous generated label migrate only with their original baseline proof; changed human text or malformed projection addresses remain conflicts, never new executable intake. Native card/lane IDs are opaque, may contain the full escaped board path, and use a path-derived bound rather than a short label limit.

The window records a bounded exact board-write batch before issuing native effects. Only its matching positive callback settles it. A lost callback or reload retains uncertainty; read-only inspection does not attest that an old writer ended or authorize the same batch again. Existing unrelated boards/cards remain untouched. Creating a separate board is an explicit alternative, not silent recovery.

Current task types are optional metadata. Legacy LABEL reports and outstanding classifier work remain settleable, but no new labeller task or static class route is created.

## Ordinary worker finish and retention

**Finish ordinary worker…** is explicit; DONE never stops a pane. Unresolved gates, deliveries, report requests, wakes, claims or pinned review/rollover/landing/deploy evidence prevent finish. After settlement the exact native stop and mailbox retirement must complete before capacity is reclaimed; a failed or uncertain stop/retirement stays held.

SPAWN's one definite pre-effect retirement refusal is `producer_unsettled` (the helper journal still holds pending reports or unresolved control messages; nothing was removed). ORCH+ settles it as `retirement_refused`: the action completes, the worker is not held, the mailbox stays provisioned. Only the nightly sweep or **Retry mailbox retirement once…** issues one fresh grant.

When Finish is refused — by the window's pre-check (held or unaccepted phase, reattach needed, another control route, an unsettled effect, a pending report request or a rejected report) or by the host — a notice names the reason and nothing is stopped. After SPAWN refuses a retirement before any effect, Finish offers **Retry mailbox retirement once…** and sends it.

Only fully retired, unreferenced generations and safely settled generic gates are reclaimable. Report cursors and identity/intent fences survive history eviction, so a pruned ASK cannot recreate work.

## Verified worker rollover

**Roll over worker…** requests an explicit handover. Automatic rollover additionally requires an accepted, continued, non-excluded ordinary worker with reliable current context at its configured threshold and a completed-work CHECKPOINT at or after that threshold was reached. Policy `rollover_threshold_pct=0` selects `current >= first_turn + ceil(55 * (window - first_turn) / 100)`; values 1–99 are explicit whole-window percentages. Integer-safe arithmetic preserves the exact boundary. The reducer rechecks idle state and all outstanding-control/effect gates; a trigger only requests a handover checkpoint. Each rollover is recorded in `dispatch.rollovers`, bound to work, predecessor/successor panes, a 64-hex handover token and controller owner/generation, with revisioned history:

`requested → checkpoint_pending → checkpoint_verified → successor_granted → successor_created → handover_accepted → predecessor_stop_requested → predecessor_closed → complete` (or `cancelled`).

- **Checkpoint.** One `report_request` with `requested_kind="CHECKPOINT"` once idle. The CHECKPOINT echoing it must state completed/remaining work with at least one check, all `passed` and fresh for its `artifact_revision`; otherwise it blocks (`verification_failed`, …) and may be requested again, up to `loop_cap`. Results are **worker-attested**; nothing is executed.
- **Successor.** A new worker on the predecessor's record/revision, cwd and placement if still current and eligible (or a routed alternative), role and declared work facts carried over, assignment = the checkpoint payload **without predecessor context measurements**. The predecessor's immutable checkpoint remains unchanged. `mailbox_provision` → `launch` (`fresh=true`) carries `{worker_id, worker_generation, enrolment_token, assignment_sha256, handover_id, handover_token}`; the provision carries `handover_id` and `handover_sha256` = SHA-256(`handover_id:handover_token`), never the token. Over-bound handovers hold `input_too_large`.
- **Acceptance.** The successor's ACCEPTED and SPAWN `accept` carry the handover pair. Only after SPAWN records acceptance *and* a fresh observation shows the successor alive does ORCH+ set the predecessor's finish intent; `complete` needs SPAWN's stopped outcome with `absent`/`exited`.
- **Failures** hold with the phase and a reason; the predecessor lives until successor acceptance. Uncertain launch, accept or stop is never retried. A different controller generation cannot advance a rollover; after reload nothing advances until continuation, and a changed window incarnation fences a never-claimed successor grant (`successor_launch_fenced`). An issued landing grant never transfers to a successor; a builder's ungranted landing item is held during its rollover.

ROLLOVER_REQUEST is evidence only. Native daemon resume of a conversation is not a rollover.

## Verified coordinator rollover

**Roll over coordinator…**, or the policy trigger when `auto_rollover` and `rollover_include_coordinator` are on, uses the same measured-headroom or numeric threshold. It does not wait for a completed project checkpoint, but still requires the running owner with acknowledged activation, a settled idle point, no retirement, no other coordinator rollover and no restored-coordinator hold. Two coordinators **never overlap** (`kind="coordinator"`, `closure` `observed` or `operator_attested`):

`requested → checkpoint_pending → checkpoint_verified → retirement_requested → predecessor_released → predecessor_stop_requested → predecessor_closed → owner_retired → successor_granted → successor_created → handover_accepted → complete`.

- The verified checkpoint quiesces the predecessor through the typed `coordinator_retirement` reply; its COORDINATOR_RELEASE, final watermark, exact stop and mailbox retirement run through the normal finish path while the slot stays occupied. Cancellation only before retirement is requested.
- After the stopped outcome and generation-bound release, one commit reserves the successor's slot and queues its provisioning; unrelated coordinator starts are refused `rollover_reserved`. The successor carries the paired owner/generation and handover; its activation token derives from the handover; `complete` needs the durable activation `reply_ack`.
- An uncertain or refused predecessor stop holds with the checkpoint retained; resolution is operator-assisted orchestrator recovery, whose retirement records `closure="operator_attested"` and lets the handover proceed.
- A coordinator releasing itself before a verified checkpoint closes the rollover `cancelled` (`predecessor_self_released`). While the rollover's CHECKPOINT request is outstanding, release is refused (held as a rejected report on the mailbox path).
- A stopped coordinator pane observed alive again is `restored` evidence: every coordinator claim, proposal and the rollover hold until an exited observation or **I stopped this restored pane**.
- From `owner_retired` on, the rollover cannot be cancelled. If the successor fails to launch, exits, is held or has a held report before accepting (`successor_launch_failed`, `successor_launch_uncertain`, `successor_launch_fenced`, `successor_unaccepted`, `successor_report_held`), the hold says no coordinator is active and shows SPAWN's diagnostic. Stop the successor pane if it exists, reconcile retained effects, then run fenced recovery on the successor's orchestrator owner card; that closes the rollover `cancelled` (`successor_owner_recovered`) and frees the slot for an explicit start from the retained checkpoint.

## Advanced explicit verified attach

An idle, ticked hand-opened agent pane row in Config offers **Attach pane N as ORCH+ worker…** once a catalog is loaded: pick an eligible, enabled `native-agent` record with `report-files-v1`, type the assignment and attest the exact window-scoped pane. The window re-verifies the pane just before sending (this session/host, recognized native agent, idle, unbound). The `adopt` command re-checks attestation (`operator_verified_exact_agent_pane`), scope (`invalid_task`), catalog (`catalog_changed`), record (`unsupported_capability`), pause, capacity and `pane_bound`, then creates a first generation with `adopt_pane_binding` and queues the ordinary `mailbox_provision`; the launch slot carries a SPAWN `adopt` request with the same immutable enrolment (no handover or coordinator pair) plus `pane_binding` and `attestation`. SPAWN delivers its preface and the assignment once via `agents:ask`. A pane that is busy or out of scope at execution is refused `target_unavailable` and held; a lost ask is `uncertain` and never repeated. Afterwards the worker is identical to a launched one. Coordinators cannot be adopted.

## Landing queue and release manager

Landing coordination uses the **verified canonical repository common-directory, execution host and canonical target ref**, across logical sessions in one authority/data directory. The owner declares `repository_queue` when an existing protected repository route supplies serialization; ORCH issues the normal authorized release grant without a competing local slot. Otherwise `orch_queue` supplies one shared slot for that repository/target and releasing it advances eligible work across sessions. This is not a distributed lock across independent authorities. ORCH+ never runs git or infers landing from REVIEW_READY, DONE, idle or a closed pane. **Builders never merge:** the session's release manager receives the grant and reports the repository operation.

State is `dispatch.landing = {queues, items}`. Persistent session/project partitions retain their FIFO `order`, granted `slot` and last recorded `head` (`{revision, source=landed|stale_target|owner, landing_id}`); repository coordination groups those partitions by the verified shared identity. An item binds work, requester builder (`worker_id`), grant `holder`, the exact request `{project_id, repo_ref, target_ref, target_revision, source_ref, source_revision, checkpoint_id}`, approval gate, `proof`, history and up to eight grants. Statuses: `queued|ready`, `verifying`, `blocked`, `granted`, `landing`, `landed`, `failed`, `cancelled`.

- **Request.** The builder's LANDING_REQUEST references a retained checkpoint of the same project whose `artifact_revision` is the source revision and opens a `landing_approval` gate. Approval: the owner's answer, an approved coordinator `landing` proposal, or the in-scope policy answer (see [Autonomy](#autonomy-inside-plan-scope)). Reject or cancel withdraws the item.
- **Release manager.** When an item needs a grant, ORCH+ queues (or reuses) one live `release_manager` worker on `release_manager_record` that passes the signer rule. Its record must carry `release-manager-v1`.
- **Grant.** `orch_queue` requires the shared repository/target slot to be free and selects eligible queued work across sessions; `repository_queue` delegates serialization without claiming that slot. Both require the item's approval, complete proof and signer, an accepted continued builder outside a rollover, no BLOCKED report, no pause or reserve, and a fresh latest checkpoint for the source revision. The immutable `landing_grant {landing_id, grant_id, project_id, checkpoint_id, repo_ref, target_ref, target_revision, source_ref, source_revision, builder_work_id, review_id, reviewer_family, proof}` goes to the release manager, which becomes the item's `holder`. A request whose expected head differs from the recorded head is `target_moved`. Eight grants per item is a structural bound (`attempts_exhausted`).
- **Refresh.** A `target_moved` item, or a `stale_target` result, sends the builder generation exactly one `landing_refresh {landing_id, project_id, repo_ref, target_ref, expected_revision, current_revision, reason}` through the reply outbox, keyed by generation and both heads so replays never duplicate it; a further move sends one notice for the new head. A full outbox, the settlement reserve or a generation that cannot receive replies keeps the hold visible with a deferral note. The builder's fresh CHECKPOINT, review and LANDING_REQUEST rebind the item at its position and void the approval; refresh cycles count against `loop_cap` (`loop:landing_refresh`).
- **Result.** Only the holder's LANDING_RESULT correlated to the grant's action counts; a builder's is refused. An ordered `landed` result records `result_revision` as head, releases any local slot and owes a deploy; `rejected` fails the item; an ordered `stale_target` records the observed head, releases any local slot and keeps the item as `refresh_required`. An automatic observation can advance a recorded head only from the grant's immutable expected head, or agree with the already recorded revision; an absent head can be initialized. Equal observations do not overwrite provenance.
- **Unordered results.** A delayed external-queue report that conflicts with the current shared head is retained as `late_result`, with `repository_head_unordered` uncertainty instead of terminal settlement or deployment. Current unresolved grants derive a repository-wide hold before refresh processing. This does not infer Git ancestry or remote freshness. An explicitly reconciled historical grant no longer contributes that hold.
- **Uncertainty and reconciliation.** An `uncertain` result, holder DONE without a result, a lost holder (exit/stop, held generation, rejected report) or **Result lost — hold slot…** retains any local slot and never transfers its grant to a successor. **Reconcile observed outcome…** records a read-only owner inspection, attestation and reason. A conflicted landed reconciliation requires both `target_revision` (this landing's result) and `current_target_revision` (the separately observed current head); a conflicted not-landed reconciliation requires the observed head in `target_revision`. The resulting deploy uses this landing's `target_revision`, never a later unrelated current head. A later worker result is evidence only. Deploy reconciliation rejects these landing-only head fields.
- **Owner controls.** **Landing queue** cards show head, slot, builder, reviewer family, release manager, holds, grants and deploy status. While an item needs a refresh (`refresh_required`, or an approved item holding `target_moved`), its row reads "approval void — awaiting fresh review/request" instead of "owner approved". **Move up/down** and **Cancel…** apply only to ungranted items.

**Deploy.** A `landed` item owes one durable deploy in `dispatch.deploys`: `pending → granted → deployed | not_applicable | held | failed | uncertain | stopped`. ORCH+ issues the release manager one `deploy_grant {deploy_id, attempt_id, landing_id, revision, target_ref}`; its DEPLOY_RESULT `{deploy_id, attempt_id, landing_id, outcome: deployed|held|not_applicable|failed, revision, evidence, reason?}` must correlate to that grant. `held` and `failed` open a `deploy_hold` gate relayed to the release manager as an `owner_decision`: after `held`, **deploy** continues the same attempt and **stop** ends it; after `failed`, **retry** issues a new `deploy_grant` (new attempt, same deploy and revision), capped by `loop_cap` (`loop:deploy_attempts`). DONE while holding a grant, or **Deploy result lost — hold…**, makes it uncertain until **Reconcile** records `deployed` or `not_deployed`. Nothing is re-granted automatically.

**Upgrade from 0.3.0** (restore only). 0.3.0 grants were addressed to builders. A `granted`/`landing` item whose current grant is such a legacy grant becomes an uncertain hold `legacy_grant_outstanding` with one owner gate; only **Result lost** or **Reconcile** settles it, the grant is never re-addressed and a builder LANDING_RESULT is refused. Approved but ungranted items keep their approval and re-verify under the proof rule. Coordinator review results from 0.3.0 carry no proof and are dropped.

## Normal coordinator finish and retirement

Coordinator start needs a record configured **and provisioned** with `coordinator-control-v1` plus report-files and a wake/poll capability; nothing is marked supported automatically. The launch enrolment carries the reserved coordinator owner ID/generation only for coordinator work; SPAWN's preface tells it to ACCEPT, then wait for and claim typed activation. After ACCEPTED, ACK and SPAWN acceptance ORCH+ issues one `coordinator_activation` reply. The coordinator self-finishes with authenticated COORDINATOR_RELEASE, or **Request graceful coordinator retirement** commits one `coordinator_retirement` reply (`retire`). Both need activation's durable receipt; neither is a stop.

Activation, retirement, quiescence, reply floors, native stop and mailbox retirement remain observable under Advanced. Normal drivers advance outboxes, report discovery and cumulative receipt settlement automatically; **Read / settle** and **Read cumulative receipt watermark** are exceptional diagnostic controls. The final watermark must cover release and every reply acknowledgement before SPAWN receives one exact `stop`; only durable `stopped` with the issued pane binding and `absent`/`exited` permits `mailbox_retire mode=retire`. Generation-bound release clears exactly that slot and preserves fences; an old release cannot clear a successor. Uncertain stop/retirement, failed commits and restored freshness keep ownership occupied. Earlier coordinators without issued activation remain occupied for inspected recovery. Native stop does not prove every remote descendant exited.
