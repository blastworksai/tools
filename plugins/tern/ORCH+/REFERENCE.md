# ORCH+ protocol reference

This is the detailed contract behind [ORCH+](README.md): storage, dispatch, mailbox, rollover, landing and recovery rules. The README covers everyday use. The agent-facing contracts are [worker-brief.md](worker-brief.md) and [coordinator-brief.md](coordinator-brief.md).

Every control named here is a native button in the ORCH+ controller or Config page, except the two palette commands **ORCH+ Continue controller in this window** and **ORCH+ Reload recovery guide** (see **Guided reload recovery** under [Dispatch and mailbox contract](#dispatch-and-mailbox-contract)); there are no `orchplus://` links. Pressing a dispatch or assistance button makes the host publish a bounded one-shot operator intent (`main.operator-intent`, role `orchplus.intent`). The ORCH+ window that owns the controller's origin runs a dispatch intent exactly once; every other window leaves it silently. This includes **Continue controller after reload…** and **Guided reload recovery — next step…**: a host-block click carries no window or client identity, and every client attached to one window key shares that key, its shown session and its focus, so no window can tell that a click came from it. A fresh window incarnation therefore continues only through the palette commands, which Tern runs in the window where they were invoked. Before anything runs, that window re-checks the controller pane, logical session, host and window incarnation, and the host block then re-validates the command. Intents carry no URL size limit, so large **Save session settings** and **Attach pane N as ORCH+ worker…** requests are never dropped. An intent whose confirmation does not reach the host within 30 s expires with a visible notice saying it will not run later. A window may still have run it before its confirmation was lost, so the owner checks the current state before acting again. A button rendered before the last host update is refused as stale rather than replayed.

Assistance buttons (**Inspect**, **Recheck**, **Reveal owner**, **Stop assistance…**) follow the same rule while a live continued origin exists: when the session's command cursor belongs to the active controller owner and generation, the host stamps that origin's window (window key, window incarnation, native session and host) into the intent, and only that window runs it. Limitations: before the controller's first command there is no cursor, so neither dispatch nor assistance intents are fenced to one window, and any ORCH+ window showing the controller in its admitted session may take them. While the controller is restored uncertain (no live origin) assistance stays open to any window showing it, so a recorded owner can still be inspected, rechecked or stopped before continuation. Both cases keep their own pickers and host re-validation.

## Session Config editing

Config is a display mode of the same block: scheduling and effect drivers keep running, and **Open ORCH+ controller** returns to the controller view. With no logical session selected, Config shows the session chooser and asks you to select or register one. Settings are per logical session and stored in the existing host-written session policy (`dispatch.policies`), not another store. The settings, defaults and bounds are listed in the [README](README.md#config-page).

Only the session's admitted active controller can edit. Other views (unbound, duplicate, uncertain) show the same values read-only with the reason; a view that is not the controller offers **Reveal recorded controller pane**. Checkboxes and −/+ buttons edit an unsaved draft in that view; **Save session settings** commits only the changed fields through the `policy` command with the displayed policy as `expected_policy`. If the saved policy changed meanwhile (another save, pause/resume), the reducer refuses with `policy_conflict` and the draft is discarded; nothing is overwritten. With no draft, **Enter value…** opens a prompt for one number and accepts only whole numbers within its bounds.

All values are exposed on the machine-readable `workflow-index` node's `policy`. Policies stored by earlier builds (the five-field, ten-field, sixteen-field pre-sweep and eighteen-field pre-rollover-routing shapes) are accepted only at the restore boundary and migrated with the README defaults; any other shape is rejected. Because the routing-policy digest covers every routing field, decisions recorded before an upgrade are re-evaluated on the next capacity refresh before they can claim.

**Pane orchestration list.** Config lists every agent pane in the current native session on this host, from the window's `cx.agents` observation (at most 64 rows, with an "N more" note; titles are UTF-8-safely truncated and never identity). Rows are ticked by default:

- Managed workers are listed by durable `worker_id`. Unticking adds the worker to `excluded_workers`; automatic progress-report requests and automatic rollover skip it. Observation, mailbox reads, receipts and owner actions continue, and a tick change never stops or retires anything.
- Hand-opened agent panes are window-scoped (pane id, window incarnation, native session and host). Their marks are eligibility only and are not durable: after reload they reappear ticked. Ticking a hand-opened pane never adopts it; orchestrating it requires the separate explicit **Attach pane N as ORCH+ worker…** (see [Explicit verified attach](#explicit-verified-attach)).

Pause/resume remains a separate scheduling control. Pausing holds new work, not committed receipt or decision settlement. Launch records, accounts, models and host configuration remain in **SPAWN Config**; Config cannot submit executable commands or credentials.

**Worker context usage.** Workers may add `context_used_pct` (integer 0–100) to READY and HEARTBEAT when omp shows context usage. Any other value rejects the report. ORCH+ stores the latest value with its report sequence and shows it in worker health as "context N% (worker-reported)".

## Mailbox lifecycle and nightly sweep

Each managed worker generation has one private report mailbox on its execution host, provisioned by SPAWN (`mailbox_provision`) under the configured permitted root before launch. The worker's producer writes reports into it; ORCH+ reads them through SPAWN, publishes exact ACKs and replies back, and the producer confirms ACKs with a cumulative receipt watermark. A confirmed watermark sets `compaction_pending`; the next poll issues `mailbox_retire` with `mode=compact`, which deletes only the confirmed prefix. Retirement (`mode=retire`) happens only after an explicit finish or coordinator release, a settled generation (receipts, replies and notifications drained and confirmed) and an exact native stop observed as `exited` or `absent`. Retirement leaves a small tombstone in SPAWN; the worker record is reclaimed later. Uncertain retirement is never repeated; it is reconciled like any other retained effect.

A mailbox can be orphaned when that last step never ran, for example when the controller was detached after the stop was observed. The nightly sweep handles this in ORCH+ itself, with no OS timer. The window scheduler checks the local wall clock on its normal ticks. The due slot is today's `sweep_time` once it has passed, otherwise yesterday's. When that slot is newer than the session's durable last run, the window sends one `sweep` command with the slot's local date (`catch_up` when it runs more than 15 minutes late). After a missed time (no window attached, host asleep), the next attach or wake therefore runs exactly one catch-up for the latest slot, not one per missed day. The host refuses any date at or before its recorded last run (`sweep_already_ran`), so reloads, duplicate views and concurrent windows never run a day twice. A refused request is retried by the same window only after 10 minutes. A run is one per *scheduled* day: a catch-up for yesterday's slot may be followed later the same calendar day by today's slot.

The rule is deterministic and checked in this order for every worker in the session that has a mailbox:

| State | Decision | Reason code |
| --- | --- | --- |
| Mailbox already retired | nothing | `retired` |
| Control route needs continuation after reload, or belongs to another controller incarnation | keep | `continuation_required` |
| Any uncertain effect for the worker | keep (auto-reconcile handles it) | `uncertain` |
| Retirement already issued and unsettled | keep | `retirement_pending` |
| Any other queued, claimed or backpressured effect | keep | `effect_pending` |
| Coordinator whose owner generation or executors are unresolved | keep | `owner_unresolved` |
| Rejected report held | keep | `report_held` |
| Worker held | keep | `held` |
| Never bound to a launched pane | keep | `unlaunched` |
| Not stopped, `compaction_pending` set | existing compaction queued | `compaction_pending` |
| Not stopped | keep (never stopped by the sweep) | `live`, or `finishing` when finish/release is requested |
| Stopped but not settled | keep | `unsettled` |
| Referenced by active rollover, landing or review work | keep | `referenced` |
| Exact native stop observed, settled, unreferenced | existing `mailbox_retire mode=retire` queued | `stopped_settled` |

Queued retirements and compactions are ordinary actions with the normal claim, grant, deadline and uncertainty rules (including automatic read-only reconciliation). The sweep never stops a worker, never infers a stop and never touches another session. Each run is logged durably in `dispatch.sweeps[session]`: `last_date` plus a ring of the latest 14 runs, each with local date, registry revision, time, catch-up flag, counts and up to 64 per-worker decisions with reason codes. Config (**Mailbox sweep** card) and the controller's workflow card show the last run and every kept or queued worker with a readable reason. Turning the sweep off in Config stops new runs and keeps the log.

## Quota routing (USAGE capacity)

With `quota_routing` on, ORCH+ consumes USAGE's read-only **capacity v1** export (owner-enabled and revocable in USAGE Setup). The window reads only USAGE's public native `usage.capacity` block, opened on the controller's host/session exactly like a SPAWN bridge (in the background **SPAWN bridges** tab, never beside the controller or moved; at most one per controller; after a reload an idle `usage.capacity` pane in that tab is reused, and the bridge sweep closes other idle leftover readers there or beside the controller, never one with a request in flight): it sends `{ev="action", act="usage.capacity"}` with a bounded `snapshot`/`page`/`validate` request and reads only the keyed `usage-capacity-response` node (`USAGE_CAPACITY v1`), correlated by request ID. Every page of one immutable revision is assembled in index order, and the byte length and SHA-256 must equal the declared `size` and `revision` before anything is parsed; ORCH+ accepts documents up to 2 MiB and treats larger or failed assemblies as no evidence. The SHA-256 is incremental: each window tick hashes at most 16 KiB (`quota.HASH_BLOCKS_PER_STEP` blocks) of the pages delivered so far, so no 50 ms window callback hashes the whole document, and `validate` is requested only after the last byte is hashed and parsed. A hashing step interrupted mid-callback (for example by a budget trip) fails the read closed as `hash_interrupted`; a snapshot reader never records evidence without a verified document. Either failure retries on the next automatic refresh (after 30 s) or an explicit refresh. USAGE then `validate`s that revision before the host records it. There is no USAGE private state, provider call, collector or credential access, and no account is discovered or guessed.

**Normalization** (`quota.luau`, per eligible catalog record, at most 24 per evidence set: pending routed records first, then the allowlist, then other eligible records):

- **Binding:** only USAGE's exact join `(scope.spawn_join.namespace, host_key, config_revision, account.id)` = SPAWN catalog `(namespace, host_key, config_revision, record id)` with a `profile_binding`. Labels, `capacity_binding`, equal percentages and pane titles are never identity. A local publication must also agree with USAGE's `current_roster` (definition revision and profile binding).
- **OMP consumers:** a record whose id matches a scope `consumers[].id` with `account_ids = ["<account id>"]` is evaluated against that account in the same scope and publication exactly as a direct match (same join, profile binding, source and freshness rules). A local publication must also find the same consumer in `current_roster` with the same `definition_revision` and `account_ids`, otherwise `local_roster_changed`. A consumer without an association is `consumer_unassociated`: associate OMP records with an account in USAGE Setup.
- **Source:** the publishing source must be `current` with unchanged generation/profile generation and no clock skew.
- **Readings:** every bound reading must exist, carry a canonical ID inside the binding, and have windows with numeric remaining percentages; unavailable or last-known windows carry no routing proof. Duplicate publications use the newest observation per window/pool; equal-time disagreement is a conflict.
- **Result:** `known` with the lowest remaining % across all bound windows (USAGE's `model_mapping` is `unknown`, so every window applies), the oldest observation time, the earliest reset, the earliest weekly (`seven_day`) reset, a binding digest and a principal digest; otherwise `unknown` with a typed reason (`unbound`, `consumer_unassociated`, `ambiguous`, `binding_unverified`, `source_*`, `local_roster_changed`, `reading_missing`, `identity_mismatch`, `unavailable`, `conflict`, `future_timestamp`, `stale`, `reset_passed`, `unit_unknown`, …). The host re-assesses freshness with its own clock: evidence past USAGE's lease, observations older than `quota_max_age_ms`, or a passed reset are **unknown**, never a refill. Missing, stale, revoked or unbound evidence is never "plenty".

**Rule**: for each new task or coordinator start, eligibility (eligible/enabled, same cwd/placement, coordinator capability) and the explicit allowlist come first, then quota (sufficient = fresh, bound and strictly above `quota_reserve_pct`), then owner preference. The record you chose is preferred and launches unchanged when sufficient. Otherwise allowlisted alternatives share one preference rank and are ordered by **earlier weekly reset**, then record ID. An alternative that changes provider, account/profile (any label/profile difference, or a USAGE principal that is unknown or different) or model needs the matching `initial_dispatch_*` permission. The first permitted sufficient alternative is selected; if the best sufficient alternative is not permitted, the work becomes a durable **`quota_fallback` owner gate** naming both exact provider/account/model tuples, the routing-policy digest, USAGE revision, catalog revision and candidate evidence. **Approve** applies to that work only and is refused if the policy, catalog or evidence revision changed or the destination is no longer sufficient; **Reject** keeps it held. With no sufficient allowed record the work is **held** (queued, never provisioned) with its reason; it is re-evaluated whenever fresh evidence arrives (the window refreshes held work about every 30 s), or the owner can **Re-check capacity now** or **Cancel this queued work…**. Each decision is recorded on the worker (`routing`: requested/selected record, authority, candidate reasons, policy and evidence revisions, decision digest, last eight outcomes) and in its durable thread. With `quota_routing` off, dispatch is exactly the record you choose.

**Launch-time reservation:** the decision binds the USAGE revision and authorization revision used. Immediately before claiming the launch, the window asks USAGE to `validate` that exact revision; the claim must carry a `current` result validated within 30 s and unexpired, and the granted claim stores it (`claim.capacity`). A changed, expired, revoked or incomplete revision means refresh: the new evidence re-evaluates the provisioned record (it can only stay or be held — a provisioned record never changes), and nothing launches on stale evidence. Routing-policy edits re-evaluate unlaunched routed work and void stale fallback gates; claims refuse a decision whose routing-policy digest changed. This checks evidence currentness; it is not a provider-side reservation, and other sessions can still consume the same quota.

**Rollover routing**: with `quota_routing` on, the successor of a verified worker or coordinator rollover is routed when its grant is due (after the verified checkpoint, or after coordinator retirement/closure). The predecessor's record is preferred; the alternatives are that rollover kind's own allowlist and `*_provider/account/model` permissions (initial-dispatch permissions never apply). A permitted sufficient alternative provisions the fresh successor on that record; the running predecessor and its conversation are never changed. An unpermitted one becomes a `quota_fallback` gate on the **running predecessor**, bound to the rollover, scope, routing-policy/evidence/catalog revisions and exact tuples (`dispatch.rollovers[*].quota`). Approve applies to that successor only; reject (or cancelling the gate) holds the rollover with `quota_fallback_rejected` until evidence or Config changes the proposal; cancelling the rollover discards the decision. With nothing sufficient the rollover is held with the quota reason and is re-evaluated on fresh evidence; the predecessor keeps running. Successors carry `routing.scope` and go through the same launch-time validation. Landing is unchanged.

**Concurrency ledger**: each routed worker's `routing.reservation` records `reserved → claimed → launching → active → released`, with `uncertain` keeping occupancy. It is bound to the decision digest and the evidence revision (rebound while still `reserved`). Phases follow committed evidence: reserved at the routed decision; claimed when the launch is claimed; launching once SPAWN binds a pane; active after acceptance; uncertain while the launch effect is uncertain; released on verified stop or mailbox retirement, a definitive pre-pane failure, or a hold before launch. A new reservation is taken when held work is selected again. With `quota_routing` on and `concurrency_limit` > 0, a decision that would exceed the limit is held with `concurrency_limit`; a rollover successor may overlap only its own predecessor. The ledger serializes this session's routed launches only and is never a provider-side reservation. Restore validates the phase enum, the history (≤8 edges, last edge equals the phase) and that only provisioned routed work holds a reservation.

**Selector evidence:** SPAWN exposes only owner-entered `selector_evidence` text, not a typed verification status. ORCH+ therefore shows every record's model/profile selector as **unverified** (`unverified_owner_text` or `unverified_absent`) in the catalog, routing decisions (`routing.selector`) and fallback-gate evidence, and does not enforce or claim selector proof.

Not covered: landing keeps its existing record; per-work-class preferences and per-window/pool reserves are not configurable. Routed work that had not launched when the controller was continued moves to the continued route and is re-evaluated there (see [Recovery workflow](#recovery-workflow)).

## Recovery workflow

**Inspect**, **Recheck**, **Reveal owner**, and **Stop assistance…** are buttons whose requests the window handles; it returns bounded events to the host block. Window observations are limited to the source pane's host. Controller aliases are associated by the host-issued nonce on the exact native plugin surface, never by cross-window ID equality or bit arithmetic.

Stop assistance asks for confirmation and closes only the uniquely nonce-associated ORCH+ controller block. It never guesses an agent or shell target. If an alias cannot be proved, or multiple aliases match, the UI asks the operator to inspect/stop the recorded owner manually. For an owner on an unavailable host/window, restore that connection or complete independent verification. There is no claim that native snapshots enumerate all ownership or execution-target membership.

Closing a controller **does not clear ownership**. Reopen ORCH+, choose the existing registration, and **Recheck**. A fresh observed-unavailable result changes current activity to unknown, not stopped, and retains all pending executors. Independently verify that the old owner is stopped. A currently observed positive executor count cannot be overridden by operator attestation.

After restore, a retained positive executor count is explicitly **unconfirmed**, not silently cleared. Only with an observed-unavailable owner, unknown current activity and unconfirmed executor evidence does a separate **Verify retained executors and unavailable owner…** confirmation appear. It requires independent verification that the owner and every retained executor stopped or were reconciled. This records `executors_verified=true` and operator-attested evidence; it is not a claim of native executor tracking. A global epoch change elsewhere does not invalidate currently observed executor facts.

After recording the permitted verification, **Begin fenced recovery** and separately confirm the displayed owner/generation/revision. Intervening registry changes invalidate confirmation. Recovery tombstones that owner and advances its generation; it never launches a replacement or clears the other ownership slot.

ORCH+ also retains the **actual dispatch action/request/executor ledger**. A zero inspection count does not clear those claims. A restored uncertain claim may be reconciled only through the displayed exact action/executor/revision confirmation after unavailable-owner evidence and independent operator verification. Reconciliation records the attestation and holds the work; it does not repeat a launch, accept a stale callback, clear a coordinator or start a replacement. Resolve retained actions before ordinary owner recovery.

For an existing controller after reload, continuation (**ORCH+ Continue controller in this window** from the palette, run in the window that should become the origin; the **Continue controller after reload…** button works only in the window that already is the origin) is separate from retiring its owner. Confirm the exact displayed owner/generation/revision only after independently verifying old executors stopped or retired. Continuation records a new control origin while retaining original claims, counters, pending decisions and coordinator uncertainty. Inspect original SPAWN outcomes read-only before attaching workers; an oversized or missing outcome is not permission to resubmit an old effect.

Work that never launched follows the continued controller. Its launch is either absent or `ready` and never claimed, so nothing of it can have started. For such a queued or provisioned ordinary worker (same owner, generation and controller alias), continuation moves its launch route to the continued window and rewrites its never-claimed `mailbox_provision`/`launch` requests there, keeping the same request and action IDs (SPAWN never saw them). A provision claimed in the old window keeps its exact request and settles through the continued route. The launch it then releases is built on the continued route and runs from **Run queued launch** in the continued window; quota routing and its reservation re-evaluate there. A claimed, backpressured, uncertain or settled launch keeps its original route and its strict fencing. Adoptions, whose pane was attested in the original window, and rollover successors (`successor_launch_fenced`) are not moved.

Continuation cannot move work whose provision, launch or adoption it **fenced** as conclusively unexecuted (`resolved` with `never_claimed` or `pre_effect_refusal`): a request SPAWN already received (a retried or refused one) keeps its exact bytes, SPAWN never accepts the same request ID with a changed route, and a mailbox is bound to its launch request ID. Adoptions and moves refused for size are fenced the same way. Such never-launched work (queued or provisioned, no pane, not a rollover successor) shows **Cancel never-launched work…** (`cancel_work`). When SPAWN received the fenced request (it has a response or was retried), the window first reads SPAWN's read-only `status` of that exact request and sends the query and answer with the command. The host accepts only definitive unexecutable evidence: SPAWN has no record (`missing`), a terminal `rejected`, or a retryable pre-effect `full` (including SPAWN's report of an unconsumed challenge past its deadline or from an earlier host VM). A live challenge refuses with `authorization_live` until it expires (30 s); any other outcome refuses with `spawn_outcome_open`; another request's status refuses with `binding_mismatch`. A never-sent request needs no read. Without a provisioned mailbox, cancellation removes the worker and its settled actions, drops its gates and exclusions, and, for a coordinator start, releases the never-bound orchestrator reservation in the same commit (refused as `coordinator_unresolved` while that owner is not plainly `reserved`). With a provisioned mailbox, the same checks run first; the commit then records `withdrawn` (op, fenced action ID and evidence) on the worker, keeps the resolved fenced action (so routing and the concurrency reservation keep treating the work as settled), drops the worker's other unclaimed `ready` actions and queues one `mailbox_retire` (`mode="retire"`) of the never-used mailbox on the current route, answering `withdrawal_retiring`; the window drives it like any queued effect. SPAWN 0.3.1 accepts that retirement without a native stop and fences the unconsumed launch challenge in the same save. On SPAWN's confirmed `retired`, the worker is reclaimed and a coordinator start releases its never-bound orchestrator reservation. A definite refusal holds the worker (`mailbox_retire` `refused`) and cancelling again, with no status evidence, issues exactly one fresh retirement; a pending or uncertain one refuses `retirement_unresolved`. `withdrawn` is part of the validated worker schema, so a restart mid-retirement restores it. Nothing is stopped, retried or re-sent; the old request can never be authorized later because SPAWN's window authorizes only an ORCH+ action it observes claimed on its current route. Queue the assignment again for a new worker with a new launch request ID. A claimed launch that became uncertain is never withdrawable. Regression: `dispatch/withdraw_fenced`, `health/withdraw_fenced` (the real window's single status read and evidence).

The same **Cancel never-launched work…** control covers held work whose `mailbox_provision` SPAWN definitively rejected before any effect (for example `binding_mismatch` while a previous SPAWN controller owner is unrecovered): no mailbox exists, no launch was built, and the retained `rejected` answer is SPAWN's terminal outcome, so no status read is needed. It applies even while quota routing still shows the work `selected`. A provision that is claimed or uncertain is never withdrawn. Regression: `dispatch/withdraw_fenced`.

When SPAWN definitively rejects the launch or adoption ask after the mailbox was provisioned, the work is held with an unused mailbox. SPAWN stores such a rejection only before any native call, so no pane exists and no producer ever ran. **Cancel never-launched work…** then queues the exact `mailbox_retire` (`mode="retire"`, zero floors) on the route the owner cancels from, with no native stop, and answers `withdrawal_retiring`; the window drives it like any queued effect. The worker stays visible with that retirement's outcome. On SPAWN's confirmed `retired`, the mailbox is retired, a coordinator start releases its never-bound orchestrator reservation, and the worker is reclaimed like any retired generation. A definite refusal keeps the worker and its reason, and a later cancel issues one fresh retirement. A pending or uncertain retirement is never issued twice (`retirement_unresolved`). SPAWN accepts this retirement only when the launch-family entry is `rejected` with no pane, attachment, acceptance or stop; an executed launch still needs its exact native stop. Regression: `dispatch/withdraw_fenced`, SPAWN `dispatch/unused_retirement`.

Then **Continue after reload / reattach explicitly…** requires selecting the exact existing worker and separately attesting its identity. A scoped proof rejects changed target/owner evidence without being invalidated by unrelated workers' health observations. SPAWN independently checks attachment and may require its Config fence/confirmation first. Immutable launch, mailbox and enrolment identities do not change; only the effective control route does. Old window callbacks remain fenced.

This applies equally to a launched generation still **awaiting acceptance**, including a rollover successor reloaded mid-handover and an ordinary first launch: when reload leaves any generation with a recorded launch pane binding but no continued route, the dispatch card also offers **Continue after reload / reattach explicitly…** beside it. The same attested `attach_worker` path, proof and SPAWN fencing apply; only afterwards are its mailbox reads (including its pending ACCEPTED) resumed.

A generation reloaded between its committed ACCEPTED and SPAWN `accept` may have an accept that SPAWN staged but never authorized. SPAWN owner recovery (or attachment) revokes such a challenge with the pre-effect code `authorization_revoked` (older SPAWN builds: `binding_mismatch` "Controller recovery revoked the unconsumed authorization" / "Explicit attachment fenced the old window challenge"). ORCH+ does not hold the worker for that refusal. It keeps `accept_pending` and, after the explicit attested attachment, re-issues the same immutable acceptance (same launch, enrolment and ACCEPTED event) on the attached route, where SPAWN validates the attachment record. A worker already held with exactly that refusal resumes as accepted when its attachment commits, or on its next poll. The recovered old controller stays fenced, and a different ACCEPTED event still conflicts.

The same revocation is pre-effect for every operation. A revoked `native_wake`, ACK/reply publication, mailbox read, compaction/retirement or stop completes as `authorization_reissue` without holding the worker. Its lane marker (wake obligation, stop or retirement action) is released, and the normal poll lanes re-issue the same obligation on the explicitly continued route. A revoked `attach_worker` completes as `reattach_required`: the worker still needs the owner's explicit reattachment. Launch, adoption and provisioning have no automatic re-issue lane and keep the explicit hold. A worker already held only by a revocation resumes `accepted` on attachment or its next poll if it has an ACCEPTED event and no pending continuation; lane markers still pointing at such a revoked action are released then. Non-holding diagnostics (transport `full`/`incomplete`, uncertainty, intake backpressure, re-issue notes, rejected-report diagnostics) never overwrite the recorded cause of a held worker.

**Unknown outcomes stay held.** Stopped-executor attestation does not establish whether an ask, publication or launch succeeded. Continuation alone cannot satisfy the existing unavailable-owner recovery prerequisites or reactivate an uncertain coordinator. A coordinator owner restored as `uncertain` resumes (`running`, or `retiring` after a retirement request or release) only when the owner's explicit attested attachment of that exact generation commits and none of that owner's executors remains claimed, uncertain or counted. It keeps its enrolment and activation evidence. A recovery intent, a retired-owner tombstone or a restored-pane hold keeps it uncertain. Unrelated safe workers may continue after their own exact attachment.


Operator attestation is labelled as such. Tern's `UiEvent` and button APIs do not authenticate a human or isolate a malicious same-user caller. Nonces correlate native aliases; they are not credentials or proof of human approval.

## Authority and persistence

- One host-module registry owns the `authority_state` KV value. Windows never write authority. Saved block data contains only its view/registration/alias binding and prior-initialization evidence.
- Reducer application creates a candidate without changing the current registry. Only successful `tern.kv.set` publishes it. Failed admission, release or recovery leaves previous ownership intact and displays an error.
- Matching committed request replay returns its original durable result without another transition. Changed-body reuse is rejected. A refused request is not silently retried after an owner leaves; a later explicit operation has a new request ID.
- Every write first checks that persisted authority still matches the host's committed value. Removed, unreadable or changed storage freezes changes rather than overwriting evidence. Refusals, exact replays and no-op answers never write, so they skip that read and compare. The host keeps the exact JSON text of what it last saved (the capacity check's encode) and compares the stored value's text natively; only differing text pays the full Lua deep compare. The 1 s workflow tick first checks each worker's derived health and due flags on shallow copies, and clones the registry only when something changed.
- Host events render every controller block only when committed authority (or store status) changed; otherwise only the originating block renders, and only when its own visible state (result, receipt, notice, controls) changed. Duplicate result replays and refused duplicates therefore render nothing.
- Sequenced window observations (`observe` with `observation_seq`) retain no command outcome. The durable `command_seq` barrier and the per-worker observation cursor carry their replay safety: the exact latest replay is answered idempotently, older ones are refused, so no replay can rewrite newer evidence. Outcomes retained by earlier versions are pruned at restore and on the next committed command. An observation repeating the persisted native state of the same host incarnation commits nothing until its stamp is `stale_ms/4` old. It still commits on a change in state or delivery error, on busy or erroring evidence while a wake is pending (the wake is deferred), on a recheckable native-input gate, and on exit or restored-coordinator evidence.
- Polls keep no command outcome either: each poll is sequenced, its commit advances the `command_seq` barrier, and its queued action is itself retained, so an exact replay is refused `stale_command`. Effect outcomes (claim/result/lost) are kept only while they are their action's current evidence. A claim is kept until a result settles its grant (the claim answer no longer echoes the request; the action holds it). A lost outcome is kept while its grant is current. One result is kept per action while its grant is `response_grant`, stored without `response_bytes` (they are the action's). An exact duplicate result therefore still replays read-only; different bytes under the same ID still conflict. Restore compacts or drops full outcomes from earlier versions once.
- An idle poll commits nothing (`mailbox_idle`, no action) when all of these hold: no publication, acceptance, compaction, decision, wake, stop/retirement, requested report, rollover, assembly or held report is due; the last report read of the next slot found nothing; the poll came after the persisted idle native evidence; and that evidence is under `stale_ms/4` old. A watermark poll is also idle only when every receipt is already compacted. A working edge, a new report or idle evidence older than `stale_ms/4` makes the next poll read again, so an unobserved working blip delays its report by at most about `stale_ms/4 + poll_ms`.
- The window re-sends a claim for an action that still looks `ready` only after 1/2/4/8 s of awake backoff, and replays a captured SPAWN outcome awaiting its host receipt after 1/2/4/8/15 s, not every tick. A delivered outcome is marked `lost` only after 5 min of awake time with no rendered host progress, or 15 min in total. Grantless refusals count for a driver only when this window sent that request; a duplicate claim refused because this window's own claim already won does not hold the action.
- Encoded authority is capped at 8 MiB before every write; the last 512 KiB is reserved for completing an existing coordinator binding, retirement/recovery and genuine safety-fact changes accepted by the reducer. Registration, admission and generic uncertainty marking stop at 7.5 MiB. No operation exceeds the absolute cap or evicts unresolved ownership.
- Durable successful outcomes are capped at 4,096, with 1,024 reserved. Ordinary operations stop at 3,072 outcomes. One-time binding of an existing reservation, retirement, fenced recovery, release and genuinely changed owner/executor evidence may use the remainder; repeated/no-progress observations or settlement requests cannot consume it. Exact committed replay consumes neither another outcome nor another grant. Both byte and outcome limits apply.
- Inside either reserve, settlements run one at a time across all sessions: while any owner's recovery intent is current, other retirement, release and recovery requests are refused `settlement_pending` with the holder's session, slot, owner and intent ID. The scope is global because an intent is bound to the global authority revision, so another session's settlement would invalidate it and force a fresh reserved begin. Confirm the intent in the view that began it, or reload the ORCH+ host: restore withdraws every pending intent without consuming an outcome. A genuinely new safety observation, which the reserve accepts, also supersedes it.
- If a fresh observation or uncertainty fact cannot persist because of capacity, serialization or storage failure, this runtime blocks later release/recovery rather than using older inactive facts. The visible safety fence survives store rechecks and does not block exact committed replay. Repair storage/capacity, then restart for fresh inspection and explicit recovery; a failed observation is never evidence of quiescence.
- Restore validates the complete schema, keeps occupied owners uncertain, fences old recovery intents and persists the new execution epoch before exposing authority. Failed restore persistence exposes no restored grant.
- Missing established storage, malformed JSON and invalid state require backup restoration/repair. Use **Recheck restored store** afterward. Schema-1 state is quarantined unchanged for a later explicit migration; there is no compatibility alias or automatic reset.
- KV durability is the documented native store guarantee, not an asserted fsync/power-loss guarantee. The authority model assumes one active native host worker for this plugin/store, not concurrent independent daemons sharing one data directory.

Coordinator reservation, its immutable task/work/enrolment and the first provisioning intent commit together in the same host-owned authority value. Provisioning must return a complete supported mailbox contract before the launch intent exists. Actual worker pane aliases bind only through the correlated SPAWN outcome, and remain window-local observations—not fabricated host-local pane IDs.

## Dispatch and mailbox contract

`dispatch.luau` is a pure extension of `state.luau`, not another store or plugin RPC. Host events use `kind="dispatch"` for catalog/queue, normalized USAGE `capacity` evidence and `cancel_work` of never-launched work (held routed work, or work whose provision, launch or adoption continuation fenced; the latter may carry `query_bytes`/`response_bytes` SPAWN status evidence), exact effect claims/results (a quota-routed launch `claim` also carries `capacity_validation`), polling, report requests, observation, policy/pause/resume, owner decisions, explicit ordinary `finish`, coordinator `retire`, and controller/worker continuation. Every intent requires an origin-scoped monotonic `command_seq`; `claim`, `result` and `lost` forbid it and remain bound to exact grants. A durable highwater rejects old intents after bounded settled-command history is reclaimed, including successful no-effect intents. `dispatch_reconcile` preserves exact operator request/result replay separately. The native adapter rejects external direct `intake`; runtime reports arrive only as correlated SPAWN mailbox pages.

Before an effect, the host commits the exact request and exclusive executor claim. The window checks the active controller alias, logical registration, native session, host and window incarnation before and after asynchronous boundaries. Native callbacks receive fresh contexts; no retained `WindowCx`, session switching, focus stealing or repeated lost-effect launch is used. SPAWN separately owns its private native execution claim. Host grants use exact native nodes `main.dispatch-state` (`orchplus.dispatch`) and `main.dispatch-request` (`orchplus.request`); the latter contains the exact bounded request JSON without duplicate escaping. Every projected claim, including the per-action `main.dispatch-action-<id>` nodes SPAWN's window authorizes from, is exactly SPAWN_DISPATCH's `{executor,epoch,grant_id}`; a routed launch's bound USAGE validation (`claim.capacity`) stays on the durable host claim, because SPAWN refuses a claim with any other field.

Selecting newly queued work does not replace an outstanding claimed action in the machine nodes. Its exact request and grant remain addressable until settlement or retained uncertainty. Definitively unstarted wake obligations are separate from execution occupancy; they cannot monopolize the mailbox driver while a native worker is busy.

Each attempt has a persisted `claim.grant_id`. Private result callbacks use `act="dispatch-result/<grant_id>/<execution_window_epoch>"` with the unchanged raw frame as `value`; internal `result`/`lost` events also require that grant ID. Current execution origin/controller alias is projected separately from the immutable original request. Delayed callbacks cannot settle a successor attempt or regain execution authority after continuation. Only a SPAWN `full` outcome explicitly carrying `retryable=true, effect_started=false` authorizes an exact-request retry under a fresh grant and ordered status fence. Other ambiguous writes remain occupied, never blindly retried. Unexecuted provisioning backpressure keeps its pane-less coordinator reservation.

Such `backpressure` is rechecked automatically after 5 s of awake time through the same `retry` command and driver as **Recheck unexecuted capacity refusal**, one per worker lane at a time and at most 120 times before it holds for that control. SPAWN reports an unconsumed window challenge that expired, or that an earlier SPAWN host VM issued, as this retryable pre-effect `full` (`resource=window_authorization`). A claimed action or one already `uncertain` after `lost` therefore recovers through the existing result and automatic read-only reconciliation paths. Uncertain outcomes are never retried.

An observed SPAWN outcome is not considered delivered merely because the window sent a host event. The window retains its exact frame until `main.dispatch-state.receipt` identifies the committed `action_id`, `grant_id` and `response_sha256`. Until then it may replay only that host observation, not the SPAWN request/effect. Host observation IDs are deterministic, so a lost commit receipt replays the saved result without another write. This UI receipt is separate from worker report ACKs/reply_ack. Dispatch result/selection metadata is published coherently after commit, including provision-to-launch transitions; errors are scoped to the action/grant they concern.

**Host sleep and throttling.** The 30 s effect deadline and the receipt-replay deadline count *awake* time. The window's one observation timer ticks every 500 ms; a gap of more than 5 s between two ticks (macOS sleep or App Nap, a throttled or budget-paused hook) counts as a single nominal tick, so a suspension extends the active deadline instead of expiring it. Deadlines are never shortened, and genuine awake waiting still ends in retained uncertainty. Heavy throttling therefore stretches deadlines (each delayed tick counts 500 ms); it never retries or re-sends an effect. SPAWN's mailbox adapter uses the same rule for its operation deadline and passes the remaining awake budget as each helper child's `process.run` timeout. Limitation: if the runtime itself kills a child at its `process.run` timeout across a suspension, that operation still settles as uncertain. SPAWN's host-issued authorization challenge keeps its 30 s host-clock freshness window, so a challenge that expires during sleep is still refused (a definitive `binding_mismatch`, not an uncertain effect); queue the work again.

**Automatic read-only reconciliation.** When an action becomes `uncertain` with its exact retained claim, the window reads SPAWN's retained outcome automatically, at most four times: 2 s of awake time after it first sees the uncertainty, then 10 s, 30 s and 60 s of awake time after each previous attempt. Each attempt is one `status` read through the same route, grant and fencing as **Read retained SPAWN outcome (never relaunch)**: it never claims, re-sends, re-executes or creates a grant, and never uses the oversize exact-request replay. A definitive outcome settles exactly as that control does; `pending`, `missing` or SPAWN's own `uncertain` keeps a mutating action uncertain. After the last attempt the controller shows a notice and the owner control plus executor attestation remain; operator attestation for coordinator, launch and stop uncertainty is unchanged. An owner click while an automatic read is running reports it instead of starting a second driver.

**Window bookkeeping is bounded.** The window VM's per-action state (`executed` set-before-send grant markers, automatic reconciliation attempts, held markers) is pruned only on positive evidence read from the action's own controller pane: phase `complete`/`resolved`, or a current claim other than the marked grant. A claimed, uncertain or backpressured action under that grant, or a missing or unreadable action surface, keeps every marker. One watched action is checked per tick. Per-publication readback counts age out FIFO after 512 identities, as issued request IDs do. Sweep attempts and per-worker poll timers of controllers or workers that no longer exist are dropped.

**Retained uncertain reads.** A read-only operation (`mailbox_read`, `catalog`) changes no worker, mailbox or ORCH+ state until its correlated outcome commits, and intake is idempotent through receipts and cursors. So an uncertain read is retained evidence, not a pending effect. When SPAWN's `status` answers `missing` for it (never staged, refused before staging, or completed and compacted), the window sends `read_missing` with the exact status query and response bytes. The host checks they name this exact retained read and claim, then resolves it (`resolution.evidence="read_lost_no_effect"` with the response's `status_sha256`). When SPAWN stays ambiguous (`pending`, its own `uncertain`, or no answer), the read still never blocks the owner's explicit attested **Continue after reload / reattach explicitly…**: the committed `attach_worker` supersedes this generation's uncertain reads (`resolution.evidence="read_superseded"`), and a reloaded coordinator then resumes as usual. Either way the read releases its executor counts, drops the worker's partial read selector and reassembly, and the normal poll lane re-reads from the durable cursor. A late outcome for its grant is refused as stale. Until then the controller keeps showing it as a retained uncertain read. Restore accepts both evidences only on a claimed read-only action, by its claim executor, and requires the status digest exactly for `read_lost_no_effect`. Mutating effects (publications, retirement, provisioning, launch, adopt, stop, `native_wake`, `attach_worker`, `accept`) keep their strict holds: `missing` never resolves them, and they still refuse reattachment until individually reconciled.

Coverage is independent of selection: the controller's machine state lists every uncertain retained action (up to 16), and each one, including stale reads and launches from earlier window incarnations after **Continue controller after reload**, gets these bounded reads. Only one read runs per bridge lane (a worker's lane, or the shared catalog lane) at a time, because concurrent reads would overwrite that bridge's single response node.

**Publication readback.** ACK and reply objects are immutable, deterministic bytes, and ORCH+ requires readback before any retry of an uncertain publication. After one non-definitive automatic read, the window sends `readback_publication` (at most three times per publication identity); the owner has the same **Read back and re-publish the exact same bytes** control on an uncertain `mailbox_publish_ack`/`mailbox_publish_reply`. The host resolves that attempt (`resolution.evidence="publication_readback"`, executor counts released) only on the worker's explicitly continued current route, while the exact receipt or reply part is still outstanding and when SPAWN has not already confirmed the publication. The outbox then re-issues the same bytes under a new request. SPAWN's journal still holds the uncertain write: it reads the object back first and republishes those bytes only if absent; equal bytes return `already_published`, and a late earlier child can only publish the same bytes. Native wakes stay canonical to the publication identity, so no ask is repeated. Launch, adopt, ask, wake, stop and retirement never take this path. Without it, an uncertain ACCEPTED ACK blocked SPAWN `accept` and so a coordinator's activation forever.

**Effect slots.** At most four host actions may be claimed or uncertain at once. Uncertain *read-only* operations (`catalog`, `mailbox_read`) do not count. Safety argument: a read has no native, mailbox-file or registry effect that a new effect could conflict with or duplicate. The slot limit protects the bound on possibly concurrent effects, and an uncertain read contributes none. If its SPAWN child were somehow still running, SPAWN's own executor limits (four per host, one per mailbox generation, plus its per-handle read fence) refuse new work before any effect. Claimed reads still hold a slot while they may run. Uncertain mutating effects (`launch`, `stop`, `mailbox_provision`, publications, `mailbox_retire`, `native_wake`, `accept`, `attach_worker`) still hold theirs. An uncertain read still holds its own worker generation exclusively until it is reconciled.

**Capacity refusals resume.** A claim refused with `full` is pre-effect: the action stays `ready` and no grant exists. The window retries the same exact claim every 5 s of awake time, at most 120 times, then holds it for **Run queued … in its original window**. The host re-checks every claim rule each time. Claimed, uncertain and settled actions never enter this path, and the resumed driver never mistakes the old refusal for a new result.

**Guided reload recovery.** **ORCH+ Reload recovery guide**, run from the palette in the window you are using (also opened automatically after continuation; the **Guided reload recovery — next step…** button works only in the window that already is the controller's origin), reads SPAWN's owner state with a read-only `owner_status` request, then lists every remaining step in order: continue the controller, recover the previous SPAWN owner, reattach each worker (with its recorded pane), and how many uncertain actions are being read automatically. The palette commands act on the session's only ORCH+ controller with a recorded owner, else on the focused one. The same list appears in the controller as a **Reload recovery checklist**. Picking a step opens the existing explicit control. Continuation and reattachment use their attested pickers. The SPAWN step opens **SPAWN: Running agents**, where Transport review keeps SPAWN's independent fence → verify → confirm. ORCH+ never attests, retries or adopts anything itself, and SPAWN owner recovery stays a SPAWN Config action.

Explicit operator dispatch commands use the local `dispatch-operator-command` UI action; background driver commands continue using `dispatch-command`. Results carry their originating `request_id`. The public `command_result` projection retains a failed operator command independently of active worker `result`/`receipt` updates, with an explicit acknowledgement bound to that request. A stale acknowledgement cannot dismiss a newer failure; a new operator command or explicit action selection supersedes the prior command. Refusing a second coordinator start never replaces the first worker's live driver or captured outcome.

Every `full` response must also include `resource` (nonempty ID, at most 96 bytes), `current` (nonnegative safe integer), and `limit` (positive safe integer). Current usage may be below the limit when projected/staging admission cost causes refusal. Optional `retryable`/`effect_started` booleans must occur together; only `true`/`false` grants retry permission. Missing accounting, partial pairs, invalid counters or resource IDs are malformed, and restored backpressure is checked against the same schema.

The bridge is the non-palette `spawn.dispatch` block. ORCH+ sends `{ev="action", id=<current response node id>, act=<operation>, value=<exact request JSON>}` and reads only `main.spawn-dispatch-response`, role `spawn.dispatch.response`, with `SPAWN_DISPATCH v1` framing, complete-byte length and SHA-256 checks. Status reads address retained request IDs. In the original execution context, an oversized nested status outcome may use exact immutable request replay against SPAWN's registry. A continued read-only reconciliation context and automatic reconciliation explicitly forbid that fallback.

Bridge panes are bounded. The window binds at most one bridge per controller and lane (a worker's lane, or the catalog lane) in its session. Before opening a pane it adopts an existing `spawn.dispatch` pane in the same host session, including one left by an earlier window or plugin reload, when SPAWN's lease node (`main.spawn-dispatch-lease`, `SPAWN_BRIDGE v1`) shows it idle: no still-consumable authorization challenge names it (an expired or earlier-VM one no longer does, whether or not its window survives), no execution projection is live, no verification is in flight, and its owner is this controller pane, alias and window. No current driver or owner probe may be using it, and panes in the bridge tab are tried first. An idle bridge of another lane of the same controller moves to the new lane. Bridges are never moved between tabs or parked: in the live window a pane moved with `move_to_tab`/`move_to_new_tab` answers `cx.session:surface` with nil, so neither ORCH+ nor SPAWN's window executor could read it again, and a parked pane has no provable session. Each bridge opens where it stays. The session's first opens with `new_block(..., "tab", {focus=false})` in a new tab named **SPAWN bridges**. Later ones open `beside` a pane of that tab (any tab holding only bridges), never splitting the controller. A tab block that lands outside the controller's session is closed unused, and the bridge then opens beside the controller. Once per second of awake time the window closes, through the native pane close, one inert bridge left by an earlier incarnation of this same window. It keeps up to two such bridges in the bridge tab per present controller as reload spares and closes the rest, including those beside the controller. Held, live, busy, unreadable (legacy SPAWN without a lease, or a pane an earlier build moved), other-window and current-incarnation bridges are never closed or reused. Regression: `health/bridge_lifecycle`, SPAWN `dispatch/bridge_view`.

The host accepts complete `report-files-v1` pages and validates initial `ACCEPTED`, capability `REGISTER`, immutable `reply_ack`, READY/HEARTBEAT/WAITING/BLOCKED, ASK, structured CHECKPOINT, review/result/proposal envelopes, DONE, rollover requests and explicitly negotiated `COORDINATOR_RELEASE`. Typed proposals/results are data, not automatic lifecycle grants. Initial acceptance has no invented handover fields. Cursor, exact ACK bytes/receipt chain, semantic state and the SPAWN accept outbox commit atomically before publication. Lost ACKs replay saved bytes and the original commit revision. Only a cumulative worker chain watermark permits receipt compaction; only the matching `reply_ack` settles worker receipt of a reply.

Full/incomplete transport does not demote accepted workers. A completed read that cannot enter the bounded receipt/reassembly lane records backpressure without a receipt, cursor advance or ACK. Its immutable source remains available; an independent watermark poll can drain the confirmed prefix. A completed but semantically rejected report instead settles the read grant and holds the exact bytes/hash and diagnostic, without accepting, replacing or ACKing the report. This releases transport capacity for unrelated work while preserving the rejected evidence.

**Re-check held report…** (owner control on a held report, never automatic) re-decodes the *same* retained bytes — same sequence, deterministic event ID and SHA-256 — with the current validation, for example after an ORCH+ defect wrongly rejected them. The held bytes must be this generation's exact next sequence and the worker must be explicitly continued. If they are now valid they enter the same semantic intake as a freshly reassembled read (receipt, ACK, acceptance and rollover progress follow normally); otherwise they stay held with the new reason. No sequence is skipped and no different bytes can be substituted.

Durable ACK/reply publication is separate from native wake. Only `wake_status="awaiting_window"` together with `wake_effect_started=false` and canonical `wake_target_request_id` / `wake_target_action_id` establishes a definitively unstarted notification. ORCH+ retains that bounded obligation, settles publication and later grants a separate `native_wake` against the exact publication when current native evidence is safely idle. Busy and waiting-input workers are not interrupted; mailbox reads continue. Started/uncertain wakes still occupy the normal four-host/one-generation execution limits. A proven pre-effect idle race can defer under a fresh exact grant; an unknown ask never retries. ACK1 may wake its exact launched worker before separate semantic acceptance. Terminal polling publications need no native wake. Neither publication nor submitted input substitutes for a worker watermark or `reply_ack`.

Structured threads retain assignments, reports, questions, owner answers and delivery/receipt states. Health keeps native state, worker-reported state, progress, freshness and pending gates separate; a worker READY cannot override a native permission prompt or exit. Clock epochs prevent restored monotonic timestamps being treated as fresh. Scheduling rearms after reload, rotates registered workers and keeps one unresolved report request per worker. No report screen-line parser, transcript reading, raw terminal typing or second filesystem/SSH resolver exists.

**Held reports.** A completed but rejected report is held with its exact bytes and blocks that generation's report lane; nothing is skipped or acknowledged. The scheduler then stops automatic report and watermark reads and automatic progress requests for that worker. It still polls when a poll would grant outbound settlement (ACK/reply publication, acceptance, compaction, an answered decision or a startable wake). **Read / settle** and **Read cumulative receipt watermark** remain explicit owner reads. Resolve the hold by inspecting the producer and recovering or replacing that generation.

[`worker-brief.md`](worker-brief.md) documents the current helper/report/control flow. SPAWN supplies the configured transport/enrolment instructions privately while preserving ORCH+'s exact assignment bytes and digest. Mockups describe the broader orchestration workflow, not acceptance evidence.

## Ordinary worker finish and retention

**Finish ordinary worker…** is an explicit owner action; DONE alone never stops a pane. Unresolved gates, deliveries, report requests, wakes, claims or pinned lifecycle evidence prevent finish. After settlement, the existing exact-native-stop and mailbox-retirement path must complete before capacity is reclaimed. A failed or uncertain stop/retirement remains held.

SPAWN's one definite pre-effect retirement refusal is `producer_unsettled`: the stopped generation's helper journal still holds pending reports or unacknowledged/unresolved control messages at the authorized floors, so the producer helper removed nothing and the target was never touched. ORCH+ settles that attempt as `retirement_refused`: the action completes (its effect slot is released and it blocks no owner release), the worker is not held, the mailbox stays provisioned and `mailbox_status` is `refused`. Nothing re-issues it automatically; the nightly sweep or **Retry mailbox retirement once…** (the finish control) issues exactly one fresh grant. Any other failure, including an uncertain retirement, stays held and is never re-armed.

Only fully retired, unreferenced generations and safely settled generic gates are reclaimable. Report cursors and monotonic identity/intent fences survive display-history eviction, so a pruned ASK or old command cannot recreate work. Active checkpoint and typed review/rollover/landing references remain pinned; full live evidence remains explicit backpressure rather than silent deletion.

## Verified worker rollover

A selected ordinary worker's health card offers **Roll over worker…**. With **Automatic worker rollover** enabled, the window also sends a policy-triggered `rollover` command when an accepted, explicitly continued, non-excluded ordinary worker is idle at a clean point (no outstanding request or gate) and its latest self-reported `context_used_pct` is at or above `rollover_threshold_pct`, and no rollover involves it. The host reducer rechecks every condition. A trigger only *requests* a checkpoint. Coordinators follow the separate coordinator rollover below.

Each rollover is a host-written record in `dispatch.rollovers`, keyed by handover ID and bound to the work, predecessor and successor panes, a 64-hex handover token and the requesting controller owner/generation. Every edge is appended to its durable history with the committed revision:

`requested → checkpoint_pending → checkpoint_verified → successor_granted → successor_created → handover_accepted → predecessor_stop_requested → predecessor_closed → complete` (or `cancelled`).

- **Checkpoint.** ORCH+ issues one ordinary `report_request` with `requested_kind="CHECKPOINT"` once the predecessor is safely idle. The CHECKPOINT echoing that request ID must state completed/remaining work and carry at least one check, every check fresh for its `artifact_revision` with outcome `passed`; `failed` (`verification_failed`), `not_run`, stale or missing checks block. The result is recorded as **worker-attested**; no check is executed and no default verifier is invented. A blocked checkpoint can be requested again on the same handover.
- **Successor.** A new worker record reuses the predecessor's configured SPAWN record/revision, cwd and placement only if they are still current and eligible; nothing is substituted or derived from the predecessor pane or its command. Its assignment is the verified checkpoint payload. The ordinary `mailbox_provision` → `launch` (`fresh=true`) path carries the immutable enrolment `{worker_id,worker_generation,enrolment_token,assignment_sha256,handover_id,handover_token}`; SPAWN's native start queues that assignment once. An over-bound handover holds as `input_too_large` and is never truncated.
- **Acceptance.** The successor's ACCEPTED must carry the exact handover pair, and the SPAWN `accept` callback includes it too. Only after SPAWN records semantic acceptance *and* a fresh native observation shows the successor working, idle or waiting for input does ORCH+ set the predecessor's finish intent; the existing finish path then issues one exact native stop after receipts and replies settle. `complete` requires SPAWN's stopped outcome with an `absent`/`exited` observation.
- **Failures.** Every failure keeps its phase plus a `hold` code/message, and the predecessor stays alive until successor acceptance. A failed or fenced successor launch can be cancelled; an uncertain launch, accept or stop is never retried and must be reconciled through the existing recovery controls. No timeout starts a successor or stops a predecessor. A different controller generation cannot advance a rollover. After a host reload the controller is uncertain and nothing advances until explicit **Continue controller after reload…**; the rollover then resumes from its durable phase without another successor or launch. If the window incarnation changed, continuation fences a never-claimed successor grant (`successor_launch_fenced`) instead of replaying it.

A worker's ROLLOVER_REQUEST report remains evidence only. Native daemon resume of an existing conversation is Tern recovery, not a fresh rollover, and is never relabelled as one.

## Verified coordinator rollover

The activated coordinator's health card offers **Roll over coordinator…**. The policy trigger selects it only when `auto_rollover` **and** `rollover_include_coordinator` are on, its self-reported `context_used_pct` (READY/HEARTBEAT) is at or above the threshold, it is the current running owner with an acknowledged activation and not retiring, it is idle at a clean point, and no other coordinator rollover or restored-coordinator hold exists in the session. Unlike worker rollover, two managed coordinators **never overlap**. The record (`kind="coordinator"`, with predecessor/successor owner IDs and generations and a `closure` of `observed` or `operator_attested`) advances through:

`requested → checkpoint_pending → checkpoint_verified → retirement_requested → predecessor_released → predecessor_stop_requested → predecessor_closed → owner_retired → successor_granted → successor_created → handover_accepted → complete`.

- The verified checkpoint quiesces the predecessor through the existing typed `coordinator_retirement` reply (`retiring` owner: no fresh proposals or launch effects). Its authenticated COORDINATOR_RELEASE, final watermark, exact native stop and mailbox retirement then run through the existing coordinator finish path; the slot stays occupied throughout. Cancellation is possible only before retirement is requested.
- Only after the stopped outcome (exit/absence) and the normal generation-bound release does the same serialized commit reserve the successor's orchestrator slot and queue its provisioning. While the rollover is unfinished, an unrelated coordinator start is refused (`rollover_reserved`).
- The successor is a fresh launch on the same configured record carrying both the paired coordinator owner/generation and the handover ID/token. Its ACCEPTED and SPAWN `accept` must carry the handover pair, and its activation token is derived from the handover, so the retired generation's token is never valid. `complete` requires the durable activation `reply_ack`.
- An uncertain or refused predecessor stop holds with the checkpoint retained; it is never retried and no successor starts. Resolution is the existing operator-assisted orchestrator recovery (observe unavailable, attest stopped, fenced recovery). Its confirmed retirement records `closure="operator_attested"` and lets the retained handover reserve the successor. Reload keeps the durable phase; the restored owner is uncertain, so nothing progresses until that recovery.
- A coordinator that publishes its own COORDINATOR_RELEASE before the rollover holds a verified checkpoint (phase `requested` or `checkpoint_pending`) leaves nothing to hand over and can never send a checkpoint afterwards. The rollover closes as `cancelled` with hold `predecessor_self_released` on the worker card; its normal release, exact stop and mailbox retirement continue, no successor is granted, and the slot is free for an explicit new start. The existing release rule still applies: release never discards an outstanding progress request. While the rollover's CHECKPOINT request is outstanding, the coordinator must answer it first (a CHECKPOINT lets the rollover continue; a HEARTBEAT echoing the request_id leaves `checkpoint_missing`). An earlier release is refused, and on the mailbox path it is held as a rejected report. After a verified checkpoint, the release is the quiescence the rollover waits for and it continues normally.
- A stopped coordinator pane observed alive again (native restoration) is recorded as `restored` evidence and never counts as healthy. Until a later exited observation or the owner's **I stopped this restored pane** attestation, every coordinator claim and proposal in the session, including the successor's, and the rollover itself are held.
- Every rollover successor's `mailbox_provision` carries the handover ID and `handover_sha256` = SHA-256 of `handover_id:handover_token`, never the token. SPAWN's producer helpers refuse an ACCEPTED whose pair does not match before allocating a report sequence, naming the field without echoing either value, so the successor retries with the exact values. Provision requests retained from earlier builds carry neither field and still validate.
- From `owner_retired` on, the predecessor is already stopped and retired and the rollover cannot be cancelled. If the successor's launch fails or is fenced, or the successor exits, is held, or has a held report before accepting, the hold (`successor_launch_failed`, `successor_launch_uncertain`, `successor_launch_fenced`, `successor_unaccepted`, `successor_report_held`) says that no coordinator is active and shows SPAWN's diagnostic. For example, an already published ACCEPTED with a mistyped handover token (from a mailbox provisioned before the producer check, or an outdated helper) is refused `binding_mismatch` "Acceptance differs from the issued assignment or handover.", and its immutable report sequence cannot be replaced. Nothing is retried or relaunched. To continue, stop the successor pane if it exists and reconcile any retained effect. Then run fenced recovery for the successor's orchestrator owner on its owner card. That retirement closes the rollover as `cancelled` with hold `successor_owner_recovered` and frees the slot, so you can start a new coordinator explicitly from the retained verified checkpoint.

## Explicit verified attach

An idle, ticked hand-opened agent pane row in Config offers **Attach pane N as ORCH+ worker…** when a SPAWN catalog is loaded. The picker asks for an eligible, enabled `native-agent` record with `report-files-v1`, the assignment, and a separate attestation that you verified the exact window-scoped pane (pane id, window incarnation, native session, host). The window re-verifies the pane immediately before sending: it must be in this controller's session/host, a recognized native agent, idle with no delivery error and not bound to any worker. Nothing is ever adopted automatically, and a shell/terminal pane is never typed into.

The host reducer (`adopt` command, operator-only) re-checks the attestation (`operator_verified_exact_agent_pane`), the pane's origin scope (`invalid_task`), the catalog revision (`catalog_changed`), the record (`unsupported_capability`), pause, capacity and limits, and refuses a pane already bound to any unstopped worker's launch, control or adoption binding (`pane_bound`). It then creates a normal first worker generation with `adopt_pane_binding` and queues the ordinary `mailbox_provision`. After provisioning, the worker's launch slot carries a SPAWN `adopt` request instead of `launch`: the same immutable enrolment `{worker_id,worker_generation,enrolment_token,assignment_sha256}` (never a handover or coordinator pair), plus `pane_binding` and `attestation`. SPAWN delivers the shared transport preface and the unchanged assignment once via `agents:ask` to that pane under the usual exact claim/begin/result rules and records the pane as the launch pane binding.

- A pane busy, not a native agent or out of scope at execution time is refused by SPAWN before any ask (`target_unavailable`); the worker is held and nothing is retried. A new explicit attach creates a new worker.
- A lost or ambiguous ask is `uncertain`, keeps the pane bound and is never repeated; it is reconciled through the existing recovery controls. A host reload mid-adopt turns a claimed ask into retained uncertainty.
- The worker then publishes ACCEPTED as normal; acceptance, health, replies, finish (exact native stop), rollover and continuation are identical to a launched worker. SPAWN reserves no managed launch capacity for an adopted pane.

Coordinator adoption is not supported.

## Landing queue

Landing is ordered per **logical session, project, repository and target ref** (never cwd), with exactly **one granted slot per target**. Other targets and projects progress independently. ORCH+ never runs git or a merge command and never infers landing from REVIEW_READY, DONE, idle or a closed pane; the registered project worker performs its own approved merge/rebase workflow and reports the exact result. A coordinator `landing` proposal is a decision record only.

State lives in the sole host-written authority as `dispatch.landing = {queues, items}`. A queue records its FIFO `order` of open items, the granted `slot` and the last recorded target `head` (`{revision, source=landed|stale_target|owner, landing_id}`). Each item binds work, worker, the exact request `{project_id,repo_ref,target_ref,target_revision,source_ref,source_revision,checkpoint_id}`, its owner approval gate, worker-attested verification, a status history and up to eight grants. Statuses are `queued|ready` (behind the head), `verifying` (head awaiting owner approval), `blocked` (head with a hold reason), `granted`, `landing` (grant consumed), `landed`, `failed` and `cancelled`.

- **Request.** The worker's `LANDING_REQUEST` must reference a retained checkpoint of the same project whose `artifact_revision` is the source revision. It opens a durable `landing_approval` owner gate for that exact request. Config has no automatic landing policy, so every grant needs that approval; reject or cancel withdraws the item.
- **Grant.** Only the queue head, with a free slot, the owner's approval, an accepted and explicitly continued worker outside any rollover, no BLOCKED report, no pause or capacity reserve, and a **latest** worker checkpoint for the exact source revision with run, passing, fresh checks and no holds receives one immutable `landing_grant` reply. Missing, stale, `not_run` or failed evidence blocks with its reason. A request whose expected head differs from the queue's recorded head is `target_moved` and must be refreshed.
- **Refresh notice.** An ungranted request blocked as `target_moved` gets exactly one immutable `landing_refresh` reply `{landing_id,project_id,repo_ref,target_ref,expected_revision,current_revision,reason}` to its bound worker generation through the ordinary reply outbox, so normal publication and wake deliver it. The obligation is derived from the item on every session commit (including items blocked before this reply existed) and is keyed by generation, expected head and current head: replays and later ticks never duplicate it, and a further target move after the worker refreshed issues one new notice for the new head only. A full reply outbox or thread, the settlement reserve, or a generation that cannot receive replies (finishing, stopped, in a rollover) keeps the `target_moved` hold visible with a deferral note and retries on a later commit. The notice is information only: the worker's fresh CHECKPOINT and LANDING_REQUEST rebind the item and need new owner approval.
- **Result.** `LANDING_RESULT` must correlate to the grant's action and echo the grant. `landed` records `result_revision` as the new head and frees the slot; `rejected` fails the item; `stale_target` records the observed head, frees the slot and keeps the item in place as `refresh_required`. A refresh (a new `LANDING_REQUEST` from the same work and target, which also rebinds a rollover successor) voids the previous approval and evidence. Nothing is retried automatically.
- **Uncertainty.** A worker-reported `uncertain` result, DONE without a result, a lost worker (exit/stop, held generation, rejected or conflicting report) or the owner's **Result lost — hold slot…** keeps the slot occupied; no later item is granted. **Reconcile observed outcome…** records the owner's read-only inspection as landed (with the resulting head) or not landed (slot released, worker must re-request), with an operator attestation and reason. A later worker result for that grant is retained as evidence only. Reload keeps slots, holds and uncertainty.
- **Owner controls.** The controller's **Landing queue** cards show head, slot, holds and grants. **Move up/down** and **Cancel…** apply only to ungranted items and never pass the granted slot. A granted worker cannot finish or roll over; an ungranted item is held while its worker rolls over.

Test coverage: `reports` sections `landing_queue`, `landing_evidence`, `landing_results`, `landing_uncertain` and `landing_lifecycle`, plus landing codec cases in `transport` and SPAWN's helper/codec suites.

## Normal coordinator finish and retirement

Coordinator start requires explicitly configured **and provisioned** `coordinator-control-v1`, in addition to report-files and a supported wake/poll capability. Existing records without this capability remain eligible for ordinary work, not coordinator startup. No production record is automatically marked supported. The launch enrolment carries the paired reserved coordinator owner ID/generation only for actual coordinator work; SPAWN's role-specific preface says to ACCEPT the unchanged assignment, then wait for and claim typed activation before acting. Ordinary work on the same capable record does not wait for activation.

After correlated ACCEPTED, ACK publication and SPAWN acceptance, ORCH+ durably issues one `coordinator_activation` reply. Its exact typed owner/generation/token and action identity survive reply compaction. A worker self-finishes with authenticated `COORDINATOR_RELEASE`; **Request graceful coordinator retirement** instead commits one immutable `coordinator_retirement` reply through the `retire` command. Both routes require activation's durable reply receipt. A retirement request is not a stop, and release intent does not clear the slot.

The controller displays activation/receipt, retirement-request, quiescence, reply-floor, native-stop and mailbox-retirement phases. **Read / settle** advances retained outboxes; **Read cumulative receipt watermark** independently commits the producer's confirmed receipt chain. A retirement reply already committed when self-finish arrives still drains normally. No new progress replies are issued after retirement. The final watermark must cover release and all contiguous reply acknowledgements before stop is granted.

SPAWN receives one exact enrolled-pane `stop` request. Only the durable `stopped` response with the issued pane binding and a post-effect `absent`/`exited` observation permits `mailbox_retire` in `retire` mode with exact settlement revision/floors/chain/grant. SPAWN settles that exact managed launch reservation only after stop plus mailbox retirement. ORCH+ then uses its normal generation-bound release transition, retains worker/history/fences and clears exactly the coordinator slot. A separate explicit start can reuse the configured record; an old generation's release cannot clear its successor. No worker idle, DONE, absent pane, button click or successful native call alone is completion.

Uncertain stop, uncertain helper retirement, failed KV commit and restored freshness keep ownership occupied. Coordinators from earlier builds without an issued activation remain occupied for inspected recovery; they are never silently granted a token. Native pane stop evidence does not prove every remote OS descendant exited. Sticky operator command refusals remain independent of background settlement.

Tests add separately runnable dispatch sections `retirement_auth`, `retirement_finish`, `retirement_race`, `retirement_uncertain`, `retirement_restore`, `retirement_capability`, `retirement_codec` and `retirement_refused`. They cover exact grant/worker/token rejection, closed wire schemas, all five capabilities, failed commits, replay, final floors, a delayed retirement race, uncertain operations, SPAWN's definite `producer_unsettled` refusal and its one-shot re-arm, successor fencing, compatible old state and explicit capability admission. Run each separately with the existing native callback limit, alongside all existing sections.
