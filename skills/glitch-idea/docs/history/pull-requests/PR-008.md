## Description

A saved browser session whose idea was removed no longer stops a seat's idea service from starting, and remove-idea refuses an idea this seat's sessions still select.

## Why
On 9 Oct a seat removed an idea one of its own saved sessions still selected. From then on every start of that seat's service restored the session, hit `not_found` and died before listening, so every page open reported `service_readiness_timeout`. `remove-idea`'s documented `idea_in_use` check had never been built, and the ideas store is shared between seats, whose sessions live in private runtime folders.

## What changes
- **Start sets an orphaned session aside.** During restore, a session whose open fails `not_found` is moved (never deleted) to `<runtime_root>/parked-bindings/<store>/` when a store read confirms its idea is gone; one activity line records it; the service starts. Any other restore error still fails the start.
- **remove-idea refuses `idea_in_use`** (with `binding_ids`) when one of this seat's saved sessions selects the idea: an early check for the preview, and a re-check under the store lock before anything is published. `session-discard` is the way out.
- **Documented limits:** another seat's sessions are not visible (its next start sets them aside); and the owner validates an idea under the store lock but saves the session after releasing it, so a removal committing in between is not seen (same bounded outcome).
