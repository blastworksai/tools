# ORCH+ protocol reference

This is the detailed contract behind [ORCH+](README.md) 0.4.0: storage, dispatch, mailbox, roles, proof, landing, rollover and recovery rules. The README covers everyday use. The agent-facing contracts are [worker-brief.md](worker-brief.md) and [coordinator-brief.md](coordinator-brief.md).

Every control named here is a native button in the ORCH+ controller or Config page, except the two palette commands **ORCH+ Continue controller in this window** and **ORCH+ Reload recovery guide** (see **Guided reload recovery**); there are no `orchplus://` links. Pressing a dispatch or assistance button makes the host publish a bounded one-shot operator intent (`main.operator-intent`, role `orchplus.intent`). The ORCH+ window that owns the controller's origin runs a dispatch intent exactly once; every other window ignores it. A host-block click carries no window or client identity, and every client attached to one window key shares that key, its session and its focus, so **Continue controller after reload…** and **Guided reload recovery — next step…** work only in the window that already is the origin; a fresh window incarnation continues only through the palette commands, which Tern runs in the window where they were invoked. Before anything runs, that window re-checks the controller pane, logical session, host and window incarnation, and the host block re-validates the command. Intents have no URL size limit, so large **Save session settings** and **Attach pane N as ORCH+ worker…** requests are never dropped. An intent whose confirmation does not reach the host within 30 s expires with a notice that it will not run later; a window may still have run it, so check the current state before acting again. A button rendered before the last host update is refused as stale, never replayed.

Assistance buttons (**Inspect**, **Recheck**, **Reveal owner**, **Stop assistance…**) follow the same rule while a live continued origin exists: when the session's command cursor belongs to the active controller owner and generation, the host stamps that origin's window (key, incarnation, native session, host) into the intent and only that window runs it. Before the controller's first command there is no cursor, so intents are not fenced to one window and any ORCH+ window showing the controller in its admitted session may take them. While the controller is restored uncertain (no live origin), assistance stays open to any window showing it, so a recorded owner can still be inspected, rechecked or stopped. Both cases keep their pickers and host re-validation.

## Session Config editing

Config is a display mode of the same block: scheduling and effect drivers keep running, and **Open ORCH+ controller** returns to the controller. With no logical session selected, Config shows the session chooser. Settings are per logical session in the host-written session policy (`dispatch.policies`). The 46 settings, defaults and bounds are listed in the [README](README.md#config-page).

Only the session's admitted active controller can edit; other views (unbound, duplicate, uncertain) show the same values read-only with the reason and offer **Reveal recorded controller pane**. Checkboxes and −/+ buttons edit an unsaved draft; **Save session settings** commits only the changed fields through the `policy` command, fenced by `expected_policy_sha256`, the digest of the displayed saved policy (`workflow-index` `policy_sha256`). If the saved policy changed meanwhile (another save, pause/resume), the reducer refuses with `policy_conflict`, the draft is discarded and nothing is overwritten. With no draft, **Enter value…** accepts one whole number within its bounds; list, text and record settings likewise save one field at a time. Templates save one entry at a time through the same command's `template_put` (one `{id, title, prompt, output, next, class?}` entry) or `template_remove` (an id), and role guidance through `role_guidance_put`; each edit carries exactly one of these fields or `policy`. A canonical policy over 48 KiB is refused as `policy_too_large`.

**Record pickers.** The **Release manager record** picker lists only eligible, enabled records offering `release-manager-v1` that are not reviewer records. The reviewer picker leaves out the configured release manager. The labeller picker lists every eligible, enabled record. `catalog-index` records carry `capabilities`.

All values are exposed on the machine-readable `workflow-index` node's `policy`. Policies stored by earlier builds (the 5-, 10-, 16-, 18- and 27-key shapes, the last being 0.3.0) are accepted only at the restore boundary and migrated with the defaults; any other shape is rejected. Because the routing-policy digest covers every routing field, decisions recorded before an upgrade are re-evaluated on the next capacity refresh before they can claim.

**Pane orchestration list.** Config lists every agent pane in the current native session on this host, from the window's `cx.agents` observation (at most 64 rows, with an "N more" note; titles are UTF-8-safely truncated and never identity). Rows are ticked by default:

- Managed workers are listed by durable `worker_id`. Unticking adds the worker to `excluded_workers`; automatic progress-report requests and automatic rollover skip it. Observation, mailbox reads, receipts and owner actions continue; a tick never stops or retires anything.
- Hand-opened agent panes are window-scoped (pane id, window incarnation, native session, host). Their marks are eligibility only and not durable. Ticking never adopts a pane; that needs the explicit **Attach pane N as ORCH+ worker…** (see [Explicit verified attach](#explicit-verified-attach)).

Pause holds new work, not committed receipt or decision settlement. Launch records, accounts, models and host configuration stay in **SPAWN Config**; ORCH+ Config cannot submit commands or credentials.

**Worker context usage.** Workers may add `context_used_pct` (integer 0–100) to READY and HEARTBEAT; any other value rejects the report. ORCH+ stores the latest value with its report sequence and shows it as "context N% (worker-reported)".

## Roles, families and role guidance

Every managed worker has a `role` that ORCH+ sets at queue time: `builder` (default for assigned and sourced work), `reviewer`, `release_manager`, `labeller` or `coordinator`. Workers restored from 0.3.0 get `coordinator` or `builder`. Reviewers, the release manager and labellers are short-lived managed workers that ORCH+ queues itself on their Config record (`reviewer_records`, `release_manager_record`, `labeller_record`) through the ordinary provision/launch path. They are never quota-routed and count against the 32-worker cap (a full cap holds the work with backpressure; nothing is dropped).

`role_guidance` text for a role is prepended to every assignment of that role, including typed `queue` tasks (role from `role`/`coordinator`), coordinator starts, `adopt` and approved `dispatch` proposals, as well as the reviewer, release-manager, labeller, plan, board, inbox and template assignments. Guidance is not enforcement; ORCH+ does not restrict tools by role. Restrict tools in the SPAWN record's CLI flags.

**Families are declared, not verified.** A record's provider family is `family_map[record_id]` or, unmapped, its provider (Claude → anthropic, Codex → openai, Kimi → moonshot, Agy → google, Grok → xai, Muse → muse). OMP and unknown providers have no family until mapped. ORCH+ cannot see which model a record actually runs; cross-family enforcement is as good as the map.

## Scope, checks and checkout facts

Queued work may declare `files`, `scope = {paths, systems}` (default: `paths` = `files`), `checks = [{check_id, argv}]` and `base_ref`. For work that declares any of them, ORCH+ builds a canonical **assignment manifest** `{checks, files, scope, base_ref?}` (≤ 4096 bytes), sends its exact bytes in `mailbox_provision.manifest` and stores its digest on the worker; the helper modes below need a record with `check-runner-v1`. SPAWN binds the digest into the provision digest and writes the bytes as the mailbox's `manifest.json`; ORCH+ re-derives the manifest before provisioning (`manifest_mismatch` otherwise). `scope.systems` is brief text only: ORCH+ cannot see outside systems, and workers must ASK before touching an unlisted one.

The SPAWN producer helper publishes two **helper-only** reports, which workers cannot send with `report`:

- `checkout` → CHECKOUT `{worktree_path, common_dir, branch, head, base?, changed_files (≤512), changed_overflow, changed_total, dirty}` computed by git (committed changes since the merge base with `base_ref`, plus uncommitted and untracked paths). When the manifest has no `base_ref` (absent or empty), the first `checkout` pins the current HEAD in `<mailbox>/checkout-base` (beside `provision.json`, written atomically, first writer wins). Every later checkout reports `base` = merge-base(checkout-base, HEAD) and includes committed changes from `base...HEAD` in `changed_files`. A `checkout-base` that is not a regular file holding one 40- or 64-hex revision is refused with `storage_error`. A hyphen-led `base_ref` is still treated as unusable and never pins.
- `run-checks <check_id>` → CHECK_RESULT `{check_id, argv_sha256, exit_code, output_sha256, head, ran_at_ms}`. The argv comes only from the authenticated manifest and runs without a shell; a result counts only for the `head` it ran on.

Gates from these facts (all host-consumed owner gates; see [Owner gates](#owner-gates-loop-caps-and-stale-claims)):

- **`shared_checkout`** at queue time, before provisioning: with `checkout_roots` configured, work whose cwd lies under a root and is the same as, or nested with, another live same-session worker's cwd or reported worktree waits for **Launch anyway** or cancel. A CHECKOUT later reporting such a shared worktree raises it once per path. Other sessions' workers are not visible. No roots: off.
- **`file_overlap`** at queue time: declared files intersecting files declared or changed by another live worker.
- **`scope`** on CHECKOUT: changed paths outside `scope.paths` (or an overflowed list). Accepting it is durable on the worker (`scope_accepted`); shared-checkout acknowledgements likewise (`shared_acked`).

A CHECKPOINT whose `worktree_ref` differs from the latest CHECKOUT holds landing as `checkout_mismatch`; an unaccepted out-of-scope checkout holds it as `scope_open`.

## Review (cross-family judge and rework)

A builder's REVIEW_READY (or an approved coordinator `review` proposal) opens one durable review per work in `dispatch.reviews` (≤64): `queued → requested → approved | changes_required → … | capped | cancelled`. Each round launches a **fresh reviewer worker** on the first configured `reviewer_records` entry (owner order) that is current and eligible, is not the builder's record and, with `enforce_cross_family` on, has a declared family different from the builder's. None configured → `reviewer_unavailable` gate; family missing → `family_unknown` gate (both offer recheck once Config changes). After ACCEPTED the reviewer receives one `review_request {review_id, round, question_id="implements_task_v1", builder_work_id, task_ref, plan_ref?, plan_revision?, source_ref, artifact_revision, scope_paths, findings_prev}` and answers the fixed question "Does the change at `<source_ref>@<artifact_revision>` implement `<task_ref>` as specified, without changes outside `<scope_paths>`?" with one REVIEW_RESULT `{review_id, round, artifact_revision, outcome: approved|changes_required, findings[≤32 {finding_id, path, line?, summary}], summary?}` — no score or confidence. It is finished automatically once the result settles (`auto_finish:reviewer`). A reviewer that ends without a result holds the review (`reviewer_lost`); ORCH+ never relaunches one on its own.

`changes_required` sends the builder one typed `rework {review_id?, round, artifact_revision, failed_checks[{check_id, exit_code}], findings}` carrying only the findings (and, with enforcement off, the declared checks that failed at that revision). The builder's next REVIEW_READY on a new revision opens the next round with `findings_prev`. Rounds are capped by `review_rounds` (1–2): a round past the cap ends `capped` and asks the owner. A new artifact revision voids every earlier approval of that work. Only reviewer workers file REVIEW_RESULT: a coordinator's is refused `review_unauthorized`, the builder's `reviewer_is_builder`.

A review's `void` is `{artifact_revision, at_ms}` when a newer checkpoint voided the approval, or `{target_revision, at_ms}` when a landing refresh (target moved / `stale_target`) voided it; earlier records keep `artifact_revision`.

## Proof rule

`codec.verify_landing_proof` decides every landing grant from durable facts; it is recomputed on every commit (`item.proof`).

| `enforce_cross_family` | Proof | Helper checks |
| --- | --- | --- |
| on (default) | approved REVIEW_RESULT for the exact source revision from a reviewer worker that is not the builder, not on the builder's record, and of a different declared family | evidence only (`check_refs` of passing results) |
| off | every declared check has a helper CHECK_RESULT with exit 0 on the exact source revision, **and** an approved review from a reviewer worker other than the builder (same family allowed) | the proof |

Failure codes: `review_required`, `reviewer_is_builder`, `reviewer_record_is_builder`, `review_stale`, `review_not_approved`, `family_unknown`, `family_same`, `checks_undeclared`, `check_missing`, `check_stale`, `check_failed`. The **signer rule** adds: a configured `release_manager_record` carrying `release-manager-v1`, current and eligible (`release_manager_missing`, `release_manager_refused`), on neither the builder's nor the approving reviewer's record (`release_manager_is_builder`, `release_manager_is_reviewer`). The worker's latest checkpoint must still be fresh for the revision with passing checks and no holds.

## Owner gates, loop caps and stale claims

Gate kinds: `owner_question`, `coordinator_proposal`, `native_input`, `landing_approval`, `quota_fallback`, `loop_cap`, `stale_claim`, `legacy_grant_outstanding`, `shared_checkout`, `file_overlap`, `scope`, `reviewer_unavailable`, `family_unknown`, `deploy_hold`, `intake`, `label_unknown`. The host-consumed kinds (`quota_fallback`, `loop_cap`, `stale_claim`, `shared_checkout`, `file_overlap`, `scope`, `legacy_grant_outstanding`, `reviewer_unavailable`, `family_unknown`, `intake`, `label_unknown`) are answered from fixed options, never free text, and send the worker nothing; the others (including `deploy_hold`) deliver an immutable `owner_decision` reply. Answers carry a tagged source: `{kind="owner", …origin}` or `{kind="policy", policy_revision, rule="auto_approve:<kind>"}`; untagged answers from earlier builds are read as owner answers only at restore.

A coordinator proposal that ORCH+ refused itself (`source.kind = refusal`) reads "Refused by ORCH+ (<code>), not an owner answer: <reason>".

**Loop caps.** Every loop that re-engages a model or worker stops at `loop_cap` (1–10, default 3) with one `loop_cap` gate whose evidence names `loop:<name>`, target, count and cap: `rollover_checkpoint`, `report_request`, `full_retry` (owner retry after backpressure), `landing_refresh`, `landing_grants` (structural bound 8 per item), `check_rework`, `review_rounds` (cap `review_rounds`), `deploy_attempts`, `labeller`, `template_chain` (bound 8 steps). **Allow more** resets only that loop; the structural bounds and the review-round cap offer only **Keep it stopped**, which is final. Code-only waits (quota re-evaluation, transport backoff, readbacks) stay time-bounded.

**Stale claims.** A claimed or uncertain action older than `stale_claim_min` minutes (default 30, 0 = off) opens exactly one `stale_claim` gate (**Keep waiting** / **Open recovery guide**). Ageing restarts after a host restart; a backpressured action never ages. ORCH+ never takes over, re-sends or settles a claim because of its age; the gate is superseded when the claim settles.

## Autonomy inside plan scope

A coordinator proposal or landing approval is **in scope** when its work came from an imported plan or the board (`source.kind` `plan`/`board`), declares `scope.paths`, has no open `scope`, `file_overlap` or `shared_checkout` gate, and, for `dispatch`, names a current eligible record. For in-scope proposals whose kind is in `auto_approve_kinds` (subset of `dispatch`, `report`, `review`, `landing`; empty by default) the session policy answers, tagged as a policy answer; never on manual work. A landing approval is policy-answered only once its proof and signer are complete, and never while paused. Out-of-scope proposals always wait, and the gate says why. A proposal sent while the session is paused is refused (`session_paused`) and a proposal naming work without a retained CHECKPOINT of its project is refused (`scope_mismatch`): ORCH+ answers its gate `reject` itself (source `{kind="refusal", code}`, shown as refused by ORCH+, not an owner answer) and delivers one `owner_decision`; the coordinator's report lane is never held and it may propose again, even with the same `proposal_id`. Pause answers nothing by policy; on resume each still-pending in-scope proposal is evaluated once against the current `auto_approve_kinds`.

Approved proposals (owner or policy) execute exactly once through a durable execution record written with the effect: `dispatch` queues the proposed record and prompt as new work inheriting the parent's source and scope; `report` sends one `report_request`; `review` opens a reviewer-worker review of that checkpoint; `landing` approves the matching landing item. `rollover` is recorded only. Policy never bypasses loop caps, proof, capacity or pause. Decisions answered before 0.4.0 are never executed.

## Mailbox lifecycle and nightly sweep

Each managed worker generation has one private report mailbox on its execution host, provisioned by SPAWN (`mailbox_provision`) under the configured permitted root before launch. ORCH+ reads reports through SPAWN, publishes exact ACKs and replies, and the producer confirms ACKs with a cumulative receipt watermark. A confirmed watermark sets `compaction_pending`; the next poll issues `mailbox_retire mode=compact`, deleting only the confirmed prefix. `mode=retire` happens only after an explicit finish or coordinator release, a settled generation (receipts, replies, notifications drained) and an exact native stop observed `exited` or `absent`. Retirement leaves a small SPAWN tombstone; the worker record is reclaimed later. Uncertain retirement is never repeated.

The nightly sweep retires orphaned mailboxes without an OS timer. On normal window ticks the due slot is today's `sweep_time` once passed, else yesterday's. When it is newer than the session's durable last run, the window sends one `sweep` with the slot's local date (`catch_up` when more than 15 minutes late), so a missed time runs exactly one catch-up for the latest slot. The host refuses any date at or before its last run (`sweep_already_ran`); a refused request is retried by the same window only after 10 minutes. Decisions, checked in order per worker with a mailbox:

| State | Decision | Reason code |
| --- | --- | --- |
| Mailbox already retired | nothing | `retired` |
| Control route needs continuation, or another controller incarnation | keep | `continuation_required` |
| Any uncertain effect | keep | `uncertain` |
| Retirement issued and unsettled | keep | `retirement_pending` |
| Other queued, claimed or backpressured effect | keep | `effect_pending` |
| Coordinator with unresolved owner generation or executors | keep | `owner_unresolved` |
| Rejected report held | keep | `report_held` |
| Worker held | keep | `held` |
| Never bound to a launched pane | keep | `unlaunched` |
| Not stopped, `compaction_pending` | compaction queued | `compaction_pending` |
| Not stopped | keep (the sweep never stops) | `live`, or `finishing` |
| Stopped, not settled | keep | `unsettled` |
| Referenced by active rollover, landing or review work | keep | `referenced` |
| Exact stop observed, settled, unreferenced | `mailbox_retire mode=retire` queued | `stopped_settled` |

Queued effects follow the normal claim, grant, deadline and uncertainty rules. The sweep never stops a worker, infers a stop or touches another session. Runs are logged in `dispatch.sweeps[session]`: `last_date` plus a ring of 14 runs (date, registry revision, time, catch-up flag, counts, up to 64 per-worker decisions). Config (**Mailbox sweep**) and the workflow card show the last run. Turning the sweep off stops new runs and keeps the log.

## Quota routing (USAGE capacity)

With `quota_routing` on, ORCH+ consumes USAGE's read-only **capacity v1** export (owner-enabled and revocable in USAGE Setup). The window opens USAGE's public native `usage.capacity` block on the controller's host/session like a SPAWN bridge (background **SPAWN bridges** tab; at most one per controller; an idle reader is reused after reload; the bridge sweep closes other idle leftovers, never one with a request in flight), sends `{ev="action", act="usage.capacity"}` with a bounded `snapshot`/`page`/`validate` request and reads only the keyed `usage-capacity-response` node (`USAGE_CAPACITY v1`), correlated by request ID. Pages of one immutable revision are assembled in index order; byte length and SHA-256 must equal the declared `size` and `revision` before parsing (≤ 2 MiB, else no evidence). Hashing is incremental, at most 16 KiB per window tick (`quota.HASH_BLOCKS_PER_STEP`); an interrupted step fails closed as `hash_interrupted`. `validate` is requested only after the last byte is hashed and parsed, and USAGE validates that revision before the host records it. Failures retry on the next automatic refresh (30 s) or an explicit one. No USAGE private state, provider call or credential is touched, and no account is guessed.

**Normalization** (`quota.luau`, at most 24 records per evidence set: pending routed records first, then the allowlist, then other eligible records):

- **Binding:** only USAGE's exact join `(scope.spawn_join.namespace, host_key, config_revision, account.id)` = SPAWN catalog `(namespace, host_key, config_revision, record id)` with a `profile_binding`. Labels, `capacity_binding`, equal percentages and titles are never identity. A local publication must agree with USAGE's `current_roster`.
- **OMP consumers:** a record matching a scope `consumers[].id` with `account_ids = ["<account id>"]` is evaluated against that account under the same rules; locally the same consumer must appear in `current_roster` with the same `definition_revision` and `account_ids` (else `local_roster_changed`). Unassociated: `consumer_unassociated`.
- **Source:** `current`, unchanged generation/profile generation, no clock skew.
- **Readings:** every bound reading exists, has a canonical ID inside the binding and numeric remaining percentages; unavailable or last-known windows carry no proof. Duplicates use the newest observation per window/pool; equal-time disagreement is a conflict.
- **Result:** `known` with the lowest remaining % across bound windows, oldest observation, earliest reset, earliest weekly (`seven_day`) reset, binding and principal digests, and a `usage` reading (below); otherwise `unknown` with a reason (`unbound`, `consumer_unassociated`, `ambiguous`, `binding_unverified`, `source_*`, `local_roster_changed`, `reading_missing`, `identity_mismatch`, `unavailable`, `conflict`, `future_timestamp`, `stale`, `reset_passed`, `unit_unknown`, …). The host re-checks freshness with its own clock: past USAGE's lease, older than `quota_max_age_ms` or past a reset is unknown, never a refill.

**Rule.** For each new task or coordinator start (including plan, board, inbox, template and approved `dispatch` work): eligibility and the explicit allowlist first, then quota (sufficient = fresh, bound, strictly above `quota_reserve_pct`), then owner preference. The chosen record launches unchanged when sufficient. Otherwise allowlisted alternatives are ordered by earlier weekly reset, then record ID. An alternative that changes provider, account/profile (including an unknown or different USAGE principal) or model needs the matching `initial_dispatch_*` permission. The first permitted sufficient alternative is selected; if the best sufficient one is not permitted, the work becomes a durable `quota_fallback` gate naming both exact tuples, the routing-policy digest and the USAGE, catalog and evidence revisions. **Approve** applies to that work only and is refused if any of those changed or the destination is no longer sufficient; **Reject** keeps it held. With nothing sufficient the work is held (never provisioned) and re-evaluated on fresh evidence (about every 30 s), **Re-check capacity now** or **Cancel this queued work…**. Each decision is recorded on the worker (`routing`: requested/selected record, authority, candidate reasons, policy and evidence revisions, decision digest, last eight outcomes). Off: dispatch is exactly the chosen record.

**Launch-time check.** The decision binds the USAGE and authorization revisions. Immediately before claiming the launch the window asks USAGE to `validate` that revision; the claim must carry a `current` result validated within 30 s, and the granted host claim stores it (`claim.capacity`). A changed, expired, revoked or incomplete revision means refresh: the provisioned record can only stay or be held. Routing-policy edits re-evaluate unlaunched routed work and void stale fallback gates. This is not a provider-side reservation.

**Rollover routing.** The successor of a worker or coordinator rollover is routed when its grant is due. The predecessor's record is preferred; alternatives are that kind's own allowlist and `*_provider/account/model` permissions. An unpermitted best alternative becomes a `quota_fallback` gate on the running predecessor, bound to the rollover (`dispatch.rollovers[*].quota`); reject holds it as `quota_fallback_rejected`. With nothing sufficient the rollover is held; the predecessor keeps running.

**Concurrency ledger.** Each routed worker's `routing.reservation` moves `reserved → claimed → launching → active → released` (`uncertain` keeps occupancy), bound to the decision digest and evidence revision. Released on verified stop or retirement, a definitive pre-pane failure, or a hold before launch. With `concurrency_limit` > 0, exceeding it holds with `concurrency_limit`; a rollover successor may overlap only its predecessor. Restore validates phases, history (≤8 edges) and that only provisioned routed work holds a reservation.

**Selector evidence.** SPAWN exposes only owner-entered `selector_evidence`, so every model/profile selector shows as **unverified** (`unverified_owner_text`/`unverified_absent`). Not covered: landing, reviewers, release manager and labeller keep their records; reserves are not per window/pool. Unlaunched routed work moves to a continued route and is re-evaluated there.

## Per-worker USAGE deltas

`quota.normalize` attaches to each known record a reading `usage = {account = {canonical_ids (SHA-256 of each USAGE canonical id, sorted), generation}, windows[≤16 {key, pool, remaining, resets_at_ms, observed_at_ms}], observed_at_ms}`. From current, unexpired evidence ORCH+ stores `usage_before` when the launch/adopt outcome binds the pane and `usage_after` at DONE, refreshed at finish when newer — never from `claim.capacity`, never copied to a rollover successor. Projected workers carry `usage_before`, `usage_after` (nil while running) and `usage_shared_with` (other workers with readings on the same account whose observation spans overlap); the health card computes `quota.usage_delta` per window, or says why it is not comparable (unbound, different account, reset crossed). USAGE is percent-only and account-wide: a delta is never one worker's exact use.

## Recovery workflow

**Inspect**, **Recheck**, **Reveal owner** and **Stop assistance…** are window-handled requests returning bounded events. Observations are limited to the source pane's host. Controller aliases are associated by the host-issued nonce on the exact native surface, never by ID equality. Stop assistance closes only the uniquely nonce-associated controller block; it never guesses a target. If an alias cannot be proved, inspect or stop the recorded owner manually. Native snapshots are not claimed to enumerate all ownership.

Closing a controller **does not clear ownership**. Reopen ORCH+, choose the registration and **Recheck**. An observed-unavailable result makes current activity unknown, not stopped, and retains pending executors; an observed positive executor count cannot be overridden by attestation. After restore, a retained positive executor count is **unconfirmed**. Only with an observed-unavailable owner, unknown activity and unconfirmed executors does **Verify retained executors and unavailable owner…** appear; it records `executors_verified=true` as operator-attested evidence. Then **Begin fenced recovery** and confirm the displayed owner/generation/revision (intervening registry changes invalidate it). Recovery tombstones that owner and advances its generation; it never launches a replacement.

ORCH+ retains the **dispatch action/request/executor ledger**; a zero inspection count does not clear it. A restored uncertain claim is reconciled only through the displayed exact action/executor/revision confirmation after unavailable-owner evidence and operator verification; this records the attestation and holds the work, never repeating an effect. Resolve retained actions before ordinary owner recovery.

**Continuation.** **ORCH+ Continue controller in this window** (palette, in the window that should become the origin) confirms the displayed owner/generation/revision after you verify old executors stopped. It records a new control origin while keeping claims, counters, pending decisions and coordinator uncertainty. Inspect original SPAWN outcomes read-only before attaching workers; a missing or oversized outcome is not permission to resubmit.

Never-launched work follows the continued controller: a queued or provisioned ordinary worker of the same owner, generation and alias whose launch is absent or never-claimed `ready` has its route and never-claimed `mailbox_provision`/`launch` requests moved to the continued window with the same request and action IDs. A provision claimed in the old window settles through the continued route, and its launch is built there (**Run queued launch**; quota routing re-evaluates). Claimed, backpressured, uncertain or settled launches, adoptions and rollover successors (`successor_launch_fenced`) keep their route.

Continuation **fences** (`resolved` with `never_claimed` or `pre_effect_refusal`) a provision, launch or adoption it cannot move because SPAWN already received it, plus moves refused for size. Such work shows **Cancel never-launched work…** (`cancel_work`). When SPAWN received the request, the window first reads SPAWN's `status` of it and sends query and answer bytes with the command. The host accepts only definitive evidence: `missing`, terminal `rejected`, or retryable pre-effect `full` (including an expired or earlier-boot challenge). A live challenge refuses `authorization_live` (retry after 30 s); other outcomes `spawn_outcome_open`; another request's status `binding_mismatch`. Without a provisioned mailbox, cancellation removes the worker and its settled actions, gates and exclusions and, for a coordinator start, releases the never-bound orchestrator reservation (`coordinator_unresolved` unless plainly `reserved`). With a provisioned mailbox, the same checks run first; the commit records `withdrawn` (op, fenced action ID and evidence) on the worker, keeps the resolved fenced action (so routing and the concurrency reservation treat the work as settled), drops the worker's other unclaimed `ready` actions, queues one `mailbox_retire` (`mode="retire"`, zero floors, no stop) of the never-used mailbox and answers `withdrawal_retiring`; SPAWN accepts that retirement without a native stop and fences the unconsumed launch challenge in the same save. Nothing is stopped or re-sent; SPAWN authorizes only an action it observes claimed on its current route. The same control covers a `mailbox_provision` SPAWN definitively rejected (no read needed, even while routing shows `selected`). When SPAWN rejected the launch or adoption after provisioning (stored only before any native call), cancel likewise queues the exact retirement and answers `withdrawal_retiring`. On `retired` the worker is reclaimed and a coordinator start releases its orchestrator reservation; a definite refusal holds the worker and cancelling again issues exactly one fresh retirement; a pending or uncertain retirement is never issued twice (`retirement_unresolved`). `withdrawn` is part of the validated worker schema, so a restart mid-retirement restores it. A claimed launch that became uncertain is never withdrawable. Regression: `dispatch/withdraw_fenced`, `health/withdraw_fenced`.

**Worker reattachment.** **Continue after reload / reattach explicitly…** selects the exact worker and attests its identity; the scoped proof rejects changed target/owner evidence but not unrelated health ticks. SPAWN checks attachment independently. Launch, mailbox and enrolment identities never change; only the control route does, and old callbacks stay fenced. The control also appears for any launched generation awaiting acceptance (including a rollover successor). A generation reloaded between its ACCEPTED and SPAWN `accept` may meet `authorization_revoked`; ORCH+ keeps `accept_pending` and re-issues the same acceptance on the attached route. Revocation is pre-effect for every operation: a revoked `native_wake`, publication, read, compaction/retirement or stop completes as `authorization_reissue` and its lane re-issues it on the continued route; a revoked `attach_worker` completes as `reattach_required`; launch, adoption and provisioning keep an explicit hold. Non-holding diagnostics never overwrite a held worker's recorded cause.

**Unknown outcomes stay held.** Continuation cannot satisfy unavailable-owner recovery or reactivate an uncertain coordinator. A coordinator restored `uncertain` resumes (`running`, or `retiring`) only when its exact attested attachment commits and none of its executors remains claimed, uncertain or counted; a recovery intent, retired-owner tombstone or restored-pane hold keeps it uncertain.

**Guided reload recovery.** **ORCH+ Reload recovery guide** (palette; also opened after continuation) reads SPAWN's owner state with a read-only `owner_status` request and lists the remaining steps: continue the controller, recover the previous SPAWN owner, reattach each worker (with its recorded pane), and how many uncertain actions are being read. It acts on the session's only controller with a recorded owner, else the focused one; the controller shows the same **Reload recovery checklist**. Steps open the existing explicit controls; the SPAWN step opens **SPAWN: Running agents**. ORCH+ never attests, retries or adopts by itself.

Operator attestation is labelled as such. Tern's `UiEvent` and button APIs do not authenticate a human or isolate a same-user caller; nonces correlate aliases and are not credentials.

## Authority and persistence

- One host-module registry owns the `authority_state` KV value; windows never write authority. Saved block data holds only view/registration/alias binding and prior-initialization evidence.
- A reducer builds a candidate; only a successful `tern.kv.set` publishes it. Failed admission, release or recovery leaves ownership intact with an error. Committed request replay returns the original result; changed-body reuse is rejected; a refused request is never silently retried.
- Every write first checks that persisted authority still equals the committed value (exact saved JSON text first, deep compare only on difference). Removed, unreadable or changed storage freezes changes. Refusals, exact replays and no-ops never write. The 1 s workflow tick clones the registry only when derived health or due flags changed. Host events render controller blocks only when committed authority or store status changed; otherwise only the originating block, and only on a visible change.
- Sequenced observations (`observation_seq`) and polls retain no command outcome: the `command_seq` barrier and per-worker observation cursor make the exact latest replay idempotent and older ones refused (`stale_command`). An observation repeating persisted native state commits nothing until `stale_ms/4` old, except on a state or delivery-error change, busy/erroring evidence with a pending wake, a recheckable native-input gate, exit or restored-coordinator evidence. Effect outcomes are kept only while they are their action's current evidence (a claim until its result settles; a lost outcome while its grant is current; one result per action without `response_bytes`), so a duplicate result replays read-only and different bytes conflict. Outcomes retained by earlier versions are compacted at restore.
- An idle poll commits nothing (`mailbox_idle`) when nothing is due (publication, acceptance, compaction, decision, wake, stop/retirement, requested report, rollover, assembly, held report), the last read of the next slot was empty, the poll follows persisted idle evidence under `stale_ms/4` old and, for a watermark poll, every receipt is compacted. An unobserved working blip therefore delays a report by at most about `stale_ms/4 + poll_ms`.
- The window re-sends a claim for a still-`ready` action after 1/2/4/8 s of awake backoff and replays a captured SPAWN outcome awaiting receipt after 1/2/4/8/15 s. A delivered outcome is marked `lost` after 5 min of awake time with no host progress, or 15 min total. A duplicate claim refused because this window's own claim won does not hold the action.
- Encoded authority is capped at 8 MiB; the last 512 KiB is reserved for completing coordinator bindings, retirement/recovery and genuine safety facts. Registration, admission and generic uncertainty stop at 7.5 MiB. Durable outcomes are capped at 4,096 with 1,024 reserved (ordinary operations stop at 3,072). Exact replay consumes neither outcomes nor grants.
- Inside either reserve, settlements run one at a time across sessions: while any recovery intent is current, other retirement, release and recovery requests are refused `settlement_pending` naming the holder. Confirm the intent in the view that began it, or reload the host (restore withdraws pending intents). A genuinely new safety observation supersedes it.
- If a fresh observation or uncertainty fact cannot persist, later release/recovery is blocked behind a visible safety fence until storage is repaired and the host restarted; a failed observation is never evidence of quiescence.
- Restore validates the complete schema, keeps occupied owners uncertain, fences old recovery intents and persists the new execution epoch before exposing authority. Missing established storage, malformed JSON or invalid state require backup restoration and **Recheck restored store**. Schema-1 state is quarantined unchanged; there is no automatic reset.
- First-use initialization (**Initialize first-use authority…**) assumes a fresh ORCH+ and SPAWN pair. ORCH+ request ids and logical session ids are per-store counters, and SPAWN keys retained request fences on `logical_session_id`/`request_id`. Re-initializing ORCH+ alone over retained SPAWN `dispatch-v1` state therefore reuses ids SPAWN has already fenced, and SPAWN refuses them fail-closed with `content_conflict` ("Compacted request ID reused"). After losing the ORCH+ store, restore its backup, or reset SPAWN's plugin state together with ORCH+'s; never re-initialize ORCH+ alone.
- KV durability is the native store's guarantee, not fsync/power-loss. One active native host worker per plugin data directory is assumed.

Coordinator reservation, its immutable task/work/enrolment and the first provisioning intent commit together. Provisioning must return a complete mailbox contract before the launch intent exists. Worker pane aliases bind only through the correlated SPAWN outcome.

## Dispatch and mailbox contract

`dispatch.luau` is a pure extension of `state.luau`. Host events use `kind="dispatch"` for catalog/queue, USAGE `capacity` evidence, `cancel_work`, effect claims/results (a routed launch `claim` carries `capacity_validation`), polling, report requests, observation, policy/pause/resume, owner decisions, `finish`, coordinator `retire`, continuation, work sources (`plan_import`, `board_intake`, `inbox_intake`, `template_start`) and owner landing/deploy controls. Every intent needs an origin-scoped monotonic `command_seq`; `claim`, `result` and `lost` forbid it and are bound to exact grants. A durable highwater rejects old intents after settled-command history is reclaimed. External direct `intake` is rejected; reports arrive only as correlated SPAWN mailbox pages.

Before an effect the host commits the exact request and an exclusive executor claim. The window checks the controller alias, registration, native session, host and window incarnation before and after async boundaries; callbacks receive fresh contexts. Grants use native nodes `main.dispatch-state` (`orchplus.dispatch`) and `main.dispatch-request` (`orchplus.request`, exact bounded request JSON). Every projected claim, including per-action `main.dispatch-action-<id>` nodes, is exactly `{executor,epoch,grant_id}`; `claim.capacity` stays on the durable host claim. Newly queued work never replaces an outstanding claimed action in the machine nodes.

Each attempt has a persisted `claim.grant_id`. Result callbacks use `act="dispatch-result/<grant_id>/<execution_window_epoch>"` with the raw frame as `value`. Delayed callbacks cannot settle a successor attempt. Only a SPAWN `full` carrying `retryable=true, effect_started=false` authorizes an exact-request retry under a fresh grant; other ambiguous writes stay occupied. Such backpressure is rechecked after 5 s of awake time through the **Recheck unexecuted capacity refusal** path, one per lane, at most 120 times. A claim refused `full` before any grant stays `ready` and is retried every 5 s of awake time, at most 120 times, then held for **Run queued … in its original window**. Every `full` must carry `resource` (≤96 bytes), `current` (≥0) and `limit` (>0); `retryable`/`effect_started` occur together.

The window retains an observed SPAWN outcome until `main.dispatch-state.receipt` names the committed `action_id`, `grant_id` and `response_sha256`; until then it may replay only that observation. Observation IDs are deterministic. This UI receipt is separate from worker ACKs.

**Host sleep.** The 30 s effect deadline and receipt-replay deadline count awake time: the 500 ms observation timer counts a gap over 5 s as one tick, so suspension extends deadlines and never shortens them or retries an effect. SPAWN's adapter applies the same rule to helper `process.run` timeouts; a child killed by the runtime across a suspension still settles uncertain. SPAWN's authorization challenge keeps its 30 s host-clock window; one that expires during sleep is refused definitively; queue the work again.

**Idle-wake helper.** Tern 0.9.12 does not wake an untouched window when a window `tern.timer` comes due. The window runs plugin timers only after something else wakes it: input, a control request, a rendered block frame or a finished child process. Without help, an untouched controller window therefore stops observing and dispatching. Under Xvfb this stall lasted minutes; host timers are unaffected. This is a Tern bug, and the helper is a workaround for it.

While the window drives an *active* controller that has timed work, it keeps exactly one short wait child in flight. Timed work means any of:

- a registered worker, whose observation and poll run every `poll_ms`;
- an effect driver;
- a capacity or backpressure backoff;
- a USAGE read;
- an owner-started recovery or withdrawal read.

Inbox or board polling this window performs counts as timed work, so a controller with only an intake inbox or board configured keeps the helper running (Health: **Idle-wake helper active: polling the intake inbox** / **the board** / **the intake inbox and board**). A remote host's inbox, or an unconfirmed remote board, does not.

The child is `sleep 2`, or `ping -n 3 127.0.0.1` on Windows; both are argv-only with no shell. It does nothing: its exit wakes the window, every due timer runs, and its callback starts the next child. The 2 s interval stays under the 5 s suspension gap, so an untouched window is not counted as suspended.

The helper does not run in these cases:

- the controller has no such work;
- the controller is awaiting continuation;
- the window drives no controller;
- the VM is a host VM (native tests).

A child that fails or exits early stops the helper for that window VM. Where `tern.process` is unavailable (iOS), the helper does not run at all.

The controller's Health card shows **Idle-wake helper active: …** with its reason, or **Idle-wake helper unavailable: …**. Covered by `health/idle_wake`.

**Automatic read-only reconciliation.** An `uncertain` action with its exact claim gets up to four `status` reads (2 s, then 10, 30, 60 s of awake time apart) through the same route, grant and fencing as **Read retained SPAWN outcome (never relaunch)**, never claiming, re-sending or using oversize replay. A definitive outcome settles; `pending`, `missing` or SPAWN `uncertain` keeps a mutating action uncertain, then a notice and the owner control remain. Coverage is independent of selection: up to 16 uncertain actions are listed, one read per bridge lane at a time.

**Retained uncertain reads.** A read-only operation (`mailbox_read`, `catalog`) changes nothing until its outcome commits, so an uncertain read is evidence, not a pending effect. SPAWN `missing` for it lets the window send `read_missing` with the exact status bytes (`resolution.evidence="read_lost_no_effect"`, with `status_sha256`); an explicit attested reattachment supersedes it otherwise (`read_superseded`). Either way the read releases its executor counts and the lane re-reads from the durable cursor; a late outcome is stale. Mutating effects (publications, retirement, provisioning, launch, adopt, stop, `native_wake`, `attach_worker`, `accept`) keep strict holds and block reattachment until reconciled.

**Publication readback.** ACK and reply objects are immutable bytes. After one non-definitive automatic read the window sends `readback_publication` (≤3 per publication; owner control **Read back and re-publish the exact same bytes**). On the worker's continued route, while the receipt or reply part is outstanding and unconfirmed, the host resolves the attempt (`publication_readback`) and re-issues the same bytes; SPAWN reads back first and republishes only if absent (`already_published` otherwise).

**Effect slots.** At most four host actions may be claimed or uncertain at once; uncertain read-only operations do not count (they have no effect a new one could conflict with), claimed reads do, and an uncertain read still holds its worker generation. SPAWN's own limits (four per host, one per mailbox generation) apply independently.

**Window bookkeeping.** Per-action markers (set-before-send grants, reconciliation attempts, holds) are pruned only on positive evidence from the action's own surface (`complete`/`resolved`, or a different current claim), one action per tick. Readback counts and issued request IDs age out after 512. State for vanished workers is dropped.

Explicit operator commands use the `dispatch-operator-command` UI action; drivers use `dispatch-command`. The `command_result` projection keeps a failed operator command, bound to its `request_id`, until acknowledged or superseded.

**Bridge.** ORCH+ sends `{ev="action", id=<response node id>, act=<operation>, value=<exact request JSON>}` to the non-palette `spawn.dispatch` block and reads only `main.spawn-dispatch-response` (`spawn.dispatch.response`, `SPAWN_DISPATCH v1`, length and SHA-256 checked). Status reads address retained request IDs; only the original execution context may use exact immutable request replay for an oversized status outcome. At most one bridge per controller and lane (worker or catalog). Before opening one the window adopts an idle `spawn.dispatch` pane of the same session whose lease node (`main.spawn-dispatch-lease`, `SPAWN_BRIDGE v1`) shows no consumable challenge, live projection or verification, owned by this controller pane, alias and window; bridge-tab panes first; an idle bridge of another lane moves lanes. Bridges are never moved between tabs (a moved pane's `cx.session:surface` reads nil). The first opens with `new_block(..., "tab", {focus=false})` in a tab **SPAWN bridges**, later ones `beside` a pane there, never splitting the controller; a tab block landing outside the session is closed and the bridge opens beside the controller. Once per awake second the window closes one inert bridge of an earlier incarnation of this window, keeping two spares per controller. Held, live, busy, unreadable, other-window and current bridges are never closed.

**Report intake.** The host accepts complete `report-files-v1` pages and validates ACCEPTED, REGISTER, `reply_ack`, READY/HEARTBEAT/WAITING/BLOCKED, ASK, CHECKPOINT, CHECKOUT, CHECK_RESULT, REVIEW_READY, REVIEW_RESULT, LABEL, DONE (`output_ref?`), ROLLOVER_REQUEST, LANDING_REQUEST, LANDING_RESULT, DEPLOY_RESULT, COORDINATOR_PROPOSAL and negotiated COORDINATOR_RELEASE. Reports are data, not lifecycle grants. Cursor, ACK bytes/receipt chain, semantic state and the SPAWN accept outbox commit atomically before publication. Only a cumulative watermark permits compaction; only the matching `reply_ack` settles a reply. Transport `full`/`incomplete` never demotes a worker: an unadmittable read records backpressure without receipt, cursor or ACK. A semantically rejected report settles the read grant and is **held** with its exact bytes and diagnostic; that generation's report lane stops automatic reads and requests (outbound settlement still polls). **Re-check held report…** re-decodes the same retained bytes with current validation; valid bytes enter normal intake, nothing is skipped or substituted.

**Wakes.** ACK/reply publication is separate from native wake. Only `wake_status="awaiting_window"` with `wake_effect_started=false` and canonical `wake_target_request_id`/`wake_target_action_id` establishes an unstarted notification; ORCH+ settles publication and later grants a separate `native_wake` when the worker is safely idle. Busy and waiting-input workers are not interrupted; started/uncertain wakes occupy execution limits and never repeat.

Threads retain assignments, reports, questions, answers and delivery states. Health keeps native state, reported state, progress, freshness and gates separate; READY cannot override a native prompt or exit. Clock epochs stop restored timestamps counting as fresh. There is no screen parsing, transcript reading or raw terminal typing.

## Work sources (plans, board, inbox, templates)

**Start work…** picks a `/glitch-plan` file or the Tern board (`glitch_integration` off: board only; `default_work_source` is listed first). File bytes never cross the 8192-byte bridge: the window sends non-operator commands and the host reads files with `tern.fs.read`.

- **`plan_import {path}`** reads the absolute path (≤1 MiB) and parses it with `plan_import.luau`; parse problems refuse with the parser's code. Each session keeps at most four durable `plans`, pinned while any work is managed. Same path and revision: `plan_already_imported`; a new revision supersedes the import (unstarted tasks never start; same-id tasks carry running or done work over). Tasks are `queued_plan` until scheduled: checkpoint *k+1* starts only when every task of *k* has landed or finished; INDEPENDENT tasks of the open checkpoint start together up to `concurrency_limit` (else 32) and the worker cap; a sequential task waits for earlier tasks of its checkpoint. A task runs on `routes[class]`, else the `build` route, else holds `route_missing`. Work carries `source{kind="plan", ref="<path>#<task id>", revision=<sha256>}`, declared `files`, `scope{paths=files, systems}` and checks with ids `<task id>-c<n>`; flagged tasks show their flags and an unparsed check is never executed. A failed or cancelled task keeps the join closed.
- **`board_intake {board_path, card_id, text, tags, text_sha256}`** and **`inbox_intake {name, content_sha256}`** record a durable intake keyed by `intake_id = digest({kind, path, sha256})` (≤256). A duplicate id returns the existing record (`intake_duplicate`; a board re-send updates `card_id`), so racing windows create one work. The host re-hashes the card (`intake_invalid`) and reads `<inbox_folder>/<name>` itself (≤32 KiB, else durably `too_large`; a changed hash is `content_changed`, retried next poll). Card text over 4096 bytes: `card_too_large`. Durable refusals answer `intake_refused`. Intakes are `received` until their work launches (`accepted`); the window archives an inbox file only then. The class is a card tag `class-<route class>` (optionally `#`-prefixed; other tags never route) or an inbox `**CLASS**: <slug>` line; otherwise `label_pending` for the labeller. With `auto_launch_intake` off the work waits behind an `intake` gate (Launch / Cancel; cancel refuses `owner_cancelled`).
- **`template_start {template_id, input}`** (≤2048) starts a template chain. The controller sends it from **Start work… → From a template** (listed only when templates are saved; you pick one and enter its `{input}`, 1–2048 bytes) or from **Start…** on a Config → Templates row. A step's DONE with `output_ref` queues the template's `next` with that path as `{input}`. Eight steps stop the chain with a `loop_cap` gate (chain bound 8); a step without DONE or `output_ref` while a next exists retries against `loop_cap`.

The window reads `workflow-intake`: `workflow.intakes` (newest 64: `intake_id, kind, ref, state, work_id, refusal, hold, lane, label?`), `workflow.board = {path, cards[{card_id, intake_id, lane}]}` (the desired lane `queued|running|review|done` mapped to `board_lanes` titles and applied with `cx.board:move`; the window is the only board writer), `workflow.plans` and `workflow.chains`. `cx.board` exists only in the desktop window and has no change events, so board and inbox are polled; when the window is attached to a remote host the board path is the desktop's and is polled only after one confirmation through **Start work…**, and the inbox only when the window runs on the execution host.

Each imported plan has a controller card, "Imported plan · <title>", with the plan id, short revision, status and path. It then lists each checkpoint (number, title, task count, flags) and each task (id, title, state, independent, worker, hold, flags), eight rows per page.

## Work-class router and labeller

An intake without a class is labelled by a `labeller` worker on `labeller_record` (not gated by `auto_launch_intake`). After its ACCEPTED ORCH+ issues one `label_request {work_ref = intake_id, classes = route classes in order, text}`; the labeller answers one LABEL `{work_ref, class, reason?}` echoing that reply's action. A routed class routes in code on the same commit (the intake then launches like any classed intake); model and effort are whatever the routed SPAWN record runs — ORCH+ never sets CLI flags. Another class opens a `label_unknown` gate (**Route it** re-checks routes, **Label again**, **Cancel** → `owner_cancelled`). A labeller ending without LABEL (or refused) and every **Label again** count against `loop_cap` (`loop:labeller`); stopping refuses the intake `label_stopped`. The labeller auto-finishes after its LABEL settles. Intake holds: `label_pending` (no labeller — Config → Routing → Choose labeller…), `route_missing`, `label_running`, `label_requested`, `label_unknown`, `loop_cap`, `record_unavailable`, `full`.

## Ordinary worker finish and retention

**Finish ordinary worker…** is explicit; DONE never stops a pane. Unresolved gates, deliveries, report requests, wakes, claims or pinned review/rollover/landing/deploy evidence prevent finish. After settlement the exact native stop and mailbox retirement must complete before capacity is reclaimed; a failed or uncertain stop/retirement stays held.

SPAWN's one definite pre-effect retirement refusal is `producer_unsettled` (the helper journal still holds pending reports or unresolved control messages; nothing was removed). ORCH+ settles it as `retirement_refused`: the action completes, the worker is not held, the mailbox stays provisioned. Only the nightly sweep or **Retry mailbox retirement once…** issues one fresh grant.

When Finish is refused — by the window's pre-check (held or unaccepted phase, reattach needed, another control route, an unsettled effect, a pending report request or a rejected report) or by the host — a notice names the reason and nothing is stopped. After SPAWN refuses a retirement before any effect, Finish offers **Retry mailbox retirement once…** and sends it.

Only fully retired, unreferenced generations and safely settled generic gates are reclaimable. Report cursors and identity/intent fences survive history eviction, so a pruned ASK cannot recreate work.

## Verified worker rollover

**Roll over worker…**, or with **Automatic worker rollover** a policy `rollover` when an accepted, continued, non-excluded ordinary worker is idle at a clean point and its latest `context_used_pct` ≥ `rollover_threshold_pct`. The reducer rechecks every condition; a trigger only requests a checkpoint. Each rollover is a record in `dispatch.rollovers` bound to work, predecessor and successor panes, a 64-hex handover token and the controller owner/generation, with a revisioned history:

`requested → checkpoint_pending → checkpoint_verified → successor_granted → successor_created → handover_accepted → predecessor_stop_requested → predecessor_closed → complete` (or `cancelled`).

- **Checkpoint.** One `report_request` with `requested_kind="CHECKPOINT"` once idle. The CHECKPOINT echoing it must state completed/remaining work with at least one check, all `passed` and fresh for its `artifact_revision`; otherwise it blocks (`verification_failed`, …) and may be requested again, up to `loop_cap`. Results are **worker-attested**; nothing is executed.
- **Successor.** A new worker on the predecessor's record/revision, cwd and placement if still current and eligible (or a routed alternative), role and declared work facts carried over, assignment = the checkpoint payload. `mailbox_provision` → `launch` (`fresh=true`) carries `{worker_id, worker_generation, enrolment_token, assignment_sha256, handover_id, handover_token}`; the provision carries `handover_id` and `handover_sha256` = SHA-256(`handover_id:handover_token`), never the token. Over-bound handovers hold `input_too_large`.
- **Acceptance.** The successor's ACCEPTED and SPAWN `accept` carry the handover pair. Only after SPAWN records acceptance *and* a fresh observation shows the successor alive does ORCH+ set the predecessor's finish intent; `complete` needs SPAWN's stopped outcome with `absent`/`exited`.
- **Failures** hold with the phase and a reason; the predecessor lives until successor acceptance. Uncertain launch, accept or stop is never retried. A different controller generation cannot advance a rollover; after reload nothing advances until continuation, and a changed window incarnation fences a never-claimed successor grant (`successor_launch_fenced`). An issued landing grant never transfers to a successor; a builder's ungranted landing item is held during its rollover.

ROLLOVER_REQUEST is evidence only. Native daemon resume of a conversation is not a rollover.

## Verified coordinator rollover

**Roll over coordinator…**, or the policy trigger when `auto_rollover` and `rollover_include_coordinator` are on, the coordinator is the running owner with acknowledged activation, not retiring, idle at a clean point, over the threshold, and no other coordinator rollover or restored-coordinator hold exists. Two coordinators **never overlap** (`kind="coordinator"`, `closure` `observed` or `operator_attested`):

`requested → checkpoint_pending → checkpoint_verified → retirement_requested → predecessor_released → predecessor_stop_requested → predecessor_closed → owner_retired → successor_granted → successor_created → handover_accepted → complete`.

- The verified checkpoint quiesces the predecessor through the typed `coordinator_retirement` reply; its COORDINATOR_RELEASE, final watermark, exact stop and mailbox retirement run through the normal finish path while the slot stays occupied. Cancellation only before retirement is requested.
- After the stopped outcome and generation-bound release, one commit reserves the successor's slot and queues its provisioning; unrelated coordinator starts are refused `rollover_reserved`. The successor carries the paired owner/generation and handover; its activation token derives from the handover; `complete` needs the durable activation `reply_ack`.
- An uncertain or refused predecessor stop holds with the checkpoint retained; resolution is operator-assisted orchestrator recovery, whose retirement records `closure="operator_attested"` and lets the handover proceed.
- A coordinator releasing itself before a verified checkpoint closes the rollover `cancelled` (`predecessor_self_released`). While the rollover's CHECKPOINT request is outstanding, release is refused (held as a rejected report on the mailbox path).
- A stopped coordinator pane observed alive again is `restored` evidence: every coordinator claim, proposal and the rollover hold until an exited observation or **I stopped this restored pane**.
- From `owner_retired` on, the rollover cannot be cancelled. If the successor fails to launch, exits, is held or has a held report before accepting (`successor_launch_failed`, `successor_launch_uncertain`, `successor_launch_fenced`, `successor_unaccepted`, `successor_report_held`), the hold says no coordinator is active and shows SPAWN's diagnostic. Stop the successor pane if it exists, reconcile retained effects, then run fenced recovery on the successor's orchestrator owner card; that closes the rollover `cancelled` (`successor_owner_recovered`) and frees the slot for an explicit start from the retained checkpoint.

## Explicit verified attach

An idle, ticked hand-opened agent pane row in Config offers **Attach pane N as ORCH+ worker…** once a catalog is loaded: pick an eligible, enabled `native-agent` record with `report-files-v1`, type the assignment and attest the exact window-scoped pane. The window re-verifies the pane just before sending (this session/host, recognized native agent, idle, unbound). The `adopt` command re-checks attestation (`operator_verified_exact_agent_pane`), scope (`invalid_task`), catalog (`catalog_changed`), record (`unsupported_capability`), pause, capacity and `pane_bound`, then creates a first generation with `adopt_pane_binding` and queues the ordinary `mailbox_provision`; the launch slot carries a SPAWN `adopt` request with the same immutable enrolment (no handover or coordinator pair) plus `pane_binding` and `attestation`. SPAWN delivers its preface and the assignment once via `agents:ask`. A pane that is busy or out of scope at execution is refused `target_unavailable` and held; a lost ask is `uncertain` and never repeated. Afterwards the worker is identical to a launched one. Coordinators cannot be adopted.

## Landing queue and release manager

Landing is ordered per **logical session, project, repository and target ref** (never cwd), with **one granted slot per target**. ORCH+ never runs git and never infers landing from REVIEW_READY, DONE, idle or a closed pane. **Builders never merge:** the builder requests, the grant goes to the session's **release manager**, which merges under the repository's own rules and reports the result.

State is `dispatch.landing = {queues, items}`. A queue records its FIFO `order`, the granted `slot` and the last recorded `head` (`{revision, source=landed|stale_target|owner, landing_id}`). An item binds work, requester builder (`worker_id`), grant `holder`, the exact request `{project_id, repo_ref, target_ref, target_revision, source_ref, source_revision, checkpoint_id}`, approval gate, `proof`, history and up to eight grants. Statuses: `queued|ready`, `verifying`, `blocked`, `granted`, `landing`, `landed`, `failed`, `cancelled`.

- **Request.** The builder's LANDING_REQUEST references a retained checkpoint of the same project whose `artifact_revision` is the source revision and opens a `landing_approval` gate. Approval: the owner's answer, an approved coordinator `landing` proposal, or the in-scope policy answer (see [Autonomy](#autonomy-inside-plan-scope)). Reject or cancel withdraws the item.
- **Release manager.** When an item needs a grant, ORCH+ queues (or reuses) one live `release_manager` worker on `release_manager_record` that passes the signer rule. Its record must carry `release-manager-v1`.
- **Grant.** Only the queue head, with a free slot, approval, complete proof and signer, an accepted continued builder outside a rollover, no BLOCKED report, no pause or reserve, and a fresh latest checkpoint for the source revision receives one immutable `landing_grant {landing_id, grant_id, project_id, checkpoint_id, repo_ref, target_ref, target_revision, source_ref, source_revision, builder_work_id, review_id, reviewer_family, proof}`, addressed to the release manager, which becomes the item's `holder`. A request whose expected head differs from the recorded head is `target_moved`. Eight grants per item is a structural bound (`attempts_exhausted`).
- **Refresh.** A `target_moved` item, or a `stale_target` result, sends the builder generation exactly one `landing_refresh {landing_id, project_id, repo_ref, target_ref, expected_revision, current_revision, reason}` through the reply outbox, keyed by generation and both heads so replays never duplicate it; a further move sends one notice for the new head. A full outbox, the settlement reserve or a generation that cannot receive replies keeps the hold visible with a deferral note. The builder's fresh CHECKPOINT, review and LANDING_REQUEST rebind the item at its position and void the approval; refresh cycles count against `loop_cap` (`loop:landing_refresh`).
- **Result.** Only the holder's LANDING_RESULT correlated to the grant's action counts; a builder's is refused. `landed` records `result_revision` as head, frees the slot and owes a deploy; `rejected` fails the item; `stale_target` records the observed head, frees the slot and keeps the item as `refresh_required`. Nothing is retried automatically.
- **Uncertainty.** An `uncertain` result, DONE without a result, a lost holder (exit/stop, held generation, rejected report) or **Result lost — hold slot…** keeps the slot. **Reconcile observed outcome…** records the owner's read-only inspection as landed (with head) or not landed, with an attestation and reason. A later result for that grant is evidence only. A holder's rollover never transfers its grant.
- **Owner controls.** **Landing queue** cards show head, slot, builder, reviewer family, release manager, holds, grants and deploy status. While an item needs a refresh (`refresh_required`, or an approved item holding `target_moved`), its row reads "approval void — awaiting fresh review/request" instead of "owner approved". **Move up/down** and **Cancel…** apply only to ungranted items.

**Deploy.** A `landed` item owes one durable deploy in `dispatch.deploys`: `pending → granted → deployed | not_applicable | held | failed | uncertain | stopped`. ORCH+ issues the release manager one `deploy_grant {deploy_id, attempt_id, landing_id, revision, target_ref}`; its DEPLOY_RESULT `{deploy_id, attempt_id, landing_id, outcome: deployed|held|not_applicable|failed, revision, evidence, reason?}` must correlate to that grant. `held` and `failed` open a `deploy_hold` gate relayed to the release manager as an `owner_decision`: after `held`, **deploy** continues the same attempt and **stop** ends it; after `failed`, **retry** issues a new `deploy_grant` (new attempt, same deploy and revision), capped by `loop_cap` (`loop:deploy_attempts`). DONE while holding a grant, or **Deploy result lost — hold…**, makes it uncertain until **Reconcile** records `deployed` or `not_deployed`. Nothing is re-granted automatically.

**Upgrade from 0.3.0** (restore only). 0.3.0 grants were addressed to builders. A `granted`/`landing` item whose current grant is such a legacy grant becomes an uncertain hold `legacy_grant_outstanding` with one owner gate; only **Result lost** or **Reconcile** settles it, the grant is never re-addressed and a builder LANDING_RESULT is refused. Approved but ungranted items keep their approval and re-verify under the proof rule. Coordinator review results from 0.3.0 carry no proof and are dropped.

## Normal coordinator finish and retirement

Coordinator start needs a record configured **and provisioned** with `coordinator-control-v1` plus report-files and a wake/poll capability; nothing is marked supported automatically. The launch enrolment carries the reserved coordinator owner ID/generation only for coordinator work; SPAWN's preface tells it to ACCEPT, then wait for and claim typed activation. After ACCEPTED, ACK and SPAWN acceptance ORCH+ issues one `coordinator_activation` reply. The coordinator self-finishes with authenticated COORDINATOR_RELEASE, or **Request graceful coordinator retirement** commits one `coordinator_retirement` reply (`retire`). Both need activation's durable receipt; neither is a stop.

The controller shows activation, retirement request, quiescence, reply floors, native stop and mailbox retirement. **Read / settle** advances outboxes; **Read cumulative receipt watermark** commits the confirmed receipt chain. The final watermark must cover release and all reply acknowledgements before SPAWN receives one exact `stop`; only a durable `stopped` with the issued pane binding and `absent`/`exited` permits `mailbox_retire mode=retire`. ORCH+ then applies its generation-bound release, keeps history and fences, and clears exactly that slot; an old generation's release cannot clear a successor. Uncertain stop or retirement, failed commits and restored freshness keep ownership occupied. Coordinators from earlier builds without an issued activation stay occupied for inspected recovery. Native stop does not prove every remote descendant exited.
